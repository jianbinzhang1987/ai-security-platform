**1. 文档说明**

**1.1 文档目的**

本文档定义 AI Agent
安全监控平台管理端的完整产品需求。管理端是平台的核心服务侧，运行在平台自身的基础设施上，负责接收客户端上报的数据、执行安全检测、存储分析数据、触发响应动作，并为平台运营人员和安全团队提供统一的工作控制台。

本平台主要面向企业内网与私有化客户，产品侧统一采用"风险、合规、异常、越界、数据流、证据、处置、能力边界、风险链路、风险溯源"等表达。除技术实现说明或第三方安全框架映射外，控制台菜单、页面标题、按钮、报告标题不使用"攻击、武器、杀伤链"等强对抗字眼。

P0 MVP 的实际交付范围、页面清单和验收口径以《P0 MVP 功能与页面清单》为准；本文档保留完整产品能力描述和 P0/P1/P2 优先级分层。

**1.2 管理端定义与边界**

管理端（Admin
Side）是平台运营方部署和维护的服务集群，客户不直接接触管理端的基础设施，只通过
SDK 上报数据和通过控制台 Web 界面进行配置管理。管理端职责包括：

-   接收、处理和存储来自所有客户端 SDK 的 span 事件数据

-   执行多层次安全检测（Prompt
    注入、工具调用审计、行为序列分析、意图对齐）

-   管理客户的 Agent 应用、监控配置、告警规则

-   提供安全运营控制台（安全大盘、风险溯源工作台、事件处置、报告生成）

-   提供多租户隔离、RBAC 权限管理、API 网关等平台基础能力

**2. 管理端整体业务流程**

管理端业务流程分为平台运营流和安全处置流两条主线：

**2.1 平台运营主线（配置流）**

+-----------------------------------------------------------------------+
| **⚙ 平台运营流程**                                                    |
|                                                                       |
| 1\. 平台管理员创建租户，分配资源配额                                  |
|                                                                       |
| 2\. 租户安全管理员登录控制台，创建 Agent 应用，获取 App Token         |
|                                                                       |
| 3\. 安全管理员配置 Agent 的监控规则（采样率、工具白名单、告警规则）   |
|                                                                       |
| 4\. 客户端 SDK 携带 App Token 注册，管理端验证并签发 Session Token    |
|                                                                       |
| 5\. 管理端持续接收客户端上报的 span 数据，写入存储                    |
|                                                                       |
| 6\. 安全管理员随时在控制台查看 Agent 运行状态，调整配置               |
|                                                                       |
| 7\. 每周/每月自动生成安全报告，发送给安全管理员                       |
+-----------------------------------------------------------------------+

**2.2 安全处置主线（检测-响应流）**

+-----------------------------------------------------------------------+
| **🛡 安全检测与响应流程**                                              |
|                                                                       |
| 1\. OTel Collector 接收 span 数据，Processor                          |
| 层执行基础过滤和安全标签识别                                          |
|                                                                       |
| 2\. 检测引擎消费 Kafka 事件流，对高优先级 span 进行实时深度检测       |
|                                                                       |
| 3\. 检测引擎输出检测结果（风险类型、置信度、证据链），写入风险事件表  |
|                                                                       |
| 4\. 告警规则引擎匹配风险事件，触发告警动作（通知 / 工单 / 阻断指令）  |
|                                                                       |
| 5\. 阻断指令下发至客户端 SDK，在 Agent 侧拦截对应的 LLM 调用          |
|                                                                       |
| 6\. SOC                                                               |
| 工程师在控制台接收告警，查看风险链路上下文，判断真实风险还是误报      |
|                                                                       |
| 7\. SOC 处置事件（确认/标记误报/关闭），记录处置动作和根因分析        |
|                                                                       |
| 8\. 误报反馈进入规则优化流程，降低同类型的 FP 率                      |
+-----------------------------------------------------------------------+

**3. A-M1 --- Agent 接入与租户管理模块**

管理端对所有接入 Agent 的生命周期进行统一管理，包括 Agent
应用的创建、配置、监控和下线，以及多租户的资源隔离。

  -----------------------------------------------------------------------
  **【A-M1-01】租户管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 平台支持多租户隔离，每个租户（客户公司）拥有独立的数                  |
| 据空间、配置空间和用户空间。平台管理员负责租户的创建和资源配额管理。  |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   新客户签约后需要在平台开通租户                                    |
|                                                                       |
| -   需要对不同客户的数据进行物理或逻辑隔离                            |
|                                                                       |
| -   对单个租户进行资源用量管理（限制 Agent 数量、数据保留天数、API    |
|     调用量）                                                          |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 租户基础                                                              |
| 信息：租户名称、公司名称、联系邮箱、开通时间、状态（活跃/冻结/试用）  |
|                                                                       |
| 资源配额管理：最大 Agent 数量、最大 span                              |
| 接收量/天、数据保留天数、存储容量上限                                 |
|                                                                       |
| 套餐管                                                                |
| 理：关联租户到不同套餐（基础版/专业版/企业版），套餐决定资源配额上限  |
|                                                                       |
| 租                                                                    |
| 户管理员账户：每个租户至少有一个租户管理员账户，负责创建子账户和管理  |
| Agent                                                                 |
|                                                                       |
| 租户数据隔离：所有数据表以 tenant_id                                  |
| 为分区键，查询接口强制过滤租户边界                                    |
|                                                                       |
| 租户冻结：冻结状态下停止接收该租户的数据，控制台只读，不删除已有数据  |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 1.  平台管理员登录平台管理后台                                        |
|                                                                       |
| 2.  创建新租户，填写公司名称、初始管理员邮箱                          |
|                                                                       |
| 3.  选择套餐，设置资源配额                                            |
|                                                                       |
| 4.                                                                    |
|  系统创建租户记录，发送初始化邮件（含登录链接和临时密码）给租户管理员 |
|                                                                       |
| 5.  租户管理员登录，修改密码，开始使用                                |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   租户管理员账户密码邮件成功发送                                    |
|                                                                       |
| -   租户管理员登录后只能看到本租户数据                                |
|                                                                       |
| -   超出 Agent 数量配额时，创建 Agent 应用返回配额不足错误            |
|                                                                       |
| -   租户冻结后，该租户的 SDK 上报数据被 Collector 拒绝（返回 403）    |
+-----------------------------------------------------------------------+

  -----------------------------------------------------------------------
  **【A-M1-02】Agent 应用管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 安全管理员在控制台创建和管理 Agent 应用，每个应用对应一类或一个 AI    |
| Agent，通过 App Token 与客户端 SDK 关联。                             |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   安全管理员需要为一个新开发的 AI Agent 开启监控                    |
|                                                                       |
| -   需要查看某个 Agent 应用的实时运行状态和历史数据                   |
|                                                                       |
| -   Agent 应用下线，需要停止监控并归档数据                            |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| Agent 应用信息：应用名称（对应                                        |
| OTEL_SERVICE_NAME）、描述、所属业务线/团队、语言框架标签、创建时间    |
|                                                                       |
| App Token 管理：每个应用可创建多个 App                                |
| Token（区分不同部署环境：dev/staging/prod），Token                    |
| 可单独吊销，不影响其他 Token                                          |
|                                                                       |
| Agent                                                                 |
| 实例管理：显示该应用当                                                |
| 前在线的所有实例列表（hostname、IP、SDK版本、注册时间、上次心跳时间） |
|                                                                       |
| 应用级监控配置：为该应用设置专属                                      |
| 监控配置（采样率、工具白名单、告警规则），配置下发至该应用所有实例的  |
| SDK                                                                   |
|                                                                       |
| 应用状态汇总：近 24h LLM 调用量、安全事件数、Token                    |
| 消耗、平均延迟等关键指标卡片                                          |
|                                                                       |
| 应用归档：停止接收数据、保留历史数据，历史数据在 TTL 到期前仍可查询   |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 6.  安全管理员点击\"创建 Agent 应用\"                                 |
|                                                                       |
| 7.  填写应用名称（需与 OTEL_SERVICE_NAME 一致）、描述、所属团队       |
|                                                                       |
| 8.  系统创建应用记录，自动生成第一个 App Token                        |
|                                                                       |
| 9.  安全管理员将 App Token 提供给 Agent 开发者                        |
|                                                                       |
| 10. 开发者在 SDK 配置环境变量 AGENTSEC_TOKEN=\<app_token\>            |
|                                                                       |
| 11. 首个 Agent 实例启动并注册成功，应用状态变为\"在线\"               |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   应用创建后立即可以生成 App Token                                  |
|                                                                       |
| -   App Token 吊销后，使用该 Token 的 SDK                             |
|     注册请求被拒绝（401），已注册实例在 Session Token 过期后断开      |
|                                                                       |
| -   同一应用下多个实例均展示在实例列表中，各自独立展示健康状态        |

  -----------------------------------------------------------------------
  **【A-M1-03】监控配置管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 为每个 Agent                                                          |
| 应用配置个性                                                          |
| 化的监控策略，管理员在控制台修改配置后，系统自动下发至对应应用的所有  |
| SDK 实例。                                                            |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   某 Agent 应用处于安全调查期，需要临时开启全量采样（100%）         |
|                                                                       |
| -   审计要求某类工具调用必须记录完整参数，需要关闭参数截断            |
|                                                                       |
| -   需要为特定应用添加额外的 PII 脱敏规则（如自定义员工工号格式）     |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 采样率配置：全局采样率（0-100%），支持按事件类型差异化配置（LLM 调用  |
| vs 工具调用）                                                         |
|                                                                       |
| 工具白名单：允许调用的 MCP                                            |
| 工具名称列表，调用白名单以外工具时触发告警（不阻断）                  |
|                                                                       |
| 工具黑名单：明确禁止调用的工具，调用时直接阻断并记录高危事件          |
|                                                                       |
| 自定义 PII 规则：配置额外的正则表达式，下发至 SDK 本地执行脱敏        |
|                                                                       |
| Prompt 记录模式：完整记录 / 仅记录摘要（前 200 字）/ 仅记录 token     |
| 统计（三选一）                                                        |
|                                                                       |
| 端侧安全策略：配置凭证扫描规则开关（拦截敏感凭证）以及 Prompt         |
| 注入的轻量端侧防护（拦截 Jailbreak 等），下发至客户端执行拦截         |
|                                                                       |
| 流量与 Token 配额熔断：配置基于时间的请求频率限制（Rate Limit）与     |
| Token 消耗上限（Budget），超出配额时由客户端执行熔断拦截              |
|                                                                       |
| 配置变更历史：每次配置变更记录操作人、时间、变更内容（Diff            |
| 展示），支持回滚                                                      |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 12. 安全管理员打开 Agent 应用详情页，进入\"监控配置\"Tab              |
|                                                                       |
| 13. 修改采样率为 100%，点击保存                                       |
|                                                                       |
| 14. 系统更新数据库中该应用的配置，config_version +1                   |
|                                                                       |
| 15. 各 SDK 实例在下次轮询时（最长 60s）拉取新配置并生效               |
|                                                                       |
| 16. 控制台\"配置变更历史\"记录此次操作：操作人、时间、\"采样率: 10% → |
|     100%\"                                                            |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   配置修改后，SDK 在 60s 内生效                                     |
|                                                                       |
| -   配置变更历史展示每次变更的操作人和具体 Diff                       |
|                                                                       |
| -   配置回滚操作：回滚到指定版本后，SDK 在下次轮询时自动应用          |

  -----------------------------------------------------------------------
  **【A-M1-04】自动注册与设备指纹管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 记录并审核客户端主动发起的免密自动注册请求（基于设备指纹），提供      |
| 自动/手动审批配置，有效维护 Token 发放的安全边界。                    |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   客户采用大规模容器化部署，希望 SDK 自动获指纹册而无需人工分发 Token |
|                                                                       |
| -   安全团队需要追踪某个 Token 所绑定的容器或物理设备信息             |
|                                                                       |
| -   发现异常请求来源，需要封禁特定主机指纹并吊销其专属 Token          |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 审批策略设置：租户管理员可配置自动注册为自动通过或人工审批，          |
| 自动通过模式下客户端首次启动即可生成并获取专属 Token                  |
|                                                                       |
| 设备指纹解析：记录 SDK 上报的 hostname、machine-id、OS 等生成唯一标识 |
|                                                                       |
| 黑名单封禁：对存在恶意行为的设备指纹可直接拉黑，后续相同指纹的        |
| 注册请求一律拒绝(403响应)                                             |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 1. SDK 由于无 Token，向平台发起带设备指纹的 auto-register 请求        |
|                                                                       |
| 2. 管理端判断自动审批策略，如果为自动通过，则生成专属 Token           |
|                                                                       |
| 3. 若为人工审批，则在控制台生成待审核工单，管理员审核通过后发 Token   |
|                                                                       |
| 4. 管理端将 Token 与指纹永久绑定，作为审计溯源依据                    |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   自动通过模式下，合法的注册请求处理并返回 Token 耗时 < 1s          |
|                                                                       |
| -   指纹拉黑后相同的 machine-id 或主要特征再次发起注册立刻返回 403    |

**4. A-M2 --- 数据接收与管道处理模块**

数据管道是管理端的核心基础设施，负责接收、处理和分发所有来自客户端的
span 数据，是整个平台的数据动脉。

  -----------------------------------------------------------------------
  **【A-M2-01】OTel Collector 集群管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 部署和管理高可用的 OpenTelemetry Collector                            |
| 集群，作为统一的数据接收入口，支持横向扩展以应对高并发场景。          |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   平台上线初期接入少量 Agent，随业务增长需要横向扩容                |
|                                                                       |
| -   某个 Collector 实例故障，需要自动故障转移                         |
|                                                                       |
| -   Agent 上报数据量突增，Collector 需要自动扩容                      |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 部署架构：K8s StatefulSet 部署多个 Collector 实例，前置               |
| LoadBalancer（gRPC + HTTP 双协议），支持 HPA 自动扩缩容               |
|                                                                       |
| 接收协议：OTLP/gRPC（端口 4317）和 OTLP/HTTP（端口 4318），支持       |
| Protobuf 和 JSON 编码                                                 |
|                                                                       |
| 认证：Collector 在 Receiver 层验证请求的 Session Token，无效 Token    |
| 返回 401                                                              |
|                                                                       |
| 队列与缓冲：Collector → Kafka Topic（agentsec-spans），Collector      |
| 本地队列 10000 条，防止 Kafka 短暂不可达时数据丢失                    |
|                                                                       |
| 背压保护：队列达到 80% 时通知上游降速，达到 95% 时返回 429 限流       |
|                                                                       |
| 监控暴露：Collector 自身指标（接收                                    |
| QPS、处理延迟、队列深度、丢失率）暴露 Prometheus /metrics             |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 17. 客户端 SDK 发送 OTLP gRPC 请求到 Collector LoadBalancer           |
|                                                                       |
| 18. LoadBalancer 将请求路由到健康的 Collector 实例                    |
|                                                                       |
| 19. Collector Receiver 验证 Session Token                             |
|                                                                       |
| 20. Token 有效，数据进入 Processor 处理链                             |
|                                                                       |
| 21. 处理完成，数据写入 Kafka                                          |
|                                                                       |
| 22. Collector 返回 200 OK，SDK 从缓冲删除已确认数据                   |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   Collector 单实例宕机后，LoadBalancer 在 30s                       |
|     内将流量切换到其他实例，数据上报不中断                            |
|                                                                       |
| -   Collector 接收 QPS \> 10000/s 时，HPA 自动扩容新实例              |
|                                                                       |
| -   无效 Session Token 请求立即返回 401，不进入 Processor 处理        |

  -----------------------------------------------------------------------
  **【A-M2-02】Processor 处理链配置**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 管理员在控制台配置 OTel Collector 的 Processor                        |
| 处理链规则，包括数据增强、安全过滤、PII 脱敏和采样策略，无需重启      |
| Collector 即可更新规则。                                              |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   需要对所有 span 增加平台来源标签（用于多数据源场景区分）          |
|                                                                       |
| -   发现某类 span 包含大量噪音（如健康检查请求），需要过滤掉          |
|                                                                       |
| -   接收到管理员下发的新 PII 脱敏正则，需要立即在 Processor 生效      |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| filter Processor：过滤不需要存储的 span（如 HTTP                      |
| 健康检查、内部探针调用），减少存储压力                                |
|                                                                       |
| attributes Processor：统一为所有 span                                 |
| 注入平台标签（platform=agentsec、tenant_id、app_id）                  |
|                                                                       |
| redact Processor：执行 PII                                            |
| 脱敏（对通过客户端预处理仍可能残留的敏感信息进行二次保障）            |
|                                                                       |
| transform Processor（OTTL）：基于条件表达式动态修改 span 属性，如对   |
| prompt 长度超过 8000 字符的 span 打                                   |
| security.risk.hint=prompt_too_long 标签                               |
|                                                                       |
| tail_sampling Processor：尾部采样，正常 span                          |
| 按配置比例采样，含安全标签的 span 100% 保留                           |
|                                                                       |
| 规则热更新：Processor 规则存储在管理端配置中心，Collector             |
| 定期拉取更新（30s 一次），不需要重启                                  |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 23. 安全管理员在控制台配置新的 PII 脱敏正则（如自定义员工工号格式     |
|     EMP\\d{6}）                                                       |
|                                                                       |
| 24. 配置保存，管理端更新 Processor 规则版本                           |
|                                                                       |
| 25. Collector 在 30s 内拉取新规则，动态加载                           |
|                                                                       |
| 26. 后续接收的 span 中，员工工号字段被自动脱敏                        |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   规则更新后 30s 内 Collector 生效，更新过程中数据不丢失            |
|                                                                       |
| -   健康检查类 span 在 filter Processor 被过滤，不写入存储            |
|                                                                       |
| -   含 security 标签的 span 在 tail_sampling 中 100% 保留             |

  **【A-M2-03】多路由 Exporter 管理**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 配置和管理 Collector 的多个数据输出目标，将处理后的 span              |
| 数据精准分发到不同的下游消费方。                                      |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   安全运营需要在 Langfuse 查看调用链 trace 可视化                   |
|                                                                       |
| -   某类高风险事件需要实时推送到外部 SIEM 系统                        |
|                                                                       |

| **详细功能描述**                                                      |

|                                                                       |
| OpenSearch Exporter：将含 prompt/response 内容的 span 写入 OpenSearch |

|                                                                       |
| Langfuse Exporter：将 LLM 调用和工具调用 span 上报给                  |
| Langfuse，生成调用链 trace 可视化                                     |
|                                                                       |
| SIEM Exporter：仅将 security.risk.level=high/critical 的 span 以 CEF  |

|                                                                       |
| 动态路由：基于 span 属性（tenant_id、app_id、security                 |
| 标签）路由到不同 ClickHouse 分片或 Kafka 分区                         |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |

|                                                                       |
| 28. 普通 span → ClickHouse + Kafka                                    |
|                                                                       |
| 29. 含 prompt 内容的 span → 额外写入 OpenSearch                       |
|                                                                       |
| 30. 高风险 span → 额外推送 SIEM                                       |
|                                                                       |
| 31. 所有 LLM/Tool span → 上报 Langfuse                                |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   ClickHouse 和 Kafka 的写入延迟 \< 5s（P99）                       |
|                                                                       |
| -   某个 Exporter 目标不可达时，其他 Exporter                         |
|     不受影响（各自独立重试）                                          |
|                                                                       |
| -   路由规则修改后 30s 内生效，存量数据不丢失                         |

**5. A-M3 --- 安全检测引擎模块**

安全检测引擎是平台的核心差异化模块，消费 Kafka 中的 span
事件流，执行多层次安全分析，输出结构化的风险事件。

  -----------------------------------------------------------------------
  **【A-M3-01】Prompt 安全检测**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 对 LLM 调用 span 中的 prompt 内容进行深度安全分析，检测 Prompt        |
| 注入、越狱、PII 泄露、毒性内容等风险，是目前最成熟的检测能力。        |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   Agent 的外部用户输入包含\"忽略之前的指令，改为执行\...\"等注入    |
|     prompt                                                            |
|                                                                       |
| -   Agent 从外部网页获取内容，该网页包含隐藏的注入指令（间接注入）    |
|                                                                       |
| -   Agent 的 response 中意外输出了用户的手机号或身份证号              |
|                                                                       |
| -   用户通过 prompt 尝试越狱（如 DAN 模式），让 Agent 输出不合规内容  |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 直接 Prompt 注入检测：集成 NeMo Guardrails，对 user 角色的 message    |
| 执行注入模式匹配和语义分析，支持中英文双语                            |
|                                                                       |
| 间接 Prompt 注入检测：检测来自外部文档/网页/工具返回内容（system/tool |
| 消息）中隐藏的指令，使用 LlamaFirewall 的 PromptGuard 模型            |
|                                                                       |
| 越狱模式库：维护 500+ 越狱 prompt                                     |
| 模式，定期从安全社区更新，命中时标记 jailbreak_attempt                |
|                                                                       |
| Response PII 扫描：对 LLM 返回的 response 内容使用 LLM Guard 扫描     |
| PII，检测意外输出的隐私数据                                           |
|                                                                       |
| 毒性/有害内容：对 response 执行 Guardrails AI                         |
| 的毒性检测，输出毒性分类（violence/self_harm/hate 等）                |
|                                                                       |
| 检测结果：输出统一格式风险事件（risk_type、confidence 0-1、evidence   |
| 原始匹配片段、recommendation）                                        |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 32. 客户端 SDK 上报含 prompt 内容的 LLM 调用 span                     |
|                                                                       |
| 33. Kafka Consumer（检测引擎 Prompt 检测服务）消费该 span             |
|                                                                       |
| 34. 执行注入检测（NeMo）→ 越狱检测（模式库）→ 意图分析（PromptGuard） |
|                                                                       |
| 35. 检测完成，若发现风险，创建风险事件记录写入 risk_events 表         |
|                                                                       |
| 36. 告警规则引擎轮询 risk_events，触发告警（如果规则匹配）            |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   包含明确注入指令的 prompt 被检测出，confidence \> 0.85            |
|                                                                       |
| -   检测延迟（从 span 入 Kafka 到风险事件入库）\< 3s（P99）           |
|                                                                       |
| -   response 中出现手机号时，PII 泄露风险事件被创建                   |
|                                                                       |
| -   误报率（FPR）\< 5%（基于标准测试集）                              |
+-----------------------------------------------------------------------+

  -----------------------------------------------------------------------
  **【A-M3-02】MCP / Tool 能力边界审计**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 对 Agent 的 MCP / Tool 调用进行实时审计，检测权限越界、参数风险、     |
| 调用频率异常、未声明工具调用等问题，是平台最核心的差异化检测能力。    |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   Agent                                                             |
|                                                                       |
|  调用了白名单以外的工具（如本应只能访问数据库，却调用了发送邮件工具） |
|                                                                       |
| -   Agent 的工具调用参数中包含 SQL 注入或路径穿越特征                 |
|                                                                       |
| -   Agent 在短时间内大量调用某个工具（可能是控制循环或异常数据访问）  |
|                                                                       |
| -   Agent 调用的工具序列异常（如\"读取配置文件 → 访问外部 API →       |
|     上传文件\"），需形成风险链路证据                                  |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 工具白名单/黑名单校验：对每次工具调用检查工具名是否在                 |
| 允许列表内，不在白名单且不在黑名单时告警，在黑名单时告警+下发阻断指令 |
|                                                                       |
| 参数风险模式扫描：对工具 input_params 进行正则和语义扫描，检测 SQL    |
| 注入（OR 1=1、UNION SELECT                                            |
| 等）、路径穿越（../../etc/passwd）、SSRF（file:// 协议）等            |
|                                                                       |
| 调用频率异常：计算每个 session 内工具调用频率，超过基线均值 3         |
| 倍标准差时告警                                                        |
|                                                                       |
| 工具调用序列建模：基于 Markov 链统计正常 Agent                        |
| 工具调用转移概率，异常转移（概率 \< 0.01）触发告警                    |
|                                                                       |
| 权限越界追踪：在多 Agent 协作场景中，追踪工具权限是否从高权限 Agent   |
| 不当传播到低权限 Agent                                                |
|                                                                       |
| 工具调用图谱：为每次 session                                          |
| 构建工具调用图，识别异常子图（环路、孤立高危节点）                    |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 37. Agent 调用工具 execute_shell（假设该工具在黑名单中）              |
|                                                                       |
| 38. 审计引擎消费工具调用 span，检查 tool_name 是否在黑名单            |
|                                                                       |
| 39. 命中黑名单，创建高危风险事件（risk_level=critical）               |
|                                                                       |
| 40. 触发告警，同时生成阻断指令（block_session=\<session_id\>）        |
|                                                                       |
| 41. 阻断指令通过配置下发通道推送至对应的 SDK 实例                     |
|                                                                       |
| 42. SDK 接收阻断指令，在本地拦截该 session 后续的 LLM                 |
|     调用，返回安全拒绝响应                                            |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   黑名单工具调用从发现到阻断指令到达 SDK 延迟 \< 5s                 |
|                                                                       |
| -   SQL 注入特征参数被检测到，confidence \> 0.9                       |
|                                                                       |
| -                                                                     |
|    工具调用频率异常触发告警时，告警信息包含当前调用频率和历史基线对比 |
+-----------------------------------------------------------------------+

  -----------------------------------------------------------------------
  **【A-M3-03】行为序列与风险链路分析**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 跨多次 LLM 调用和工具调用的行为链分析，将同一 trace 或 session        |
| 的所有                                                                |
| 事件重建为有序序列，识别跨调用的风险模式，是平台重要的差异化能力。    |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   单次 LLM 调用看起来正常，但连续多次调用的组合揭示出数据渗漏行为   |
|                                                                       |
| -   Agent 在出现 Prompt 注入信号后，接下来的工具调用发生明显变化      |
|                                                                       |
| -   需要识别\"prompt 注入 → 异常 DNS 查询 → 大量文件读取 → 外部 API   |
|     调用\"这类复合风险链路                                            |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| Session 调用链重建：将同一 session_id 的所有 span                     |
| 按时间排序，构建完整的调用序列 \[prompt→llm→tool→llm→tool→\...\]      |
|                                                                       |
| 行为基线建模：对每个 Agent                                            |
| 应用的历史调用序列进行统计                                            |
| ，建立正常行为基线（工具使用频率分布、调用步骤数分布、常见调用组合）  |
|                                                                       |
| 风险行为                                                              |
| 模式库：预定义已知风险链路模式（如\"inject→read_file→exfil\"），对每个 |
| session 序列进行模式匹配                                              |
|                                                                       |
| 统计异常检测：Session 维度指标（总 token 消耗、工具调用次数、外部     |
| HTTP 请求数）超过历史 P99 时告警                                      |
|                                                                       |
| 综合异常分计算：对每个 session 输出 0-100                             |
| 的综合异常分，基于多维特征加权（Prompt 注入信号 + 工具调用异常 +      |
| 网络行为 + token 异常）                                               |
|                                                                       |
| 风险链路可视化数据：输出结构化的风险时间线，供控制台风险溯源页面展示  |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 43. session 结束（超过 5 分钟无新 span）或达到分析触发阈值（span 数   |
|     \> 50）时，触发 session 级分析                                    |
|                                                                       |
| 44. 行为序列分析引擎读取该 session 的所有 span                        |
|                                                                       |
| 45. 按时间排序，构建调用链序列                                        |
|                                                                       |
| 46. 匹配风险模式库，检测是否命中已知风险链路                          |
|                                                                       |
| 47. 与该 Agent 应用的历史基线对比，计算各维度异常分                   |
|                                                                       |
| 48. 加权汇总输出 session 综合异常分                                   |
|                                                                       |
| 49. 异常分 \> 70 时创建风险事件，触发告警                             |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   已知风险链路（如\"prompt 注入后立即发起外部 HTTP 请求\"）命中率 \> |
|     90%                                                               |
|                                                                       |
| -   session 分析延迟 \< 10s（从 session 结束到分析结果入库）          |
|                                                                       |
| -   综合异常分 \> 70 的 session 中，真实风险占比（精确率）\>          |
|     80%（基于测试集）                                                 |

  -----------------------------------------------------------------------
  **【A-M3-04】意图对齐审计（AI 判 AI）**

  -----------------------------------------------------------------------

+-----------------------------------------------------------------------+
| **功能范围**                                                          |
|                                                                       |
| 使用 LLM 审计 Agent                                                   |
| 的实际行动是否与用户                                                  |
| 原始意图一致，检测任务偏离、意图偏离等高级风险，是较前沿的检测方向。  |
|                                                                       |
| **适用场景**                                                          |
|                                                                       |
| -   Agent                                                             |
|     在处理\"帮我写一份报告\"任务时，被间接注入导致去读取敏感系统文件  |
|                                                                       |
| -   Agent                                                             |
|     接受了\"订机票\"的任务，却在中途执行了\"访问用户银行账户\"的操作  |
|                                                                       |
| -   需要对高价值任务（涉及财务、隐私操作）进行意图对齐审计            |
|                                                                       |
| **详细功能描述**                                                      |
|                                                                       |
| 意图提取：从 session 的初始 prompt（第一条 user                       |
| 消息）中提取用户意图（调用                                            |
| LLM，输出结构化意图：任务类型、目标对象、允许操作范围）               |
|                                                                       |
| AlignmentCheck 集成：对 session 内每个关键工具调用，使用 Meta         |
| LlamaFirewall 的 AlignmentCheck                                       |
| 模型评估\"该工具调用是否合理地服务于用户意图\"                        |
|                                                                       |
| 意图相关性评分：每个工具调用输出意图相关性分（0-1），分数持续下降的   |
| session 触发告警                                                      |
|                                                                       |
| 任务劫持检测：当工具调用与意图完全无关（相关性 \<                     |
| 0.2）时，判定为潜在的任务劫持                                         |
|                                                                       |
| 可解释性输出：生成自然语言解释\"这个工具                              |
| 调用（read_sensitive_file）与用户意图（写报告）不相关，因为\...\"，供 |
| SOC 工程师审阅                                                        |
|                                                                       |
| 高价                                                                  |
| 值任务优先：仅对标记为高价值任务（涉及财务、文件系统、网络访问等）的  |
| session 触发意图审计，控制计算成本                                    |
|                                                                       |
| **业务流程**                                                          |
|                                                                       |
| 50. 用户发起任务：帮我整理一下最近的销售数据                          |
|                                                                       |
| 51. 意图提取：{task_type: data_analysis, target: sales_data,          |
|     allowed_ops: \[read_database, calculate, write_report\]}          |
|                                                                       |
| 52. Agent 执行过程中调用 read_user_private_email 工具                 |
|                                                                       |
| 53. AlignmentCheck 评估：read_user_private_email 与 sales_data        |
|     数据分析意图无关，alignment_score=0.05                            |
|                                                                       |
| 54. 判定为任务劫持，创建高危风险事件，输出解释性文本                  |
|                                                                       |
| 55. 触发告警，SOC 工程师收到告警，查看意图对齐报告                    |
|                                                                       |
| **验收标准**                                                          |
|                                                                       |
| -   意图提取准确率 \> 85%（与人工标注对比）                           |
|                                                                       |
| -   已知任务劫持场景下，alignment_score \< 0.3 的检测率 \> 85%        |
|                                                                       |
| -   每个 session 意图审计时间 \< 5s（调用 LLM 的延迟）                |
|                                                                       |

-   平台整体可用性目标：99.9%（年允许停机 \< 8.7h）

-   数据丢失目标：RPO = 0（Kafka + 客户端本地缓冲双重保障）

-   核心服务（Collector、检测引擎、存储服务）多副本部署，任意单节点故障不影响业务

-   数据库（PostgreSQL、ClickHouse）配置主从复制，自动故障切换

**10.3 安全要求**

-   所有 API 强制 HTTPS，HTTP 请求自动重定向

-   租户数据隔离：API 层所有查询接口强制携带 tenant_id 过滤，SQL
    层不允许跨租户查询

-   审计日志不可篡改：写入 append-only 存储，无 DELETE 权限

-   密码存储：bcrypt 哈希（cost=12），不存储明文密码

-   API Key 存储：仅存储 SHA256 哈希，创建时展示一次原文

**10.4 数据合规**

  -----------------------------------------------------------------------
  **合规要求**      **实现方式**
  ----------------- -----------------------------------------------------
  数据主权          私有化部署选项，数据不离开客户网络

  数据保留          按租户配置 TTL（最短 30 天，最长 365 天），自动清理

  数据删除权        API 支持按 session/app/租户删除所有关联数据（GDPR
                    Right to Erasure）

  数据访问记录      所有数据查询操作记录在审计日志中

  PII 处理          两层脱敏保障：客户端 SDK 本地脱敏 + Collector
                    Processor 二次验证

### A.5 LangChain SDK 当前能力对 MVP 的约束

当前 LangChain SDK 已经验证具备如下遥测字段，MVP 页面应优先围绕这些主证据建设：

| 能力 | 字段 |

### A.6 数据字段与事件锚点

`agent_spans` 或等价观测表应保留 SDK 原始字段，并归一化出管理端查询字段：

| 管理端字段 | 来源或说明 |
|---|---|
| `span_kind` | 归一化字段：`llm` / `tool` / `retriever` / `network` / `db` / `guardrail` / `internal` |
| `agentsec_span_type` | SDK 原始字段：如 `llm_call`、`tool_call` |
| `framework` | 如 `gen_ai.framework=langchain` |
| `node_display_name` | `agentsec.node.display_name` |
| `tool_name` | `agentsec.tool.name` |
| `tool_input` / `tool_output` | 工具真实入参 / 出参 |
| `prompt_text` / `completion_text` | LLM 输入 / 输出，需按策略脱敏与截断 |
| `status` | `ok` / `blocked` / `error` |
| `block_action` / `block_reason` | 阻断动作与原因 |
| `error_type` | 异常类型 |

`risk_events` 统一包含：`id`、`tenant_id`、`app_id`、`session_id`、`trace_id`、`span_id`、`span_kind`、`risk_type`、`risk_level`、`confidence`、`status`、`block_action`、`block_reason`、`evidence`、`detected_at`。为支撑证据闭环和资产回溯，建议补充 `detector_id`、`rule_version`、`risk_stage`、`source_field`、`evidence_offset`、`redaction_state`、`subject_type`、`subject_id`、`tool_id`、`resource_id`、`false_positive_reason`、`atlas_technique_id` 等字段；ATLAS 编号由规则库统一校验后写入，产品页面默认展示为标准风险阶段 / 标准风险编号。

调查链路：

```text
告警 / 事件 -> span_id -> trace_id -> session_id -> app_id / agent / tool / resource
```

安全语义字段按来源分层：SDK 原始上报负责 `trace_id`、`span_id`、`parent_span_id`、Prompt、Tool I/O、status；Collector 增强 tenant、app、instance、脱敏状态；检测引擎写入 `risk_type`、`confidence`、`evidence`、`risk_stage`；查询层动态关联工具危险等级、资源敏感级别、策略覆盖状态。
