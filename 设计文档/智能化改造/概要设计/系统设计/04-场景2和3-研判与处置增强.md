# 智能化改造概要设计 — 场景2&3：研判与处置增强

## 1. 场景2：风险研判增强

### 1.1 场景目标

从"纯人工研判"升级为"AI辅助研判+人工确认+反馈回流"模式，提升研判效率和准确性，同时建立持续改进的反馈闭环。

### 1.2 AI智能研判摘要

#### 1.2.1 研判流程

```text
风险事件创建
→ 触发AI研判任务（异步）
→ 收集事件关联证据(Span序列)
→ 构造研判Prompt（含证据引用+风险上下文）
→ 调用大模型生成研判摘要
→ 写入ai_judgement_result
→ 更新事件ai_analysis_status=generated
→ 事件详情页展示AI研判卡片
→ 人工确认/修正/补充
→ 反馈回流样本库
```

#### 1.2.2 研判输出结构

```text
ai_judgement_result:
  核心字段:
  - judgement_id: 研判结果唯一标识
  - event_id: 关联事件ID
  - inference_id: 关联AI推理记录ID
  - attack_technique: 攻击手法分析
  - impact_assessment: 影响面评估
  - similar_events: 相似历史事件引用列表(event_id列表)
  - priority_suggestion: 处置优先级建议(low/medium/high/critical)
  - reasoning: 判断理由与依据引用
  - confidence_level: 置信等级(high/medium/low)
    → low置信必须人工复核
  - missing_evidence: 缺失证据列表
  - open_questions: 需人工补充的问题
  - model_version: 模型版本号
  - prompt_template_version: Prompt模板版本号
  - generated_at: 生成时间

  反馈字段:
  - adoption_status: 采纳状态(pending/confirmed/modified/rejected)
  - modification_content: 修正内容
  - modifier: 修正人
  - modification_time: 修正时间
  - knowledge_recalled: 是否召回知识(bool)
  - recalled_knowledge_ids: 召回的知识条目ID列表
```

#### 1.2.3 不确定性表达

安全研判中"哪里不确定"比一段顺滑摘要更有价值，AI研判必须输出：

1. **置信等级**：high/medium/low，low置信必须人工复核
2. **缺失证据列表**：哪些关键证据未获取，影响判断完整性
3. **需人工补充的问题**：AI无法判定的开放问题

#### 1.2.4 约束

- 研判摘要为建议性质，安全运营可确认/修正/补充
- 高危事件必须人工确认后才可采纳
- 研判过程和结果必须审计留痕
- AI研判状态枚举：
- `pending` — 等待AI研判
- `generated` — AI研判已生成
- `timeout` — AI研判超时
- `error` — AI研判调用出错
- `circuit_open` — 熔断器打开，研判暂停
- `skipped` — 策略配置跳过AI研判
- `confirmed` — 人工确认采纳
- `modified` — 人工修正
- `rejected` — 人工拒绝

### 1.3 攻击链自动还原

```text
输入：事件关联的完整Span序列
处理：大模型分析Span序列，还原攻击链路
输出：
  - attack_chain_graph: 攻击链路图（节点=Span，边=因果/时序关系）
  - attack_stages: 攻击阶段标注（侦察/武器化/投递/利用/升级/横向/外泄）
  - intent_inference: 意图推断
  - key_turning_points: 关键转折点
约束：自动还原结果为辅助展示，不改变任何数据状态
```

### 1.4 知识检索辅助研判

#### 1.4.1 调用契约

| 项目 | 说明 |
|---|---|
| 检索方式 | 向量相似检索为主，关键词检索为辅 |
| 调用模式 | 同步RAG（研判场景需要即时结果） |
| 结果注入 | 检索结果先过内容安全扫描再注入Prompt |
| 角色分离 | 系统提示词与知识内容分不同角色 |
| 输出 | 知识检索结果列表+相关性评分+知识来源引用+可信度元数据 |

#### 1.4.2 RAG安全沙箱

```text
知识检索结果
→ 内容安全扫描（检测恶意指令注入）
→ 通过扫描的结果注入Prompt（角色分离：system vs knowledge）
→ 未通过扫描的结果过滤，标注过滤原因
→ AI输出必须引用知识来源
→ 知识内容不可覆盖系统指令
```

#### 1.4.3 知识引用关联

```text
ai_knowledge_reference:
  - reference_id: 引用唯一标识
  - judgement_id: 关联研判结果ID（或inference_id）
  - knowledge_entry_id: 知识条目ID
  - knowledge_version: 知识版本号
  - referenced_at: 引用时间
  - recall_status: 召回状态(not_recalled/recalled)
    → 知识条目下架时，相关引用的recall_status标记为recalled
    → 关联的研判结果标注knowledge_recalled=true
```

### 1.5 相似历史事件关联

```text
输入：当前风险事件（类型/特征/证据摘要）
处理：
  1. 向量相似检索历史事件（基于事件嵌入向量）
  2. 关键词匹配补充
输出：
  - similar_events: 相似事件列表(event_id + similarity_score)
  - key_similarities: 关键相似点标注
约束：关联结果为参考性质，不自动继承处置结论
```

### 1.6 反馈闭环机制

```text
人工操作AI研判结果
├── 确认(采纳)
│   → adoption_status=confirmed
│   → 样本标注"确认命中" → 候选集
├── 修正
│   → adoption_status=modified
│   → 记录修正内容和原因
│   → 样本 → 候选集 → 争议集
└── 拒绝
    → adoption_status=rejected
    → 标注"误报"+原因
    → 样本 → 候选集 → 争议集

反馈自动收集，不需手动触发
修正和拒绝的样本优先进入下一轮模型评测
```

### 1.7 数据模型影响

| 现有实体 | 新增字段 | 说明 |
|---|---|---|
| `risk_event` | `ai_analysis_id` (FK) | 关联AI研判结果实体（替代JSON blob） |
| `risk_event` | `ai_analysis_status` (enum) | AI研判状态：pending/generated/timeout/error/circuit_open/skipped/confirmed/modified/rejected |

**新增实体：**

- `ai_judgement_result`：AI研判结果（含不确定性表达、反馈字段）
- `ai_knowledge_reference`：AI推理与知识条目的引用关联表

## 2. 场景3：处置响应增强

### 2.1 场景目标

从"纯人工处置"升级为"AI建议+受限自动响应+人工审批"模式，提升处置效率同时确保安全可控。

### 2.2 AI处置建议

#### 2.2.1 建议生成流程

```text
输入：风险事件（类型/等级/影响面）+ 历史处置效果
处理：大模型生成处置建议
输出：
  - recommended_action_type: 推荐动作类型
  - suggested_scope: 建议范围
  - ttl_suggestion: TTL建议
  - impact_assessment: 影响评估
  - approval_level: 审批级别推荐
约束：建议性质，高危处置必须人工确认和审批
```

### 2.3 自动响应四级动作分级

#### 2.3.1 动作分级表

| 级别 | 动作类型 | 可否自动执行 | 审批要求 | TTL | 灰度 | 回滚 | 最大影响范围 |
|---|---|---|---|---|---|---|---|
| **L1 通知类** | 告警通知、消息推送 | 可自动 | 规则审批后启用 | 默认带 | 支持 | 无需回滚 | 单人 |
| **L2 观察类** | 标记观察、升级关注、加入监控名单 | 可自动 | 规则审批后启用 | 默认带 | 支持 | 移除标记 | 单会话 |
| **L3 软限制类** | 会话TTL限制、频率降级、工具调用次数限制 | 可自动（需白名单） | 规则审批+业务确认 | 必须 | 必须 | 自动恢复 | 单Agent/单应用 |
| **L4 强控制类** | 应用降级、工具禁用、主体阻断、策略变更 | **不可自动** | 必须人工审批+MFA | 必须 | 必须 | 必须支持 | 多应用/全局 |

#### 2.3.2 L3软限制类特殊约束

- 必须有白名单机制（仅对白名单内对象生效）
- 必须有熔断机制（影响超过N个会话则暂停该规则）
- 所有自动执行动作必须写入审计日志
- 自动响应动作默认带TTL到期自动恢复
- 自动响应规则需审批后启用，支持灰度模式
- 执行失败必须告警并转人工

### 2.4 自动响应职责边界

**谁判定：** `policy-service` 的自动响应规则引擎
- 接收 `event-service` 的事件通知
- 匹配 `auto_response_rule` 触发条件
- 判定是否满足自动执行条件（白名单/熔断/灰度）
- **输出：** 执行指令（action_type + target + TTL）

**谁执行：** 分级执行
- **L1/L2：** `policy-service` 直接执行（通知/标记操作）
- **L3：** `policy-service` 调用 `event-service` 执行限制动作
- **L4：** **禁止自动执行**，必须人工在 `event-service` 发起审批流程

**谁回滚：**
- **TTL自动恢复：** `policy-service` 定时任务扫描 `auto_response_execution`，TTL到期自动回滚
- **手动提前恢复：** 运营人员在 `event-service` 动作台账点击"恢复"，调用 `policy-service` 执行回滚
- **急停批量恢复：** 在 `policy-service` 急停页面一键恢复所有可逆动作

**谁写台账：**
- **判定记录：** `policy-service` 写 `auto_response_execution`（判定结果/执行指令）
- **执行记录：** `event-service` 写 `event_action`（实际动作执行结果/回滚状态）
- **审计记录：** `audit-service` 写审计日志（谁/何时/执行了什么/是否回滚）

**服务调用链：**
```
event-service (风险事件创建)
  ↓ 发送事件通知
policy-service (规则匹配与判定)
  ├─ L1/L2: 直接执行，写auto_response_execution
  ├─ L3: 调用event-service执行，写auto_response_execution
  └─ L4: 不自动执行，返回"需人工审批"
event-service (执行L3动作/人工执行L4，写event_action)
audit-service (全链路审计)
```

### 2.5 自动响应规则数据结构

```text
auto_response_rule:
  - rule_id: 规则唯一标识
  - name: 规则名称
  - description: 规则描述
  - trigger_condition: 触发条件（风险类型+等级+来源组合，JSON表达式）
  - action_level: 动作级别(L1/L2/L3/L4)
  - action_type: 动作类型(notify/mark/throttle/block/...)
  - action_config: 动作配置（动作参数，如通知模板、限制阈值等）
  - action_scope: 动作范围定义
  - whitelist: 白名单（L3必须，对象ID列表）
  - circuit_breaker_threshold: 熔断阈值（影响超过N个会话则暂停）
  - ttl_seconds: TTL（秒，L3/L4必须，L1/L2默认）
  - approval_status: 审批状态(pending/approved/rejected)
  - approval_id: 审批单ID
  - enabled: 启用状态(true/false)
  - gray_percentage: 灰度比例(0-100)
  - tenant_id: 租户ID
  - created_by/updated_by: 创建人/更新人
  - created_at/updated_at: 创建时间/更新时间

auto_response_execution:
  - execution_id: 执行唯一标识
  - rule_id: 关联规则
  - event_id: 关联事件
  - action_level: 动作级别
  - executed_action: 执行动作描述
  - execution_result: 执行结果(success/failed/pending_rollback)
  - execution_time: 执行时间
  - executor_type: 执行类型(auto/manual)
  - auto_recoverable: 是否可自动恢复
  - ttl_remaining: TTL剩余秒数
  - recovered: 是否已恢复
  - recover_time: 恢复时间
  - recover_type: 恢复类型(auto_ttl/manual_early/emergency_batch)
  - failure_reason: 失败原因
```

### 2.5 人工撤销与紧急停止机制

| 操作 | 作用范围 | 触发方式 | 效果 |
|---|---|---|---|
| **全局急停** | 所有自动响应规则 | 管理界面一键急停按钮 | 所有自动响应规则暂停，已执行动作按TTL自然恢复 |
| **单规则暂停** | 指定自动响应规则 | 规则详情页暂停按钮 | 该规则暂停，已执行动作按TTL自然恢复 |
| **单租户暂停** | 指定租户的所有自动响应 | 租户管理页暂停按钮 | 该租户自动响应暂停 |
| **手动提前恢复** | 单个已执行的自动动作 | 动作台账手动恢复按钮 | 立即恢复，不等待TTL到期 |
| **急停后批量恢复可逆动作** | L2标记/L3频率降级等可逆动作 | 急停页面批量恢复按钮 | 立即恢复所有可逆动作，L1通知无需恢复 |

**约束：**

- 全局急停操作必须审计留痕
- 急停后需人工重新启用自动响应规则，不可自动恢复
- 急停后可选择立即恢复可逆动作（L2标记移除、L3限制解除），也可选择按TTL自然恢复

### 2.6 AI规则优化建议

#### 2.6.1 优化建议流程

```text
前置条件：样本采集与标注闭环已建立（底座3），有足够的确认样本和误报样本

流程：
1. 从样本库提取误报/命中样本
2. 大模型分析样本特征，生成规则调整建议
3. 建议类型：
   - 条件修改建议（修改现有规则条件）
   - 阈值调整建议（调整置信度/风险评分阈值）
   - 新增规则建议（发现新的攻击模式）
4. 干跑验证：用历史流量回放验证建议效果
5. 影响面估算：评估规则变更的影响范围
6. 建议经审批后发布

约束：
- 建议性质，支持干跑验证闭环
- 规则变更必须走正式审批流程
- 建议必须经过历史流量回放和影响面估算
- 发布后标注ai_optimized=true
```
