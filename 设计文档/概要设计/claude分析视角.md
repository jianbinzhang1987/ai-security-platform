大模型安全监测平台 — 设计分析与改进建议

**文档说明**：本文档综合两个独立 AI 分析视角对当前平台设计的审查结论，结合对现有原型页面、PRD、概要设计、详细设计、SDK 能力说明等文档的逐一核查，提出系统性改进建议。两个视角互为补充，已在本文中整合去重。

**版本**：v1.1 | **日期**：2026-04-16 | **状态**：参考使用

---

## 一、核心结论

> **不要把平台做成"LLM 版 APM"，而应该做成"智能体运行安全证据平台"。**

现有文档中已经出现了正确的核心口径：`app_id` 是治理边界，`trace_id` 是调查入口，`span_id` 是最小证据锚点，`session_id` 是跨轮聚合视角（见 `目录结构.md:3` 和 `admin_prd_管理端需求文档.md:1702`）。

`安全可观测性设计概念规范` 中定义的 C1～C7 概念体系是目前设计中最有价值的部分，方向正确。`目录结构.md` 中将安全主轴重构为"智能体(Actor) → 行为意图(Intent) → 工具/MCP(能力边界)"也是正确方向。

**最大问题是：设计文档的新理念、PRD 主体、数据模型和原型页面四者尚未收敛。** 概念规范已经往"安全可观测性"走，但原型仍有大量"性能可观测性 / 运维监控"惯性残留。需要以安全调查主链路为标准，重新对齐所有页面的信息优先级。

**面向内网客户的产品文案口径**：本平台主要面向企业内网与私有化客户，正式产品页面和对外材料应尽量避免使用"攻击、武器、杀伤链"等强对抗字眼。建议统一使用"风险、合规、异常、越界、数据流、证据、处置、能力边界、风险链路、风险溯源"等表达。本文档中的技术框架说明可保留必要的安全行业术语，但菜单、页面标题、按钮、报告标题应优先采用内网客户更易接受的合规与风险治理口径。

## 二、参考资料的认知边界

当前参考资料（Dify、ARMS、Langfuse 等）全部是**性能/运营可观测性**视角，这是设计安全功能时的认知天花板：

| 参考资料关注（已有） | 你实际需要关注（缺少） |
|---|---|
| Token 消耗、推理成本 | 高风险意图识别、风险置信度 |
| Latency、P99 延迟 | 风险链路重建、风险路径还原 |
| LLM 调用成功率 | 数据泄露风险、PII 曝露轨迹 |
| Workflow 节点执行状态 | 工具权限越界、影子工具发现 |
| RAG 召回质量 | 注入载荷定位、间接注入追踪 |
| 多轮对话体验指标 | 任务劫持检测、意图偏移评分 |

参考资料中**适合借鉴**的部分：OTel 协议规范、Trace Link 联通方案、输入输出采集机制、Collector 健康指标。

安全平台**必须额外补齐**的部分：风险分类体系、证据链完整性、权限边界审计、阻断响应闭环、标准风险映射（可参考 MITRE ATLAS，但产品侧不必直接暴露强对抗术语）。

## 三、当前原型的具体问题（逐一核查）

以下问题均经过对原型 HTML 文件的实际核查确认。

### 3.1 安全大盘仍像通用监控大盘

`pages/assets/dashboard.html:74` 第一屏展示的是：

```
接入应用总数 | 活跃智能体数 | 今日拦截请求 | 触发策略告警
近三十日请求与拦截趋势 | 安全风险类型分布
```

这是典型的"运维大盘"信息结构。安全平台的首屏应该回答的核心问题是**"当前系统是否安全、是否合规、是否存在待处置风险"**，而不是"系统运行了多少量"。应优先展示：安全态势评分（C1）、风险向量雷达图（C2 的产品化命名）、高风险 Agent 排行、高风险工具排行、影子工具发现、未处置事件数、策略覆盖空缺、监控健康度。

### 3.2 Trace 工作台仍是 APM 式瀑布图

`pages/monitor/trace-list.html:83` 的列表字段包含"总计耗时(毫秒)"，`:143` 的弹窗标题是"调用链瀑布图"，弹窗内有"响应时延(毫秒)"列。

这与 PRD `admin_prd_管理端需求文档.md:1273` 中定义的"Trace 剧本视图：意图产生 → 推理链 → 物理触角"的安全调查视角完全不一致。安全场景需要的不是"哪一步最慢"，而是"哪一步出现了风险、证据是什么、后续影响是什么"。

### 3.3 应用详情页以性能指标为主

`pages/assets/app-detail.html` 的统计卡片展示：近 24h 调用量、Token 消耗、平均延迟、P95/P99。这些是 DevOps 关心的指标，不是安全运营关心的。安全运营关心的主区应该是：安全评分、近 24h 高危 Span 数、风险类型分布、MCP 权限越界情况。

### 3.4 Agent 详情页展示的是服务器信息

`pages/assets/agent-detail.html:17` 页面标题是"生产服务器-01"，展示内容是 IP 地址、操作系统（Linux CentOS 7）、所属部门。这是彻底的"服务器中心"视角——把服务器当主角，把安全风险当服务器属性。Agent 详情页应该展示的是 Agent 的安全画像，不是宿主服务器的运维信息。

### 3.5 应用级阻断缺少保护机制

`pages/assets/app-detail.html:54` 有一个"应用级阻断"按钮，直接点击就可以断掉整个应用所有实例的全部 LLM 调用，没有任何影响范围预估、二次确认或 TTL 限制。生产环境一旦误操作后果严重。

### 3.6 C1～C7 安全概念未落到原型页面

`安全可观测性设计概念规范.md` 中定义的 C1 安全态势评分、C2 风险向量雷达图（原规范命名需产品化调整）、C3 安全证据面板、C5 MCP 权限边界图、C6 工具调用安全矩阵，在现有原型 HTML 页面中均无体现，概念与原型之间存在明显脱节。

### 3.7 `app_id` 与 `Agent` 的主资产定位不统一

部分文档说 `app_id` 是主资产，部分又说 Agent 是核心施动者。建议明确：`app_id` 是接入、计费、租户、策略归属边界（治理对象）；`Agent / Workflow Node` 是安全分析主体；`Span` 是证据主体。

### 3.8 MCP / Skills 仅做成了工具列表

当前设计把 MCP/Tool 当成一个简单的名称列表处理，没有建模为"能力资产"：谁声明了它、谁实际调用了它、能访问什么资源、允许哪些参数范围、是否可写、是否可联网、是否可执行命令、是否出现未声明调用。

## 四、资产管理设计重构

### 4.1 五层资产模型

当前资产管理混淆了"安全主角"和"基础设施背景"，建议按五层重新组织：

| 层级 | 安全语义 | 在平台中的地位 | 设计重点 |
|---|---|---|---|
| **接入应用 `app_id`** | 安全隔离边界、计费单元、责任归属 | 二级资产，管理入口 | Token 管理、策略绑定、采集健康、风险汇总 |
| **智能体 / 工作流节点** | 安全分析主体，有自主行为的 AI 实体 | **一级安全主角** | 行为基线、意图范围、风险评分、关联工具 |
| **MCP / Skill / Tool** | 风险面，能力边界，潜在高风险操作入口 | **一级安全风险面** | 能力分类、权限边界、高危动作、越权证据 |
| **资源** | 数据存储、外部服务，数据泄露的终点 | 重要安全配置对象 | 数据库/文件/API/知识库，标注敏感级别和允许动作 |
| **运行环境** | 失陷时的爆炸半径 | 背景信息，折叠展示 | 服务器/Pod/进程/SDK 版本，不作为一级菜单 |

**关键原则：服务器/Pod 不作为安全运营主导航，只作为应用详情中的"运行实例"、爆炸半径分析和平台运维场景的辅助对象展示。**

### 4.2 Agent 详情页应重构为安全画像

建议 Agent 详情页按以下 Tab 组织，彻底去掉"服务器信息"：

```
Tab 1: 安全态势概览
  ├── 安全评分仪表盘（C1）+ 近30天评分趋势
  ├── 风险向量雷达图（C2，沿用概念规范能力但调整产品命名）
  ├── 本周 TOP3 风险事件摘要
  └── 与同类 Agent 横向对比（P2）

Tab 2: 行为基线与异常
  ├── 常用工具 TOP10 及调用频率分布（正常基线）
  ├── 典型 Session/Trace 步骤数分布
  ├── Token 消耗基线（用于异常检测，非成本分析）
  └── 近30天偏离基线的异常记录

Tab 3: 工具授权审计（MCP 权限边界图 C5）
  ├── 声明工具列表 vs 实际调用工具对比
  ├── 越界工具高亮（未声明但被调用）
  ├── 影子工具发现（从未声明也从未见过）
  └── 工具调用安全矩阵（C6）

Tab 4: 风险事件历史
  └── 与该 Agent 关联的所有历史风险事件列表

Tab 5: 运行配置（降级到这里）
  ├── 接入实例、SDK 版本、心跳状态
  └── 监控配置、采样率、脱敏规则
```

### 4.3 需要独立的"工具与权限图谱"视图

当前设计对 MCP/Tool 的管理分散，缺乏以工具为中心的全局视图。建议新增 `/assets/tools` 菜单：

```
工具与权限图谱 /assets/tools
├── 全局工具列表
│   ├── 工具名称、类型（内置/MCP/自定义）
│   ├── 使用此工具的 Agent 数量
│   ├── 近7天调用次数、越界次数、阻断次数
│   ├── 危险等级（Shell执行=高危，只读查询=低危）
│   └── 来源可信度（官方/社区/自建/未知）
│
├── 工具安全档案（点击进入）
│   ├── 工具说明 + 能力边界（文件读写/网络访问/代码执行/数据库/消息）
│   ├── 调用此工具的 Agent 列表
│   ├── 参数安全分析（哪些字段存在注入风险）
│   └── 历史风险事件（以此工具为载体的安全事件）
│
└── 影子工具管理（重要！）
    ├── 已观测到但未在任何 Agent 声明列表中出现的工具
    ├── 风险等级自动标注
    └── 一键"要求声明 / 加入黑名单"操作
```

落地优先级需要收敛：P0 阶段先做"已观测工具发现 + 工具白黑名单 + 影子工具提示"；P1 再建设完整的工具权限图谱；P2 再扩展到参数级权限、资源级越界和供应链可信度审计。

### 4.4 MCP 与 Skill/Tool 的概念统一

| 概念 | 含义 | 平台内处理方式 |
|---|---|---|
| **MCP（Model Context Protocol）** | 协议层，智能体通过标准协议接入外部服务的方式 | 作为工具的"接入协议"在工具详情中标注 |
| **Tool / Skill / Function** | 能力层，智能体可以调用的具体能力单元 | 平台内**统一用"工具（Tool）"称呼** |
| **Resource** | 工具可访问的底层资源（数据库/文件/API） | 独立建档，标注敏感级别 |

## 五、安全可观测性补充维度

`安全可观测性设计概念规范.md` 的 C1～C7 方向正确，但存在以下三个维度缺口：

### 5.1 缺少"安全盲点"的可观测性

现有设计只关注"发现了什么威胁"，没有回答**"有哪些威胁可能没被发现"**。建议在大盘增加"监控健康度"板块：

```
监控健康度（大盘底部小组件）
┌─────────────────────────────────────────────────────────┐
│ 采集覆盖度                                               │
│   已接入监控: 12/15 Agent  (80%)   ⚠️ 3 个未接入         │
│   调用链完整率: 94.3%  (6 条 Trace 断链)                  │
│                                                         │
│ 检测覆盖度                                               │
│   规则激活率: 18/22 条生效                               │
│   影子工具: 🔴 3 个未声明工具                             │
│   近24h 零触发检测类型: 间接注入（可能采集不到数据）      │
└─────────────────────────────────────────────────────────┘
```

需要展示的覆盖度维度：

- **采集覆盖度**：哪些 Agent 未接入（盲区）、哪些工具调用无 Span 数据（黑盒工具）、哪些 Trace 调用链断裂
- **检测覆盖度**：已启用规则数/总规则数、各检测类型近期触发率（长期零触发可能是采集缺失的信号）
- **声明覆盖度**：未声明工具调用占比（影子工具比例）

### 5.2 缺少"数据流安全"视角

现有设计关注"哪个对象触发了风险"，对**数据泄露路径**（PII 的进/转/出轨迹）的可视化不足。内网客户最核心的合规场景之一，是跟踪敏感数据从哪里进入、经过哪些工具、最终可能从哪里流出：

```
数据流安全事件类型：
├── 输入侧：用户 Prompt 中含 PII（手机号/身份证/邮箱）
├── 传递侧：PII 从 LLM response 被传递给 Tool Input
├── 外传侧：Tool 将含 PII 的数据发送到外部 API（数据出境）
└── 缓存侧：PII 被存在 Session 上下文中，跨会话泄露

Span 详情页建议增加"数据流向"标注：
  [llm_call] 检测到 PII: 手机号 ×1 (已脱敏)
  [tool_call: send_email] 输入参数包含脱敏手机号残留 ⚠️

大盘建议增加：
  今日 PII 事件: 手机号 23次 | 邮箱 17次 | 身份证 5次
```

### 5.3 需要引入标准风险框架映射（可参考 MITRE ATLAS）

参考资料里完全没有 AI 安全专用的威胁框架。建议在安全事件和风险分类中引入 **MITRE ATLAS**（专为 AI/ML 系统设计的对抗性威胁矩阵）：

```
示例映射：
  检测到: Prompt 注入
  → ATLAS 战术: AML.T0051 (LLM Prompt Injection)
  → 风险阶段: Initial Access（初始接触）
  → 可能后续步骤: Execution → Exfiltration

  检测到: 工具越权调用 Shell
  → ATLAS 技术编号: 待规则库初始化时统一校验
  → 风险阶段: Execution（执行）
  → 可能后续步骤: Persistence → Impact
```

引入 MITRE ATLAS 的作用：
1. 帮助 SOC 快速理解风险意图和潜在后续步骤，不只是看到"高危"标签
2. 为告警提供标准化分类（"初始接触阶段的注入风险"比"Prompt 注入高危"信息量更大）
3. 支持与企业现有 SIEM/SOC 体系对接
4. 在安全报告中体现专业深度

注意：ATLAS 技术编号不要在产品设计稿中随意写死，需在规则库初始化阶段统一校验。内网客户界面可展示为"标准风险阶段 / 标准风险编号"，在高级详情或 SIEM 对接字段中保留 ATLAS 原始编号。

## 六、数据模型改进建议

### 6.1 `risk_events` 表字段补充

当前表（见 `admin_tech_detailed_design.md:85`）有 `span_id/risk_type/confidence/evidence`，但缺少支撑调查闭环的关键字段：

| 建议新增字段 | 类型 | 用途 |
|---|---|---|
| `detector_id` | VARCHAR | 是哪个检测器触发的（NeMo/LlamaFirewall/自研规则引擎） |
| `rule_version` | INTEGER | 命中的规则版本号，支持误报回溯和规则变更追踪 |
| `risk_stage` | VARCHAR | 风险阶段（initial_access/execution/exfiltration），可映射 ATLAS |
| `source_field` | VARCHAR | 哪个字段触发了检测（prompt/response/tool_input/tool_output） |
| `evidence_offset` | JSONB | 命中片段在原文的起止偏移（用于 UI 精确高亮） |
| `redaction_state` | VARCHAR | 证据脱敏状态（none/partial/full），影响 SOC 查看策略 |
| `subject_type` | VARCHAR | 风险主体类型：app / agent / tool / resource / session |
| `subject_id` | UUID / VARCHAR | 风险主体 ID，与 `subject_type` 配合使用 |
| `tool_id` | UUID / VARCHAR | 关联工具 ID，可空 |
| `resource_id` | UUID / VARCHAR | 关联资源 ID，可空 |
| `false_positive_reason` | TEXT | 标误报时填写，反馈给规则优化流程 |
| `atlas_technique_id` | VARCHAR | MITRE ATLAS 技术编号，需由规则库统一校验后写入 |

### 6.2 `agent_spans` 表的安全维度补充

当前字段（见 `admin_tech_detailed_design.md:155`）已有 prompt、response、tool、risk、status，建议**在服务端 Processor/检测引擎阶段动态关联**（不在 SDK 端填写，避免耦合）以下安全维度：

- `tool_risk_level`：工具危险等级（从工具资产档案查表关联）
- `tool_declared`：工具是否已声明（从应用工具声明列表核查）
- `resource_sensitivity`：访问资源的敏感级别
- `pii_types`：检测到的 PII 类型列表
- `pii_action`：PII 处置动作（masked/blocked/allowed）
- `data_classification`：数据分类标签（内部/保密/公开）

**注意**：这些字段由服务端动态写入，好处是工具危险等级、资源敏感度等配置变更后无需推 SDK 新版本，只需更新服务端配置表即可立即生效。

### 6.3 安全 Span 属性规范（OTel 扩展字段）

在 OTel 标准属性之上，统一定义平台安全语义属性。字段来源建议分层，避免 SDK 端负担过重：

| 层级 | 字段来源 | 典型字段 |
|---|---|---|
| SDK 原始字段 | 客户端自动插桩上报 | `trace_id`、`span_id`、`parent_span_id`、Prompt、Tool Input、Tool Output、status |
| Collector 增强字段 | 服务端接收与处理链 | tenant、app、instance、采样状态、脱敏状态、路由标签 |
| 检测引擎字段 | Prompt / Tool / 数据流检测 | risk_type、confidence、evidence、risk_stage、atlas_technique_id |
| 查询层派生字段 | 资产与策略关联 | 工具危险等级、资源敏感度、策略覆盖状态 |

```
检测结果属性（检测引擎或服务端增强后写入，不要求 SDK 原始上报全量具备）
  security.risk.level        none | low | medium | high | critical
  security.risk.type         prompt_injection | tool_abuse | pii_leak | ...
  security.confidence        0.0 ~ 1.0
  security.action            none | monitor | alert | block
  security.block.reason      阻断原因说明（block 时必填）

意图对齐属性（多轮 Session 有）
  security.intent.alignment_score   0.0 ~ 1.0
  security.intent.deviation_reason  偏离原因说明

工具权限属性（Tool Span 有）
  security.tool.declared      true | false（是否在声明列表中）
  security.tool.permission    allowed | unlisted | blacklisted
  security.tool.risk_level    工具本身的危险等级（与工具资产档案关联）

数据流属性（含 PII 时有）
  security.pii.detected       true | false
  security.pii.types          [phone, email, id_card, credential, ...]
  security.pii.action         masked | blocked | allowed
```

### 6.4 标准化 8 类安全风险分类

建议先固定 8 类风险类型，作为检测规则、告警规则、事件分类、统计报告的统一口径，避免各处 magic string 不一致：

| 编号 | 风险类型 | 英文标识 | 典型场景 |
|---|---|---|---|
| R1 | Prompt 注入 | `prompt_injection` | 用户输入中嵌入越权指令 |
| R2 | 越狱 | `jailbreak` | 绕过 LLM 安全限制的 Prompt 模式 |
| R3 | 间接注入 / RAG 投毒 | `indirect_injection` | 外部文档/网页中隐藏的注入指令 |
| R4 | 工具越权 | `tool_abuse` | 调用黑名单工具或未声明工具 |
| R5 | 数据泄露 / 外传 | `data_exfiltration` | PII 或机密数据通过工具流出 |
| R6 | 凭证泄露 | `credential_leak` | Prompt 或 Response 中含密钥/密码 |
| R7 | 行为异常 / 成本滥用 | `behavior_anomaly` | 偏离历史基线的异常调用序列 |
| R8 | 策略绕过 | `policy_bypass` | 绕过 Guardrail 规则的输入输出 |

## 七、安全可观测性主链路

建议将平台的核心数据流固定为以下线性主链路，所有设计决策以此为依据：

```
Raw Span（客户端 SDK 上报）
  ↓
归一化 Span（OTel Collector Processor：脱敏 / 打标 / 路由）
  ↓
安全检测结果（检测引擎输出：risk_type / confidence / evidence）
  ↓
Risk Event（风险事件入库：关联 subject / risk_stage / 标准风险映射）
  ↓
Alert / Incident（告警规则匹配：通知 / 工单 / 阻断指令）
  ↓
Evidence Panel（安全证据面板：SOC 调查 C3 视图）
  ↓
Trace / Asset / Policy 回溯（还原风险路径 / 关联受影响资产 / 定位策略缺口）
```

**所有页面都应围绕这条主链路设计交互路径：发现风险 → 定位证据 → 还原路径 → 判断影响 → 处置响应。**

## 八、`session_id` 的 MVP 边界

**`session_id` 不应成为 MVP 依赖。**

`phase-03-3.2-LangChain-SDK当前遥测能力说明.md:117` 明确记录：当前 SDK 稳定具备 `trace_id / span_id / parent_span_id`，`session_id` 是可选上报字段，不保证每次都有。

因此：
- **MVP 阶段**：工作台默认以 `trace_id` 为粒度展示，Trace 列表 + Trace 剧本视图是主视图。
- **Session 视图**：仅在 `session_id` 可靠存在时启用（作为可选增强视图）。
- **不建议做**：因为没有 `session_id` 就让整个"多轮分析"功能空白或报错。

## 九、阻断能力分级设计

`app-detail.html:54` 的"应用级阻断"按钮没有任何保护机制，生产环境误操作风险极高。建议拆分为四个粒度，并分别配套保护措施：

| 阻断粒度 | 影响范围 | 触发条件 | 保护措施 |
|---|---|---|---|
| **Session 阻断** | 仅一次会话 | 自动规则触发 / SOC 手动 | 无需额外确认，自动 TTL 1h |
| **Tool 阻断** | 禁用某个工具的调用 | SOC 手动 / 黑名单命中 | 确认框 + 影响 Agent 数预估 |
| **Agent 阻断** | 一个智能体实例 | SOC 手动 | 确认框 + TTL 必填 |
| **应用熔断** | 整个应用所有实例 | 仅 SecAdmin 可操作 | 二次确认或 MFA、影响评估、TTL、审批流、支持一键回滚 |

## 十一、事件处置中心增强

每个风险事件的详情页必须支持一键跳转和完整证据展示：

```
一键跳转：
  · span_id  → 安全证据面板（C3）
  · trace_id → Trace 剧本视图（还原完整风险链路）

  · 命中字段（source_field: prompt / tool_input）
```

## 十五、关键设计原则

1. **安全优先排序**：安全调查类列表默认按风险等级排序，不按时间或耗时排序；审计日志、告警记录、报告列表仍可按时间排序。

2. **证据驱动**：每一个安全结论（风险判定）背后必须有可追溯的证据（命中字段、原始片段、规则版本）。

3. **下钻闭环**：大盘的每一个指标都必须能一键下钻到对应的 Trace/Span 证据，不允许出现"信息孤岛"。

4. **基础设施降级**：服务器、Pod、延迟、Token 消耗都可以存在，但只能服务于安全判断，不能成为平台主叙事。

5. **MVP 不依赖 session_id**：以 `trace_id` 为默认调查单元，`session_id` 仅作可选增强，不得作为 MVP 必要依赖。

6. **阻断必须分级**：应用级熔断必须有二次确认或 MFA、TTL、审批和回滚能力，不能是一个普通按钮。

7. **检测结果可解释**：SOC 工程师看到的每个风险事件都必须能回答"为什么判定为风险"（命中规则 + 原始片段 + 标准风险阶段），不能只有风险等级标签。

8. **安全维度服务端关联**：工具危险等级、资源敏感级别等分类数据不在 SDK 端维护，由服务端 Processor 阶段动态关联，支持热更新。
