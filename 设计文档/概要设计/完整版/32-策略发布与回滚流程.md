# 策略发布与回滚流程设计

## 1. 文档目标

本文档定义统一策略中心中策略、规则项、策略包的发布、灰度、下发、验证和回滚流程。

---

## 2. 流程目标

1. 保证策略变更有版本。
2. 保证生产变更可灰度。
3. 保证下发过程可追踪。
4. 保证异常情况下可回滚。

---

## 3. 主流程

```text
创建 / 编辑策略
→ 保存新版本 policy_version
→ 测试 / 校验
→ 审批
→ gray 灰度发布
→ 创建 deployment
→ 下发到目标实例
→ runtime_effect 生效验证
→ 正式启用
```

---

## 4. 流程步骤设计

## 4.1 创建 / 编辑

适用对象：

1. 规则项 `rule`
2. 策略 `policy`
3. 策略包 `policy_package`

要求：

1. 所有编辑都生成新版本。
2. 必须填写变更说明。
3. 已发布版本不可直接覆盖。
4. 版本号建议使用 `major.minor.patch`。

## 4.2 测试 / 校验

测试内容建议包括：

1. 条件表达式合法性
2. 动作配置合法性
3. 绑定目标合法性
4. 样本验证 / 干跑

干跑要求：

1. 干跑不得影响线上生效版本。
2. 干跑结果应记录样本范围、命中数、误报样本和执行人。
3. 命中样本应能跳转到风险溯源工作台。

## 4.3 审批

以下情况建议审批：

1. 高危策略启用
2. 生产环境发布
3. 大范围灰度切换
4. 高危回滚

审批通过后，策略或策略包才允许进入灰度或正式下发。审批拒绝时，业务对象保持原状态。

## 4.4 灰度发布

灰度维度建议支持：

1. 按应用
2. 按环境
3. 按实例
4. 按比例

灰度阶段应监控：

1. 下发成功率
2. 错误率
3. 误报率变化
4. 风险拦截效果

灰度状态要求：

1. 策略或策略包状态进入 `gray`。
2. 绑定关系记录灰度比例和目标范围。
3. 下发任务进入 `pending_dispatch` 或 `dispatching`。

## 4.5 全量下发

灰度验证通过后，进入全量下发。

应记录：

1. `deployment_id`
2. 目标对象数
3. 同步成功数
4. 同步失败数
5. 失败原因
6. 期望版本
7. 当前版本

## 4.6 生效验证

验证内容：

1. 是否全部同步
2. 是否产生异常告警
3. 是否影响核心链路
4. 运行实例是否达到期望版本
5. 是否存在 `partially_synced` 或 `failed` 实例

验证结果：

1. 全部正常后，策略进入 `enabled`。
2. 部分失败时，下发状态为 `partially_synced`。
3. 全部失败或关键实例失败时，下发状态为 `failed`。

---

## 5. 回滚流程

```text
发现异常
→ 发起回滚申请
→ 审批
→ 执行回滚
→ 创建回滚 deployment
→ 下发目标版本
→ 验证恢复效果
→ 记录回滚审计
```

## 5.1 回滚触发条件

1. 误拦截明显升高
2. 服务异常
3. 下发错误
4. 配置不兼容

## 5.2 回滚要求

1. 回滚必须指向明确版本。
2. 回滚必须保留审批单号。
3. 回滚后必须重新验证同步状态。
4. 回滚不删除失败版本。
5. 回滚成功后使用 `rolled_back` 表示已回滚。
6. 回滚失败必须保留失败原因和重试入口。

---

## 6. 下发状态管理

下发过程建议统一以下状态：

1. `not_dispatched`
2. `pending_dispatch`
3. `dispatching`
4. `partially_synced`
5. `synced`
6. `failed`
7. `rollbacking`
8. `rolled_back`

聚合状态要求：

1. 任一目标实例失败且存在成功实例时，整体状态为 `partially_synced`。
2. 全部目标实例成功时，整体状态为 `synced`。
3. 关键目标实例失败时，可根据策略标记为 `failed`。
4. 实例级结果必须写入 `runtime_effect`。

## 7. 关键对象与字段

策略发布与回滚流程至少涉及以下对象：

1. `rule`
2. `policy`
3. `policy_package`
4. `policy_version`
5. `policy_binding`
6. `deployment`
7. `runtime_effect`
8. `approval_order`
9. `status_change_log`

关键字段：

1. `rule_id`
2. `policy_id`
3. `package_id`
4. `version_id`
5. `version_no`
6. `binding_id`
7. `deployment_id`
8. `effect_id`
9. `policy_status`
10. `package_status`
11. `dispatch_status`
12. `expected_version`
13. `current_version`
14. `approval_id`

## 8. 关键接口引用

1. `POST /rules/{ruleId}/dry-run`
2. `GET /rules/{ruleId}/hit-samples`
3. `POST /policies/{policyId}/publish`
4. `POST /policies/{policyId}/rollback`
5. `GET /policies/{policyId}/versions`
6. `POST /policy-packages/{packageId}/publish`
7. `POST /policy-packages/{packageId}/rollback`
8. `POST /policy-bindings/{bindingId}/deploy`
9. `GET /deployments`
10. `GET /deployments/{deploymentId}`
11. `GET /deployments/{deploymentId}/runtime-effects`
12. `POST /deployments/{deploymentId}/rollback`

---

## 9. 与其他模块关系

1. 风险事件会触发策略优化需求。
2. 资产中心展示应用绑定和同步结果。
3. 系统管理审计全部发布与回滚操作。
4. 安全监控中的规则解释依赖规则版本。
5. 总览展示下发失败待办和策略覆盖缺口。
