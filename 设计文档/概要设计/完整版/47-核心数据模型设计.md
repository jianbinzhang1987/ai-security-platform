# 核心数据模型设计

## 1. 文档目标

本文档用于定义大模型安全监测平台的核心数据模型范围、实体对象、关系模型和建模要求，为后续数据库设计、接口设计、状态机设计和检索设计提供统一基础。

本文档当前输出的是概要级数据模型，不替代后续详细表结构设计。

---

## 2. 设计原则

1. 围绕正式业务对象建模，而不是围绕页面建模。
2. 核心对象必须支持全生命周期和审计留痕。
3. 业务状态与审批状态分离建模。
4. 事件对象与证据对象分离建模。
5. 策略对象、绑定对象、下发对象分离建模。
6. 需要支持跨对象检索和下钻。

---

## 3.1 核心字段类型约定

1. 主键字段统一使用字符串 ID，便于跨系统引用和日志追踪。
2. 时间字段统一包含创建时间、更新时间；事件类对象额外保留首次发生时间和最近发生时间。
3. 状态字段必须引用 [13-全局状态模型.md](</E:/code/大模型安全监测平台/设计文档/概要设计/完整版/13-全局状态模型.md>)。
4. Raw 证据不直接进入事件、审计、通知正文，只保存引用和访问记录。
5. 涉及密钥、Webhook、SMTP 密码等敏感配置时，只保存密钥引用，不保存明文。

## 5. 核心关系模型

## 5.1 主关系链

```text
App
├── Instance
├── Agent / Node
├── Tool / Resource
├── Session
│   └── Trace
│       └── Span / Observation
├── Risk Event
│   ├── Event Evidence
│   └── Event Action
└── Policy Binding
    ├── Policy
    └── Policy Package
        └── Rule
```

## 5.2 关键关系说明

1. 一个应用可对应多个实例。
2. 一个应用可对应多个 Agent / 节点。
3. 一个会话可对应多个 Trace。
4. 一个 Trace 对应多个 Span。
5. 一个事件至少关联一个 Trace 和一个 Span。
6. 一个事件可通过 `event_evidence_rel` 关联多个 Span 证据。
7. 一个事件可对应多个处置动作。
8. 一个审批单可关联一个事件、一个动作、一个策略发布或一个回滚任务。
9. 一个策略包可绑定多个应用。
10. 一次下发任务可对应多个运行实例的生效结果。

## 5.3 事件证据关系

```text
Risk Clue
→ Span / Observation
→ Event Evidence Relation
→ Risk Event
→ Event Action
```

建模要求：

1. 风险线索用于记录事件前的识别结果。
2. 正式事件通过关系表引用证据，不复制 Raw Payload。
3. 事件主表只保存主证据锚点，便于列表检索和跳转。
4. 事件详情读取关系表展示完整证据链。

## 5.4 策略发布关系

```text
Rule
→ Policy / Policy Package
→ Policy Version
→ Binding
→ Deployment
→ Runtime Effect
```

建模要求：

1. 已发布版本必须不可变。
2. 绑定关系必须记录绑定版本。
3. 下发任务记录一次同步过程。
4. 生效实例记录每个目标的实际版本。
5. 回滚通过新的下发任务表达，不删除历史版本。
