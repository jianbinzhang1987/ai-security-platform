# 风险事件模块概要设计

## 1. 文档目标

本文档定义大模型安全监测平台“风险事件”模块的业务定位、功能范围、页面设计、对象关系、核心流程和关键设计要求。

风险事件模块是平台的正式闭环中心，负责把风险线索转化为可追踪、可指派、可处置、可审计的正式安全事件。

---

## 2. 模块定位

### 2.1 业务定位

风险事件模块负责承接来自风险溯源工作台、会话审计、策略命中、自动检测等来源的风险线索，并通过统一的事件主档和动作记录，完成事件全生命周期管理。

### 2.2 核心职责

1. 接收风险线索并形成正式事件。
2. 聚合证据锚点与上下文信息。
3. 支持事件指派、确认、误报、接受风险、关闭。
4. 记录处置动作、审批信息、TTL 和回滚状态。
5. 为总览、资产中心、策略中心提供闭环状态反馈。

### 2.3 模块边界

风险事件模块负责：

1. 事件主档管理。
2. 事件状态流转。
3. 负责人和协同处理。
4. 处置记录审计。

风险事件模块不直接负责：

1. 底层证据采集。
2. 调用链细节还原。
3. 策略规则本体配置。
4. 外部通知系统本体实现。

---

## 3. 页面范围

当前风险事件模块包含两个正式页面：

1. 风险事件
2. 告警与响应记录

建议后续保留一个事件详情页作为二级详情承载页。

## 4. 核心对象

## 4.1 风险事件 `event`

风险事件是平台正式的安全闭环对象。

### 核心属性

1. `event_id`
2. 事件标题
3. 风险等级
4. 风险类型
5. 风险摘要
6. 关联应用
7. 关联 Agent / 节点
8. 关联工具 / 资源
9. `trace_id`
10. `span_id`
11. 状态
12. 负责人
13. 来源渠道
14. 首次发生时间
15. 最近发生时间
16. 处置结论
17. 误报标记
18. 风险接受标记

### 状态字段

风险事件统一使用 `event_status` 字段，枚举必须引用 `13-全局状态模型.md`：

1. `new`
2. `confirmed`
3. `in_progress`
4. `resolved`
5. `false_positive`
6. `accepted_risk`
7. `closed`

事件状态不得与风险等级、审批状态、处置动作状态混用。

## 4.2 处置动作 `action`

处置动作是事件执行过程中的操作留痕对象。

### 核心属性

1. `action_id`
2. `event_id`
3. 动作类型
4. 动作范围
5. 动作目标
6. TTL
7. 操作人
8. 审批单号
9. 执行状态
10. 回滚状态
11. 执行结果
12. 操作备注

### 状态字段

处置动作统一使用：

1. `action_status`
   - 表示动作执行状态，例如 `pending`、`executing`、`effective`、`failed`、`expired`。
2. `rollback_status`
   - 表示动作回滚状态，例如未回滚、待回滚、已回滚。

当动作类型不支持回滚时，`rollback_status` 可为空，但页面应展示“不支持回滚”而不是展示失败。

## 4.3 审批单 `approval`

审批单是高危操作和风险接受的审批承载对象。

### 核心属性

1. `approval_id`
2. 审批类型
3. 关联事件 / 动作
4. 发起人
5. 审批人
6. 审批状态
7. 审批意见
8. 生效时间

### 审批类型

风险事件模块至少涉及以下审批类型：

1. 风险接受审批
2. 高危处置审批
3. 处置回滚审批
4. 生产策略联动审批

审批状态统一引用 `13-全局状态模型.md` 中的审批单状态，不在本模块另建状态口径。

## 5. 风险事件页面设计

## 5.1 页面目标

以事件为主档，统一查看风险、证据摘要、负责人、状态和处置入口，支撑事件分诊、协同和闭环。

## 5.2 页面结构

建议页面结构如下：

1. 页面头部
2. 统计卡区
3. 查询筛选区
4. 事件列表区
5. 批量操作区
6. 事件详情弹窗 / 抽屉 / 二级页

## 5.3 统计卡设计

建议保留以下指标：

1. 待确认事件数
2. 已确认 / 处理中事件数
3. 待关闭事件数
4. 误报样本数
5. 接受风险事件数

## 5.4 查询条件设计

建议支持以下筛选项：

1. 时间范围
2. 事件状态
3. 风险等级
4. 风险类型
5. 接入应用
6. 负责人
7. Agent / 节点
8. 工具 / 资源
9. `trace_id`
10. `span_id`
11. `event_id`

## 5.5 列表字段设计

建议列表字段如下：

1. 事件编号
2. 发生时间
3. 关联对象
4. 风险等级
5. 风险类型
6. 证据要点
7. 状态
8. 负责人
9. 最近处置动作
10. 操作

## 5.6 列表操作设计

单条事件支持：

1. 指派
2. 确认风险
3. 处置登记
4. 标记误报
5. 接受风险
6. 查看详情
7. 跳转会话审计
8. 跳转风险溯源

### 操作与状态迁移关系

| 操作 | 允许的前置状态 | 目标状态 | 是否需要原因 | 是否需要审批 |
|---|---|---|---|---|
| 指派 | `new`、`confirmed` | `in_progress` | 否 | 否 |
| 确认风险 | `new` | `confirmed` | 建议填写 | 否 |
| 标记误报 | `new`、`confirmed`、`in_progress` | `false_positive` | 是 | 否 |
| 接受风险 | `confirmed`、`in_progress` | `accepted_risk` | 是 | 是 |
| 处置完成 | `in_progress` | `resolved` | 是 | 视动作类型 |
| 关闭事件 | `resolved`、`false_positive`、`accepted_risk` | `closed` | 是 | 否 |
| 重新打开 | `closed` | 新事件或派生事件 | 是 | 视等级 |

关闭后的事件原则上不直接回到处理中；如需继续调查，应创建派生事件或重新生成事件线索。

批量事件支持：

1. 批量指派
2. 批量确认
3. 批量标记误报
4. 批量关闭

## 6. 事件详情设计

## 6.1 页面目标

以单个事件为中心，整合事件信息、证据摘要、调查结果、处置记录、审批记录和审计日志。

## 6.2 建议区域

1. 事件头部摘要
2. 风险说明区
3. 证据摘要区
4. 关联 Trace / Span 区
5. 会话上下文区
6. 处置记录区
7. 审批记录区
8. 操作日志区

## 6.3 详情页核心功能

1. 查看事件基础属性
2. 查看风险证据摘要
3. 跳转到原始 Trace / Span
4. 查看会话审计上下文
5. 提交事件处置结论
6. 查看和发起处置动作
7. 查看审批记录
8. 查看回滚状态

## 6.4 事件详情字段分区

事件详情建议按以下分区组织字段：

1. 事件摘要
   - `event_id`
   - 标题
   - 风险等级
   - 风险类型
   - 当前状态
   - 负责人
2. 关联对象
   - 应用
   - Agent / 节点
   - 工具 / 资源
   - 会话
3. 证据锚点
   - `trace_id`
   - `span_id`
   - 风险阶段
   - 证据来源字段
   - 命中规则版本
4. 调查结论
   - 调查人
   - 调查时间
   - 结论类型
   - 结论说明
5. 处置与审批
   - 处置动作
   - TTL
   - 审批单号
   - 回滚状态
   - 复核结果

## 8. 核心流程设计

## 8.1 风险线索转事件流程

```text
规则命中 / 调查发现风险
→ 生成风险线索
→ 人工确认是否转事件
→ 创建正式事件
→ 关联 trace_id / span_id
→ 进入待确认或待指派状态
```

### 关键要求

1. 一个事件可关联多个风险线索。
2. 一个风险线索至少要能关联到一个 `trace_id` 和一个 `span_id`。
3. 创建事件时必须记录来源和证据锚点。

## 8.2 事件分派流程

```text
新事件
→ 指派负责人
→ 负责人接单
→ 进入处理中
```

### 关键要求

1. 未分派事件应在总览与待办中高亮。
2. 分派操作必须记录操作人和时间。
3. 指派时应支持选择负责人、协作人和处理截止时间。

## 8.3 事件确认流程

```text
待确认事件
→ 查看证据和上下文
→ 确认真实风险
→ 状态变更为已确认
→ 发起处置动作
```

## 8.4 误报处理流程

```text
待确认 / 处理中事件
→ 判定为误报
→ 填写误报原因
→ 状态变更为误报
→ 可转入规则优化池
→ 最终关闭
```

### 关键要求

1. 误报必须填写原因。
2. 误报应支持沉淀到规则优化样本池。

## 8.5 接受风险流程

```text
已确认 / 处理中事件
→ 发起接受风险申请
→ 进入审批流
→ 审批通过
→ 状态变更为接受风险
→ 关闭归档
```

### 关键要求

1. 接受风险必须走审批。
2. 接受风险必须留痕并支持后续复核。

## 8.6 处置与关闭流程

```text
处理中事件
→ 执行限制 / 降级 / 通知 / 恢复等动作
→ 风险得到控制
→ 状态变更为已处置
→ 复核通过
→ 关闭归档
```

### 关键要求

1. 处置动作必须先形成 `action` 记录，再驱动事件状态变化。
2. 高危处置动作审批通过前，事件不得直接进入 `resolved`。
3. TTL 到期后如动作自动失效，应在事件详情中展示失效记录。
4. 关闭事件前必须至少存在调查结论或处置结论。

## 8.7 处置动作创建流程

```text
事件处理中
→ 选择动作类型
→ 选择动作范围和目标
→ 设置 TTL
→ 填写影响说明
→ 判断是否需要审批
→ 创建 action
→ 执行或等待审批
```

### 动作表单字段

1. 动作类型
2. 动作范围
3. 动作目标
4. TTL
5. 期望生效时间
6. 影响说明
7. 回滚方案
8. 审批备注
9. 通知渠道
10. 操作备注

## 8.8 回滚流程

```text
已生效动作
→ 发起回滚申请
→ 审批通过
→ 执行回滚
→ 更新 action 回滚状态
→ 记录回滚结果
```

### 关键要求

1. 只有支持回滚的动作才展示回滚入口。
2. 回滚不得删除原处置动作记录。
3. 回滚后事件是否重新进入处理中，应由复核结果决定。
4. 回滚失败必须保留失败原因和重试入口。

## 9. 关键交互要求

1. 事件列表点击“溯源”必须准确跳转到对应 `trace_id` 和 `span_id`。
2. 事件列表点击“会话审计”必须带入 `session_id` 或上下文参数。
3. 事件详情必须能看见核心证据摘要，而不是只看编号。
4. 处置动作不能只用 toast，应有正式表单承载：
   - 动作类型
   - 动作范围
   - TTL
   - 审批备注
   - 影响说明
5. 所有关键操作必须有确认和审计记录。

## 10. 与其他模块的关系

### 10.1 与安全监控

1. 风险事件消费安全监控输出的调查结论和证据锚点。
2. 事件详情支持回跳风险溯源工作台。

### 10.2 与会话审计

1. 事件查看上下文时依赖会话审计提供会话原文和网关动作。
2. 会话审计不承担事件闭环，只提供辅助上下文。

### 10.3 与统一策略中心

1. 事件处置动作会触发或引用策略能力。
2. 误报、接受风险和处置结果会反馈策略优化。

### 10.4 与安全总览

1. 事件状态变化会更新总览待办和统计卡。

## 11. 数据与审计要求

## 11.1 必填数据要求

事件创建时至少必须具备：

1. `event_id`
2. 风险等级
3. 风险类型
4. 关联应用
5. `trace_id`
6. `span_id`
7. 风险摘要
8. 来源渠道
9. 创建时间

动作创建时至少必须具备：

1. `action_id`
2. `event_id`
3. 动作类型
4. 动作范围
5. 操作人
6. 创建时间

处置动作如涉及审批，还必须具备：

1. 审批类型
2. 审批人或审批角色
3. 审批原因
4. 影响范围
5. 回滚方案

## 11.2 审计要求

以下动作必须写入操作审计：

1. 创建事件
2. 指派事件
3. 确认风险
4. 标记误报
5. 接受风险
6. 创建处置动作
7. 回滚处置动作
8. 关闭事件

状态变更审计至少记录：

1. 原状态
2. 新状态
3. 操作人
4. 操作时间
5. 变更原因
6. 审批单号
7. 关联 `trace_id / span_id`
