# 统一策略中心概要设计

## 1. 文档目标

本文档定义平台“统一策略中心”的业务定位、能力边界、模块结构、核心对象和设计要求。

当前原型中的策略中心已形成“网关策略管理 + 探针策略管理 + 通知渠道管理”的真实导航，因此本设计以该结构为正式业务口径。

---

## 2. 模块定位

### 2.1 业务定位

统一策略中心是平台的治理能力中心，负责对网关侧安全行为和探针侧运行行为进行规则约束、策略发布、灰度下发、版本管理、回滚和通知联动。

### 2.2 核心职责

1. 配置网关侧访问、流量、内容、会话安全策略。
2. 配置探针侧策略包和高级规则项。
3. 管理绑定、下发、灰度和回滚。
4. 管理通知渠道和联动能力。
5. 将风险处置结果回流到策略优化过程。

### 2.3 模块边界

统一策略中心负责：

1. 策略和规则治理。
2. 版本管理。
3. 策略发布链路。
4. 通知联动配置。

统一策略中心不直接负责：

1. 风险证据采集。
2. 正式事件闭环。
3. 用户与权限管理。

## 4. 核心对象

### 4.0 策略对象层级

统一策略中心采用以下对象层级：

```text
rule 规则项
→ policy 策略
→ package 策略包
→ binding 绑定关系
→ deployment 下发任务
→ runtime_effect 生效实例
```

含义如下：

1. `rule`
   - 最小检测、匹配或治理能力单元。
2. `policy`
   - 可独立启停、测试、发布和审计的业务策略。
3. `package`
   - 面向探针侧或场景化治理的组合发布单元。
4. `binding`
   - 策略或策略包与应用、路由、环境、实例的目标映射。
5. `deployment`
   - 一次具体下发、灰度、回滚或同步任务。
6. `runtime_effect`
   - 目标网关、探针或实例上的最终生效状态。

检测规则不再作为孤立菜单口径存在，应归入 `rule` 或被具体策略引用。业务风险告警规则应作为策略联动能力，与通知渠道和事件创建规则关联。

## 4.1 策略 `policy`

适用于网关侧单条策略或可单独管理的治理对象。

### 关键属性

1. `policy_id`
2. 策略名称
3. 策略类型
4. 条件定义
5. 动作定义
6. 适用范围
7. 状态
8. 当前版本

### 状态字段

策略统一使用 `policy_status`，状态枚举引用 `13-全局状态模型.md`：

1. `draft`
2. `testing`
3. `gray`
4. `enabled`
5. `disabled`
6. `archived`

## 4.2 规则项 `rule`

用于描述细粒度检测或治理能力。

### 关键属性

1. `rule_id`
2. 规则名称
3. 规则类型
4. 风险类型
5. 条件表达式
6. 风险等级
7. 默认动作
8. 状态

### 规则能力要求

规则项至少应支持：

1. 启用 / 停用
2. 版本号
3. 风险类型
4. 风险等级
5. 置信度阈值
6. 适用数据域
7. 干跑验证
8. 命中样本预览
9. 误报样本回流
10. 最近 7 / 30 天命中统计

## 4.3 策略包 `package`

探针侧的组合治理对象。

### 关键属性

1. `package_id`
2. 包名称
3. 模板来源
4. 规则集合
5. 绑定范围
6. 当前版本
7. 发布状态
8. 下发状态

### 状态字段

策略包统一使用：

1. `package_status`
   - 表示策略包生命周期，如草稿、就绪、灰度、启用、停用、已回滚、归档。
2. `dispatch_status`
   - 表示策略包在目标应用或实例上的下发同步状态。

## 4.4 绑定关系 `binding`

描述策略或策略包与目标对象的关联。

### 关键属性

1. `binding_id`
2. 绑定对象类型
3. 绑定对象 ID
4. 绑定策略 / 包 ID
5. 环境范围
6. 灰度比例
7. 生效状态

### 绑定目标

绑定关系至少支持以下目标：

1. 应用
2. 环境
3. 网关路由
4. Agent / 节点
5. 工具 / MCP
6. 探针实例
7. 应用实例

绑定必须记录版本和生效范围，避免策略变更后无法判断目标实例实际运行的是哪个版本。

## 4.5 下发任务 `deployment`

下发任务用于记录一次策略或策略包同步到目标运行组件的过程。

### 关键属性

1. `deployment_id`
2. 目标类型
3. 目标 ID
4. 策略 / 策略包 ID
5. 期望版本
6. 当前版本
7. 下发状态
8. 失败原因
9. 发起人
10. 发起时间
11. 完成时间
12. 回滚目标版本

## 4.6 通知渠道 `channel`

用于接收安全事件、审批和运维通知。

### 关键属性

1. `channel_id`
2. 渠道名称
3. 渠道类型
4. 通知范围
5. 目标地址
6. 状态
7. 最近测试结果

## 5. 网关策略管理设计

## 5.1 访问控制策略

### 业务目标

控制请求主体、请求来源、访问路由和调用资格。

### 核心能力

1. 基于用户 / 应用 / API Key 的访问控制
2. 基于环境 / 来源 / 时间窗口的限制
3. 拒绝、放行、审批放行等动作

## 5.2 流量与服务治理

### 业务目标

保护模型服务和后端服务的稳定性，防止过载与异常扩散。

### 核心能力

1. 限流
2. 配额控制
3. 熔断
4. 降级
5. 恢复策略

## 5.3 提示词防护策略

### 业务目标

识别注入、越狱、提示词泄露等风险 Prompt。

### 核心能力

1. Prompt 风险识别
2. 风险分级
3. 拦截 / 放行 / 告警
4. 规则版本和灰度控制

## 5.4 输入安全策略

### 核心能力

1. 敏感输入识别
2. 非法内容识别
3. 输入脱敏或改写
4. 输入阻断

## 5.5 输出安全策略

### 核心能力

1. 敏感输出识别
2. 合规风险识别
3. 输出脱敏
4. 输出阻断与告警

## 5.6 会话安全策略

### 核心能力

1. 多轮上下文风险累积
2. 意图偏移识别
3. 会话级限流或限制
4. 会话级处置建议

## 5.7 会话审计

### 业务定位

会话审计用于查看用户会话、Prompt 信息、命中策略和网关动作，是事件调查的补充上下文页。

### 核心能力

1. 按会话、用户、应用查询
2. 查看 Prompt 信息
3. 查看命中策略
4. 查看网关动作
5. 关联风险事件

## 5.8 网关绑定与下发

### 核心能力

1. 绑定策略到应用 / 路由 / 环境
2. 设置灰度范围
3. 查看下发状态
4. 查看版本历史
5. 发起回滚

## 6. 探针策略管理设计

## 6.1 策略包管理

### 业务目标

通过面向场景的策略包，把探针侧高危工具限制、运行控制、采集治理和审计能力组合成可发布、可下发、可回滚的治理单元。

### 核心能力

1. 策略包列表管理
2. 向导式新建策略包
3. 模板化生成内容
4. 版本管理
5. 绑定范围管理
6. 下发状态查看
7. 回滚

### 向导建议步骤

1. 选择场景模板
2. 选择策略强度
3. 设置通知与审批
4. 预览生成内容
5. 高级配置

## 6.2 高级规则项

### 业务目标

承载探针侧细粒度控制能力，面向专家用户提供深度配置能力。

### 核心能力

1. 工具边界规则
2. 采集控制规则
3. 审计控制规则
4. 运行熔断规则
5. 规则与策略包关系管理

## 6.3 探针绑定与下发

### 核心能力

1. 绑定应用
2. 绑定环境
3. 设置灰度比例
4. 查看实例级同步状态
5. 处理失败重试
6. 发起回滚

## 7. 通知渠道管理设计

## 7.1 页面目标

统一管理风险事件通知、审批通知和运维告警通知通道。

## 7.2 核心能力

1. 支持多种渠道类型
2. 配置目标地址和认证信息
3. 设置通知范围
4. 测试连通性
5. 查看渠道状态
6. 统计发送成功率和失败率

## 7.4 业务风险告警规则

通知渠道管理需要承接业务风险告警，而不只是运维告警。业务风险告警规则建议支持：

1. 高危 Prompt / 越狱事件聚合告警
2. 工具越界调用频次超阈值告警
3. 敏感数据输出持续发生告警
4. 同一用户 / 应用短时间多次触发高危规则告警
5. 事件超时未确认告警
6. 高危处置审批超时告警

告警规则应配置：

1. 触发条件
2. 聚合窗口
3. 抑制窗口
4. 通知渠道
5. 是否自动创建事件
6. 是否升级通知
7. 测试样本或历史回放范围

## 7.3 渠道类型建议

1. 飞书机器人
2. 钉钉机器人
3. SMTP 邮件
4. 短信网关

## 8. 核心流程设计

## 8.1 网关策略发布流程

```text
创建 / 编辑网关策略
→ 保存草稿
→ 测试 / 校验
→ 灰度发布
→ 正式启用
→ 生效监控
→ 失败回滚
```

## 8.2 探针策略包发布流程

```text
创建策略包
→ 生成版本
→ 绑定应用与环境
→ 提交下发
→ 查看实例同步状态
→ 部分失败处理
→ 全量同步
→ 版本沉淀
```

## 8.2A 规则干跑验证流程

```text
编辑规则 / 策略
→ 选择历史样本或上传样本
→ 执行干跑
→ 查看命中样本、置信度、误报样本
→ 调整规则条件
→ 通过后进入测试或灰度
```

### 关键要求

1. 干跑不得影响线上生效策略。
2. 干跑结果必须记录样本范围、执行人和执行时间。
3. 干跑命中样本应能跳转风险溯源工作台查看证据。
4. 误报样本应能回流到规则优化记录。

## 8.3 策略优化闭环

```text
风险事件 / 误报样本 / 调查结论
→ 提出规则优化需求
→ 调整策略 / 规则项 / 策略包
→ 灰度验证
→ 发布生效
```

## 8.4 通知联动流程

```text
事件触发 / 审批触发 / 运维告警触发
→ 匹配通知范围
→ 选择目标渠道
→ 发送消息
→ 记录发送结果
→ 渠道异常时标记告警
```

## 9. 关键设计要求

## 9.1 统一分层要求

必须明确以下分层关系：

1. 规则项是最底层能力单元。
2. 策略是可独立治理的业务对象。
3. 策略包是策略与规则项的组合发布单元。
4. 绑定是策略生效的目标映射关系。
5. 下发是配置真正同步到目标的执行过程。

## 9.2 版本治理要求

所有策略类对象至少应具备：

1. 版本号
2. 变更说明
3. 发布时间
4. 发布人
5. 当前状态
6. 回滚能力

### 版本号要求

建议版本号采用 `major.minor.patch`：

1. `major`
   - 策略语义或适用范围发生重大变化。
2. `minor`
   - 规则条件、动作配置、绑定范围发生可兼容变更。
3. `patch`
   - 文案、阈值微调、误报样本修正等低风险变更。

每次发布必须生成不可变版本快照，不允许直接覆盖已发布版本。

## 9.3 审批要求

以下操作建议强制审批：

1. 高危网关策略启用
2. 生产策略回滚
3. 高危探针限制策略发布
4. 全量灰度切换

## 9.4 审计要求

以下操作必须写入审计：

1. 创建策略
2. 编辑策略
3. 发布策略
4. 回滚策略
5. 修改绑定
6. 修改通知渠道
7. 测试通知渠道

## 9.5 下发与回滚要求

1. 下发必须展示聚合状态和实例级状态。
2. 部分实例失败时，整体状态应展示为部分同步。
3. 回滚必须明确回滚目标版本。
4. 回滚不删除失败版本，只改变当前生效版本。
5. 下发失败必须支持失败原因、重试和导出失败清单。
6. 策略发布、下发、回滚都必须关联操作审计。

## 10. 与其他模块关系

### 10.1 与风险事件

1. 风险事件处置动作需要引用策略能力。
2. 误报、接受风险和事件趋势会反向驱动策略优化。

### 10.2 与安全监控

1. 安全监控中的规则解释和命中信息来源于策略中心。

### 10.3 与资产中心

1. 应用详情需要展示当前绑定策略、版本和覆盖状态。

### 10.4 与系统管理

1. 平台角色和审批权限由系统管理控制。
2. 策略发布、回滚和通知测试要进入操作审计。
