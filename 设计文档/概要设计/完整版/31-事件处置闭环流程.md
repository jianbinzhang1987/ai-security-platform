# 事件处置闭环流程设计

## 1. 文档目标

本文档定义从正式风险事件创建，到事件指派、处置、审批、回滚和关闭的完整闭环流程。

---

## 2. 流程目标

1. 保证所有正式风险都有主档。
2. 保证事件状态流转清晰。
3. 保证处置动作有留痕、有审批、有回滚。
4. 保证误报和接受风险有正式路径。

---

## 3. 主流程

```text
风险线索转正式事件
→ new 待确认
→ 指派负责人
→ 风险确认
→ confirmed 已确认
→ in_progress 处理中
→ 执行处置动作
→ resolved 已处置
→ 复核
→ closed 已关闭
```

---

## 4. 流程步骤设计

## 4.1 创建事件

输入来源：

1. 风险溯源工作台
2. 会话审计
3. 自动事件生成规则

创建要求：

1. 必须带 `trace_id`
2. 必须带 `span_id`
3. 必须带风险摘要
4. 必须带风险等级和类型
5. 必须带 `source_field`
6. 建议带 `evidence_offset`
7. 可关联 `clue_id`

输出：

1. 创建 `risk_event`
2. 创建主证据关系 `event_evidence_rel`
3. 事件状态为 `new`

## 4.2 待确认

事件创建后进入 `new` 状态，等待人工判断。

待确认阶段可执行：

1. 查看详情
2. 指派负责人
3. 确认风险
4. 标记误报

## 4.3 指派负责人

目标：

1. 明确责任人
2. 进入处理队列

指派后需要记录：

1. 负责人
2. 指派人
3. 指派时间
4. 指派备注

## 4.4 风险确认

确认动作后：

1. 事件状态由 `new` 变为 `confirmed`
2. 可进一步进入 `in_progress`
3. 状态变化写入 `status_change_log`

确认时建议填写：

1. 确认依据
2. 影响范围
3. 下一步动作

## 4.5 处理中

处理中阶段可执行：

1. 发起处置动作
2. 发起审批
3. 补充调查
4. 更新处理进展

状态要求：

1. 已指派并开始处理后，事件进入 `in_progress`。
2. 补充调查不改变事件状态，但要记录处理进展。

## 4.6 执行处置动作

动作类型示例：

1. 通知
2. 限制
3. 降级
4. 恢复
5. 观察

动作范围示例：

1. Session
2. Tool
3. Agent
4. App

每个动作建议记录：

1. 动作类型
2. 作用范围
3. TTL
4. 审批单号
5. 执行状态
6. 回滚状态

动作状态要求：

1. 新建动作进入 `pending`。
2. 需要审批的动作审批通过后进入 `approved`。
3. 下发执行时进入 `executing`。
4. 生效后进入 `effective`。
5. 执行失败进入 `failed`。
6. TTL 到期进入 `expired`。

## 4.7 已处置

当关键处置动作生效并控制风险后，事件进入 `resolved` 状态。

此时应支持：

1. 复核
2. 查看生效状态
3. 查看回滚可能性

进入 `resolved` 前，至少应满足：

1. 存在调查结论或处置结论。
2. 关键处置动作已 `effective`，或确认无需动作。
3. 高危审批已完成。

## 4.8 关闭

关闭前应确认：

1. 风险已受控
2. 处置已留痕
3. 审批已完成
4. 结论已明确

关闭后：

1. 事件进入归档
2. 不再允许直接修改处理中状态
3. 如需继续处理，应创建派生事件或重新打开为新事件流程

---

## 5. 分支流程

## 5.1 误报流程

```text
new / confirmed / in_progress
→ 判定误报
→ 填写误报原因
→ 状态变更为 false_positive
→ 最终关闭
```

关键要求：

1. 误报原因必填。
2. 可选择回流规则优化样本池。
3. 误报事件关闭前仍需保留证据关系。

## 5.2 接受风险流程

```text
confirmed / in_progress
→ 发起接受风险申请
→ 审批通过
→ 状态变更为 accepted_risk
→ 关闭归档
```

关键要求：

1. 接受风险必须关联 `approval_id`。
2. 接受风险应记录风险范围、复核周期和责任人。
3. 审批拒绝后事件保持原状态。

## 5.3 回滚流程

```text
已生效处置动作
→ 发起回滚
→ 回滚审批
→ 执行回滚
→ 更新动作回滚状态
→ 事件重新评估
```

关键要求：

1. 只有 `effective` 且支持回滚的动作展示回滚入口。
2. 回滚审批通过后，动作进入 `rollback_pending`。
3. 回滚成功后，动作进入 `rolled_back`。
4. 回滚失败时保留失败原因和重试入口。
5. 回滚后事件是否回到 `in_progress` 由复核结果决定。

---

## 6. 审批流程嵌入点

以下场景建议强制审批：

1. 接受风险
2. 高危限制动作
3. App 级限制
4. 批量关闭高风险事件
5. 回滚高危处置动作

审批状态必须引用 `approval_status`，业务对象状态不得代替审批状态。

---

## 7. 输出与回流

事件闭环完成后，应向其他模块回流：

1. 向总览回流事件统计
2. 向资产中心回流应用风险状态
3. 向策略中心回流误报样本和优化需求
4. 向审计模块回流全部操作记录
5. 向状态变更日志回流全部状态迁移

---

## 8. 字段与接口引用

事件闭环流程涉及的关键字段：

1. `event_id`
2. `event_status`
3. `action_id`
4. `action_status`
5. `rollback_status`
6. `approval_id`
7. `trace_id`
8. `span_id`
9. `source_field`
10. `evidence_offset`

主要接口引用：

1. `GET /risk-events`
2. `POST /risk-events/{eventId}/assign`
3. `POST /risk-events/{eventId}/confirm`
4. `POST /risk-events/{eventId}/false-positive`
5. `POST /risk-events/{eventId}/accept-risk`
6. `POST /risk-events/{eventId}/actions`
7. `POST /event-actions/{actionId}/rollback`
8. `POST /risk-events/{eventId}/close`
