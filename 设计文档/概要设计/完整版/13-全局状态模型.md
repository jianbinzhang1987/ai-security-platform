# 大模型安全监测平台全局状态模型

## 1. 文档目标

本文档用于统一平台核心对象的状态定义、状态迁移规则和状态口径，避免后续页面、接口、数据库和流程设计中出现状态不一致问题。

---

## 2. 设计原则

全局状态模型设计遵循以下原则：

1. 同一业务对象只保留一套正式状态口径。
2. 列表页、详情页、接口和数据库中的状态语义必须一致。
3. 状态要能支撑审计和流程回放。
4. 状态要能明确区分“处理中”“已完成”“已失败”“已回滚”等语义。
5. 需要审批的对象，其业务状态与审批状态分离建模。

---

## 3. 核心状态对象

建议本平台优先统一以下对象的状态模型：

1. 应用接入状态
2. Agent / 节点识别状态
3. 风险线索状态
4. 风险事件状态
5. 处置动作状态
6. 审批单状态
7. 策略状态
8. 策略下发状态
9. 通知渠道状态
10. 采集器实例状态

---

## 3.1 状态字段命名规范

为了避免同一对象在页面、接口和数据库中出现多个口径，建议统一以下字段命名：

| 对象 | 主状态字段 | 辅助状态字段 | 说明 |
|---|---|---|---|
| 应用 | `access_status` | `health_status` | 接入生命周期与运行健康分离 |
| Agent / 节点 | `identify_status` | `confidence_level` | 识别状态与置信度分离 |
| 风险线索 | `clue_status` | `review_result` | 线索状态与人工判断结果分离 |
| 风险事件 | `event_status` | `severity` | 事件生命周期与风险等级分离 |
| 处置动作 | `action_status` | `rollback_status` | 执行状态与回滚状态分离 |
| 审批单 | `approval_status` | `approval_result` | 流程状态与审批结论分离 |
| 策略 | `policy_status` | `publish_status` | 配置状态与发布过程分离 |
| 策略包 | `package_status` | `dispatch_status` | 包生命周期与下发状态分离 |
| 通知渠道 | `channel_status` | `last_test_status` | 渠道启停与最近测试结果分离 |
| 采集器实例 | `instance_status` | `sync_status` | 实例运行状态与配置同步状态分离 |

### 3.2 状态码约束

1. 状态码使用小写英文和下划线。
2. 状态码一经接口发布，不建议随意重命名。
3. 页面中文展示不得反向作为接口枚举。
4. `rolled_back` 统一表示“已回滚”，不使用 `rollbacked`。
5. 业务状态、审批状态、下发状态、回滚状态不得混用。

## 4. 应用接入状态模型

## 4.1 状态定义

1. `draft`
   - 应用已创建，但尚未完成接入准备。
2. `pending_activation`
   - 已生成接入信息，等待首次上报激活。
3. `active`
   - 已收到首次有效上报，处于正常接入状态。
4. `degraded`
   - 应用仍在接入，但存在配置缺口、策略不同步或采集异常。
5. `disabled`
   - 应用被人工停用，不再接收数据或不再参与治理。
6. `retired`
   - 应用已下线归档，不再作为活跃治理对象。

## 4.2 状态迁移

```text
draft
→ pending_activation
→ active
→ degraded
→ active
→ disabled
→ retired
```

### 4.3 迁移规则

1. `draft -> pending_activation`
   - 生成接入指引和配置后触发。
2. `pending_activation -> active`
   - 收到首次有效 Trace / Span 上报。
3. `active -> degraded`
   - 采集异常、配置缺口、策略不同步、实例异常等。
4. `degraded -> active`
   - 异常恢复后回到正常状态。
5. `active/degraded -> disabled`
   - 人工停用。
6. `disabled -> retired`
   - 确认下线归档。

---

## 5. 风险线索状态模型

风险线索是正式事件生成前的平台识别结果，通常存在于 Trace / Span 调查域。

## 5.1 状态定义

1. `detected`
   - 已被规则识别为风险线索。
2. `under_review`
   - 已进入人工调查。
3. `linked_event`
   - 已关联到正式事件。
4. `dismissed`
   - 已确认为误报或无需形成事件。

## 5.2 状态迁移

```text
detected
→ under_review
→ linked_event

detected / under_review
→ dismissed
```

说明：

1. 风险线索不等同于正式事件。
2. 同一事件可关联多个风险线索。
3. `linked_event` 表示线索已进入事件闭环，不再回退为 `dismissed`；如事件后续被判定为误报，应通过事件状态表达。

---

## 6. Agent / 节点识别状态模型

Agent / 节点识别状态用于表达平台对应用内部智能体、工作流节点、工具调用节点的识别结果。

## 6.1 状态定义

1. `unidentified`
   - 尚未识别为 Agent 或工作流节点。
2. `suspected`
   - 已根据调用特征推断为疑似 Agent / 节点，但置信度不足。
3. `identified`
   - 已完成自动识别，具备稳定节点标识和关联上下文。
4. `confirmed`
   - 已由人工或接入配置确认。
5. `merged`
   - 已与其他重复节点合并。
6. `ignored`
   - 已人工忽略，不再作为独立治理对象展示。

## 6.2 状态迁移

```text
unidentified
→ suspected
→ identified
→ confirmed

identified / confirmed
→ merged

suspected / identified
→ ignored
```

## 6.3 迁移规则

1. `unidentified -> suspected`
   - 出现连续模型调用、工具编排、计划执行等 Agent 特征。
2. `suspected -> identified`
   - 达到识别置信度阈值，且可稳定生成节点标识。
3. `identified -> confirmed`
   - 应用负责人或安全管理员确认节点归属。
4. `identified/confirmed -> merged`
   - 确认为重复节点，合并到主节点。
5. `suspected/identified -> ignored`
   - 人工判定无需治理或属于噪声节点。

---

## 7. 风险事件状态模型

## 7.1 状态定义

1. `new`
   - 新生成事件，尚未确认或尚未分派。
2. `confirmed`
   - 已确认是真实风险，但尚未进入正式处置执行。
3. `in_progress`
   - 已有负责人，正在处理中。
4. `resolved`
   - 风险已完成处置，待确认关闭。
5. `false_positive`
   - 已确认为误报。
6. `accepted_risk`
   - 已完成风险接受审批，保留风险但不继续处置。
7. `closed`
   - 已完成闭环归档。

## 7.2 状态迁移

```text
new
→ confirmed
→ in_progress
→ resolved
→ closed

new
→ false_positive
→ closed

confirmed / in_progress
→ accepted_risk
→ closed
```

## 7.3 迁移规则

1. `new -> confirmed`
   - 人工确认是真实风险。
2. `confirmed -> in_progress`
   - 已分派负责人并启动处置。
3. `in_progress -> resolved`
   - 处置动作执行完成，风险得到控制。
4. `resolved -> closed`
   - 完成复核和归档。
5. `new -> false_positive`
   - 人工认定为误报。
6. `confirmed/in_progress -> accepted_risk`
   - 风险经审批被接受。
7. `false_positive/accepted_risk/resolved -> closed`
   - 完成最终归档。

## 7.4 补充规则

1. `accepted_risk` 不等于 `closed`，必须保留单独状态。
2. `resolved` 不等于 `closed`，要保留复核空间。
3. 事件一旦 `closed`，不得直接修改为处理中，需重新开启或派生新事件。

---

## 8. 处置动作状态模型

处置动作用于记录通知、限制、降级、恢复、回滚等动作的执行过程。

## 8.1 状态定义

1. `pending`
   - 动作已创建，待执行或待审批。
2. `approved`
   - 审批通过，待执行。
3. `executing`
   - 动作下发执行中。
4. `effective`
   - 动作已生效。
5. `failed`
   - 动作执行失败。
6. `rollback_pending`
   - 已发起回滚，待执行。
7. `rolled_back`
   - 已完成回滚。
8. `expired`
   - TTL 到期自动失效。
9. `canceled`
   - 动作在执行前被取消。

## 8.2 状态迁移

```text
pending
→ approved
→ executing
→ effective
→ expired

executing
→ failed

effective
→ rollback_pending
→ rolled_back

pending
→ canceled
```

## 8.3 设计说明

1. 审批状态与动作状态分离，但动作流转要受审批结果影响。
2. TTL 型动作必须支持 `expired`。
3. 可回滚动作必须支持回滚状态链路。
4. 通知类动作可从 `pending` 直接进入 `executing`，不强制经过 `approved`。
5. 高危限制、降级、恢复、回滚类动作必须先完成审批。

## 8.4 动作类型与状态要求

| 动作类型 | 是否需要审批 | 是否需要 TTL | 是否支持回滚 | 说明 |
|---|---|---|---|---|
| `notify` 通知 | 否 | 否 | 否 | 发送企业 IM、邮件、短信、工单 |
| `restrict_session` 限制会话 | 视等级 | 是 | 是 | 限制单个会话继续执行 |
| `restrict_tool` 限制工具 | 是 | 是 | 是 | 禁用或限制指定工具调用 |
| `degrade_app` 应用降级 | 是 | 是 | 是 | 对应用、路由或实例生效 |
| `block_subject` 阻断主体 | 是 | 是 | 是 | 阻断用户、API Key、应用等主体 |
| `restore` 恢复 | 是 | 否 | 否 | 恢复前序限制动作 |
| `manual_record` 人工登记 | 否 | 否 | 否 | 仅记录线下处置或外部系统动作 |

## 9. 审批单状态模型

## 9.1 状态定义

1. `submitted`
   - 已提交审批。
2. `in_review`
   - 审批中。
3. `approved`
   - 审批通过。
4. `rejected`
   - 审批拒绝。
5. `canceled`
   - 申请人撤销。
6. `expired`
   - 审批超时失效。

## 9.2 状态迁移

```text
submitted
→ in_review
→ approved

submitted / in_review
→ rejected

submitted / in_review
→ canceled

submitted / in_review
→ expired
```

## 10. 策略状态模型

适用于网关策略、探针高级规则项等可独立配置对象。

## 10.1 状态定义

1. `draft`
   - 草稿态，尚未发布。
2. `testing`
   - 测试或干跑中。
3. `gray`
   - 灰度发布中。
4. `enabled`
   - 已启用。
5. `disabled`
   - 已停用。
6. `archived`
   - 已归档。

## 10.2 状态迁移

```text
draft
→ testing
→ gray
→ enabled
→ disabled
→ archived
```

补充说明：

1. `gray` 和 `enabled` 要严格区分。
2. 停用后允许再次启用。

---

## 11. 策略包状态模型

适用于探针策略包这种组合治理对象。

## 11.1 状态定义

1. `draft`
2. `ready`
3. `gray`
4. `enabled`
5. `disabled`
6. `rolled_back`
7. `archived`

### 含义说明

1. `ready`
   - 包内容完整，可进入发布流程。
2. `rolled_back`
   - 最近一次正式版本已回滚。

## 11.2 状态迁移

```text
draft
→ ready
→ gray
→ enabled
→ disabled
→ archived

enabled
→ rolled_back
→ disabled / ready
```

### 11.3 迁移规则

1. `draft -> ready`
   - 策略包内容、规则项、通知配置和绑定范围完成校验。
2. `ready -> gray`
   - 进入灰度发布或小范围下发。
3. `gray -> enabled`
   - 灰度验证通过并正式启用。
4. `enabled -> disabled`
   - 人工停用或被替代版本取代。
5. `enabled -> rolled_back`
   - 当前版本发生异常并执行回滚。
6. `rolled_back -> ready`
   - 基于回滚后的稳定版本继续编辑新版本。

---

## 12. 策略下发状态模型

适用于网关绑定下发、探针绑定下发、应用实例同步等场景。

## 12.1 状态定义

1. `not_dispatched`
   - 尚未下发。
2. `pending_dispatch`
   - 已进入下发任务队列。
3. `dispatching`
   - 下发中。
4. `partially_synced`
   - 部分实例已同步。
5. `synced`
   - 全部目标已同步。
6. `failed`
   - 下发失败。
7. `rollbacking`
   - 回滚中。
8. `rolled_back`
   - 已回滚。

## 12.2 状态迁移

```text
not_dispatched
→ pending_dispatch
→ dispatching
→ partially_synced
→ synced

dispatching
→ failed

synced
→ rollbacking
→ rolled_back
```

## 12.3 实例级下发结果

策略下发在列表页可展示聚合状态，但详情页必须保留实例级结果：

1. 目标实例总数。
2. 已同步实例数。
3. 失败实例数。
4. 最近同步时间。
5. 失败原因。
6. 当前生效版本。
7. 期望版本。

当任一实例失败但存在成功实例时，聚合状态应为 `partially_synced`，不得展示为 `synced`。

## 13. 通知渠道状态模型

## 13.1 状态定义

1. `enabled`
   - 渠道可正常使用。
2. `degraded`
   - 渠道可用但存在异常，例如延迟高、部分失败。
3. `abnormal`
   - 渠道测试失败或发送异常。
4. `disabled`
   - 人工停用。

## 13.2 状态迁移

```text
enabled
→ degraded
→ abnormal
→ enabled

enabled / degraded / abnormal
→ disabled
```

---

## 14. 采集器实例状态模型

## 14.1 状态定义

1. `online`
   - 实例在线且指标正常。
2. `busy`
   - 在线但负载高或存在明显积压。
3. `degraded`
   - 在线但错误率高、写入异常或心跳异常。
4. `offline`
   - 心跳丢失或实例离线。
5. `maintenance`
   - 运维维护中。

## 14.2 状态迁移

```text
online
→ busy
→ online

online / busy
→ degraded
→ online

online / busy / degraded
→ offline

offline
→ online

online / busy / degraded
→ maintenance
→ online
```

## 16. 状态与审批联动规则

### 16.1 必须审批的状态迁移

| 对象 | 状态迁移 | 审批类型 |
|---|---|---|
| 风险事件 | `confirmed/in_progress -> accepted_risk` | 风险接受审批 |
| 处置动作 | `pending -> approved` | 高危处置审批 |
| 处置动作 | `effective -> rollback_pending` | 回滚审批 |
| 策略 | `gray -> enabled` | 生产发布审批 |
| 策略 | `enabled -> disabled` | 生产停用审批 |
| 策略包 | `gray -> enabled` | 策略包发布审批 |
| 策略下发 | `synced -> rollbacking` | 下发回滚审批 |

### 16.2 审批拒绝后的处理

1. 风险接受审批被拒绝后，事件保持原状态。
2. 高危处置审批被拒绝后，动作状态变为 `canceled`。
3. 策略发布审批被拒绝后，策略保持 `draft`、`testing` 或 `gray`，不得进入 `enabled`。
4. 回滚审批被拒绝后，原生效版本继续保持生效。

## 17. 状态变更审计规则

所有核心对象状态变更必须生成状态变更记录，建议字段如下：

1. `change_id`
2. 对象类型
3. 对象 ID
4. 原状态
5. 新状态
6. 触发方式
7. 触发人 / 系统任务
8. 触发时间
9. 变更原因
10. 审批单号
11. 关联事件 / Trace / Span
12. 执行结果
13. 失败原因

### 17.1 触发方式枚举

1. `manual`
   - 人工操作触发。
2. `system`
   - 系统规则或定时任务触发。
3. `approval`
   - 审批结果触发。
4. `sync_callback`
   - 下发或实例同步回调触发。
5. `ttl_expired`
   - TTL 到期触发。

## 19. 当前结论

### 19.1 本轮必须统一的三类状态

优先级最高的三类状态是：

1. 风险事件状态
2. 处置动作状态
3. 策略下发状态

原因如下：

1. 它们直接决定平台闭环是否成立。
2. 它们跨越溯源、事件、策略、审计四大模块。
3. 若这三类状态不统一，后续接口和页面会持续返工。

### 19.2 建议下一步

后续模块设计中，所有页面、接口、表结构和流程说明，必须直接引用本文状态模型，不得另起状态口径。
