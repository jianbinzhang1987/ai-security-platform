# 系统管理模块概要设计

## 1. 文档目标

本文档定义平台“系统管理”模块的业务定位、页面范围、功能结构和关键设计要求。

系统管理是平台的基础能力域，负责用户权限、操作审计和采集器配置三个核心子域。

---

## 2. 模块定位

### 2.1 业务定位

系统管理负责保障平台的身份权限、审计留痕和采集运行基础能力，为其他业务模块提供可信的管理底座。

### 2.2 核心职责

1. 管理用户和角色。
2. 提供权限边界控制。
3. 记录关键操作审计。
4. 监控采集器运行状态。
5. 管理采集配置和发布。

### 2.3 模块边界

系统管理负责：

1. 身份与权限体系。
2. 操作审计体系。
3. 采集链路管理。

系统管理不直接负责：

1. 风险调查。
2. 风险事件闭环。
3. 业务安全策略本体配置。

---

## 3. 页面范围

当前纳入正式设计的页面：

1. 用户与权限
2. 操作审计日志
3. 数据采集器配置

---

## 4. 用户与权限设计

## 4.1 页面目标

统一管理平台账号、角色和账户安全状态，为平台提供稳定的身份管理能力。

## 4.2 核心功能

1. 用户列表查询
2. 用户创建
3. 用户编辑
4. 角色分配
5. MFA 状态管理
6. 用户启用 / 禁用
7. 强制下线

## 4.3 查询条件

建议支持：

1. 用户名
2. 账号
3. 角色
4. 账号状态
5. MFA 状态

## 4.4 列表字段

建议字段如下：

1. 用户名
2. 账号
3. 所属角色
4. MFA 状态
5. 账号状态
6. 最近登录时间
7. 操作

## 4.5 页面操作

1. 新建用户
2. 编辑角色
3. 启用 / 禁用
4. 强制下线
5. 查看用户详情

## 4.6 关键设计要求

1. 文案必须全部企业化、专业化。
2. 账号状态、MFA 状态和角色必须严格区分。
3. 高危角色变更应支持审批或双人确认。

---

## 5. 操作审计日志设计

## 5.1 页面目标

记录平台关键操作，支持事后追溯、合规检查和问题排查。

## 5.2 核心功能

1. 审计日志查询
2. 审计详情查看
3. 审计导出
4. 审计对象跳转

## 5.3 查询条件

建议支持：

1. 时间范围
2. 操作人
3. 模块
4. 操作类型
5. 操作结果
6. 对象类型
7. 对象 ID

## 5.4 列表字段

建议字段如下：

1. `audit_id`
2. 操作时间
3. 操作人
4. 模块
5. 操作类型
6. 对象类型
7. 对象 ID
8. 结果
9. 操作

## 5.5 详情内容

建议详情至少包含：

1. 操作摘要
2. 变更前后
3. 请求来源
4. 审批单号
5. 关联对象链接

## 5.6 必须审计的操作范围

1. 用户创建 / 角色变更
2. 应用创建 / 配置变更
3. 事件确认 / 关闭 / 接受风险
4. 处置动作下发 / 回滚
5. 策略创建 / 发布 / 回滚
6. 渠道配置变更
7. 采集器配置发布
8. 高敏证据访问与导出

---

## 6. 数据采集器配置设计

## 6.1 页面目标

统一展示采集链路健康状态，并管理 Collector 相关配置。

## 6.2 页面定位

该页面不是单纯的运维配置页，而是安全监测平台的采集健康与配置治理页，应同时服务：

1. 平台管理员
2. 安全管理员
3. 安全运营的查看需求

## 6.3 健康概览

建议首页展示以下健康指标：

1. Collector 在线实例数
2. 最近心跳时间
3. OTLP 接收 QPS
4. 错误率
5. 丢弃数
6. Kafka / 队列积压
7. ClickHouse / 存储写入状态

## 6.4 实例状态列表

建议字段如下：

1. `collector_id`
2. 区域
3. 版本
4. 状态
5. 最近心跳
6. 接收 QPS
7. 丢弃数
8. 配置版本

## 6.5 配置项设计

建议配置项包括：

1. 噪音过滤
2. 采样率
3. 高风险保留策略
4. 批量发送大小
5. 最大等待时间
6. 心跳参数
7. 队列参数

## 6.6 配置管理能力

1. 查看当前配置版本
2. 保存并发布
3. 恢复默认
4. 查看历史版本
5. 查看实例同步状态

## 6.7 页面关键要求

1. 采集健康必须和安全总览、资产中心形成下钻关系。
2. 配置发布必须形成版本留痕。
3. 配置变更必须有同步状态反馈。

---

## 7. 核心流程设计

## 7.1 用户权限管理流程

```text
创建 / 编辑用户
→ 分配角色
→ 设置账号状态
→ 生效
→ 审计留痕
```

## 7.2 审计追溯流程

```text
输入筛选条件
→ 查询审计日志
→ 查看详情
→ 关联对象跳转
→ 导出或归档
```

## 7.3 采集配置发布流程

```text
修改采集配置
→ 生成配置新版本
→ 保存并发布
→ Collector 拉取配置
→ 查看实例同步状态
→ 审计留痕
```

## 7.4 采集异常处置流程

```text
发现心跳丢失 / 队列积压 / 写入异常
→ 查看实例状态
→ 定位异常组件
→ 执行运维处置
→ 恢复后回到正常状态
```

---

## 8. 与其他模块关系

### 8.1 与安全总览

1. 安全总览中的采集健康指标来源于数据采集器配置页面的聚合数据。

### 8.2 与资产中心

1. 应用列表和应用详情中的采集健康状态依赖 Collector 健康数据。

### 8.3 与风险事件

1. 平台级处置、回滚和高危访问行为要进入审计日志。

### 8.4 与统一策略中心

1. 策略发布、回滚、通知测试等动作要写入审计日志。
2. 用户权限决定策略管理边界。

---

## 9. 数据与权限要求

## 9.1 权限要求

1. 平台管理员拥有全量系统管理权限。
2. 安全管理员默认只读审计与采集健康，不管理用户。
3. 安全运营默认仅查看采集健康，不修改配置。
4. 审计只读可查看审计日志，不得修改任何系统配置。

## 9.2 审计要求

以下动作必须进入操作审计：

1. 用户创建
2. 角色变更
3. 用户禁用
4. 强制下线
5. 审计日志导出
6. 采集配置变更
7. 采集配置发布
8. 采集配置恢复默认
