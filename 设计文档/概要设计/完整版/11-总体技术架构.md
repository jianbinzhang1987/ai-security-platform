# 大模型安全监测平台总体技术架构

## 1. 文档目标

本文档用于定义大模型安全监测平台的总体技术架构，明确系统分层、核心组件、数据流向、部署边界和关键技术能力，为后续详细设计与实施提供统一技术基线。

---

## 2. 技术架构目标

平台总体技术架构需要同时满足以下目标：

1. 支撑网关侧与探针侧双链路安全监测。
2. 支撑 Trace / Span 级证据采集与检索。
3. 支撑风险事件闭环、策略治理和审计留痕。
4. 支撑高并发采集、近实时处理和多维检索。
5. 支撑策略下发、灰度发布和回滚。
6. 支撑高敏数据脱敏、授权访问和操作审计。

---

## 3. 总体分层

建议平台技术架构按以下五层组织：

1. 接入采集层
2. 数据处理层
3. 业务服务层
4. 存储检索层
5. 展示与管理层

### 3.1 接入采集层

负责接收和采集来自不同运行面的安全数据。

主要来源包括：

1. 网关侧请求与响应数据
2. 探针侧 Trace / Span / Tool I/O 数据
3. 应用实例心跳与运行元数据
4. 策略执行与下发反馈数据
5. 通知渠道发送结果

### 3.2 数据处理层

负责将采集到的数据转换为可用于风险识别、调查和闭环处理的标准化数据。

主要职责：

1. 数据标准化
2. 风险规则匹配
3. 事件聚合
4. 指标计算
5. 数据路由与异步分发

### 3.3 业务服务层

负责承载平台核心业务逻辑。

主要服务包括：

1. 资产中心服务
2. 安全监控服务
3. 风险事件服务
4. 策略中心服务
5. 用户权限服务
6. 审计服务
7. 通知服务
8. 采集配置服务

### 3.4 存储检索层

负责承载结构化、半结构化和原始证据数据的存储与查询。

建议按数据类型分层：

1. 关系型业务库
2. 检索索引库
3. 时序 / 明细分析库
4. 对象存储
5. 缓存

### 3.5 展示与管理层

负责管理端前端界面、查询交互、运维控制和审计可视化。

---

## 4. 核心技术架构图

建议总体技术链路抽象如下：

```text
应用 / Agent / 网关
    ↓
SDK / 探针 / 网关日志
    ↓
Collector / 接入网关
    ↓
消息队列 / 流式处理
    ↓
规则识别 / 聚合计算 / 事件生成
    ↓
业务服务
    ├── 资产中心
    ├── 安全监控
    ├── 风险事件
    ├── 统一策略中心
    ├── 系统管理
    └── 审计服务
    ↓
多类型存储
    ├── 业务库
    ├── 检索库
    ├── 分析库
    └── 对象存储
    ↓
管理端前端
```

## 5. 核心组件设计

## 5.1 采集接入组件

### 目标

统一接收网关侧和探针侧的安全相关数据。

### 关键能力

1. 接收 OTLP / Trace / Span 数据
2. 接收网关会话与动作日志
3. 接收实例心跳和配置同步反馈
4. 数据基础校验和过滤

## 5.2 消息队列与异步处理组件

### 目标

解耦高并发采集与后续业务处理。

### 关键能力

1. 削峰填谷
2. 异步聚合
3. 多消费链路分发
4. 失败重试

## 5.3 风险识别与聚合组件

### 目标

将采集数据转化为风险标记、风险线索和事件输入。

### 关键能力

1. 风险规则匹配
2. Prompt / 输入 / 输出检测
3. 工具边界检测
4. 多轮会话风险聚合
5. 风险打分与分级

## 5.4 事件闭环组件

### 目标

管理风险事件与处置动作的生命周期。

### 关键能力

1. 创建事件
2. 指派与协同
3. 动作执行
4. 审批与回滚
5. 事件关闭与归档

## 5.5 策略治理组件

### 目标

统一承载网关策略、探针策略、高级规则项、绑定下发和回滚。

### 关键能力

1. 策略 CRUD
2. 版本管理
3. 策略包生成
4. 绑定与灰度
5. 下发与回滚

## 5.6 审计与权限组件

### 目标

统一管理用户、角色、对象级权限和操作审计。

### 关键能力

1. 身份鉴权
2. 角色授权
3. 数据权限控制
4. 高敏访问控制
5. 全链路操作审计

## 6. 存储架构建议

## 6.1 关系型业务库

适合存储：

1. 用户
2. 角色
3. 应用
4. 事件
5. 动作
6. 审批
7. 策略
8. 策略包
9. 通知渠道
10. 审计日志索引信息

## 6.2 检索库

适合存储：

1. Trace 检索索引
2. Span 检索索引
3. 会话检索索引
4. 事件全文检索
5. 风险字段搜索索引

## 6.3 分析库

适合存储：

1. 高并发明细数据
2. 趋势分析数据
3. 聚合指标
4. 覆盖率、排行、分布统计

## 6.4 对象存储

适合存储：

1. 原始 Prompt / Response / Tool Payload
2. 高敏证据原文
3. 导出文件
4. 审计归档附件

## 6.5 缓存

适合存储：

1. 高频查询结果
2. 字典项
3. 权限会话
4. 临时审批上下文

## 7. 数据流设计

## 7.1 采集流

```text
网关 / 探针数据
→ Collector 接入
→ 队列
→ 标准化处理
→ 存储与识别
```

## 7.2 风险识别流

```text
标准化数据
→ 风险规则识别
→ 风险打分
→ 风险线索
→ 事件候选
```

## 7.3 调查流

```text
风险线索
→ Trace / Span 查询
→ 证据工作区展示
→ 人工调查结论
→ 进入事件闭环
```

## 7.4 策略发布流

```text
创建 / 编辑策略
→ 版本生成
→ 审批 / 灰度
→ 绑定与下发
→ 同步反馈
→ 生效监控
```

## 7.5 审计流

```text
关键操作
→ 审计事件生成
→ 审计存储
→ 查询与导出
```

## 8. 服务拆分建议

建议后续逻辑上至少拆分为以下服务域：

1. `asset-service`
2. `monitor-service`
3. `event-service`
4. `policy-service`
5. `session-audit-service`
6. `auth-service`
7. `audit-service`
8. `collector-config-service`
9. `notify-service`

说明：

1. 初期可以是单体逻辑模块化。
2. 后续可按负载和组织边界演化为独立服务。

---

## 9. 安全与合规要求

## 9.1 数据安全

1. 高敏原文与脱敏视图分离。
2. 原始证据存储加密。
3. 对象存储访问必须授权。
4. 导出行为必须审计。

## 9.2 接口安全

1. 统一鉴权。
2. 角色与对象级权限校验。
3. 高危接口支持审批前置。

## 9.3 审计安全

1. 关键变更必须审计。
2. 高敏访问必须审计。
3. 回滚与审批必须可追溯。

---

## 10. 部署架构建议

建议部署至少包含：

1. 前端管理端
2. API 网关
3. 业务服务集群
4. Collector 集群
5. 消息队列
6. 业务数据库
7. 检索与分析存储
8. 对象存储

部署建议原则：

1. 业务服务与采集服务分离部署。
2. 原始证据存储与业务库分离。
3. 检索与分析链路独立于事务链路。

---

## 11. 可观测性要求

平台自身也需要具备可观测能力，建议至少包括：

1. 服务 QPS
2. 接口耗时
3. 错误率
4. 队列积压
5. 存储写入成功率
6. 下发成功率
7. 通知发送成功率
