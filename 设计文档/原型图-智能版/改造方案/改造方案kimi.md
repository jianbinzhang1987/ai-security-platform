基于已审阅的系统设计文档（`智能化改造/概要设计/系统设计`）和原型实现（`原型图-智能版`），当前原型在**系统易用性**和**用户理解度**方面存在以下核心问题：

---

## 一、导航与信息架构：用户会"迷路"

### 1.1 默认首页不合理

[index.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/index.html:0:0-0:0) 默认加载 **接入应用管理**（资产管理），而非安全总览或风险事件。对于一个安全监测平台，运营人员登录后最想看到的是"今天有多少风险需要处理"，而不是"系统接入了多少个应用"。

### 1.2 导航分组错位

**数据分级管理** 被错误地挂在 **统一策略中心** 下（与自动响应规则、通知渠道并列），但它的文件路径是 [pages/system/](cci:9://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/system:0:0-0:0)，内容属于系统管理范畴。这会导致用户按"策略"分类查找时看到不相关的"数据分级"功能。

### 1.3 分期页面未隔离，造成"功能幻影"

[index.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/index.html:0:0-0:0) 导航中，P1（知识库管理全部页面）、P2（SOC分析驾驶舱等）、P3（自动响应规则）的功能全部可见，没有任何 `nav-hidden` 标记。用户点击后可能进入只有标题和空状态的页面，产生"系统坏了"或"我权限不够"的困惑。

## 二、概念与状态过载：用户需要同时理解三套状态机

以 [event-detail.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/events/event-detail.html:0:0-0:0) 为例，一个风险事件的顶部同时出现：

| 状态类型    | 示例值                           | 用户认知负担                 |
| ----------- | -------------------------------- | ---------------------------- |
| 事件状态    | 高风险、处理中                   | 业务语义，容易理解           |
| 检测来源    | 规则+AI检出                      | 需要理解"联合检出"的含义     |
| AI 检测状态 | success / timeout / circuit_open | **技术术语，用户困惑** |
| AI 研判状态 | generated / confirmed            | 需要理解"生成"和"确认"的区别 |
| 置信度标识  | 低置信待复核                     | 又一个独立概念               |

**核心问题**：`circuit_open`（熔断）、`timeout`（超时降级）属于系统运维/研发关注的**工程指标**，以醒目的警示标签出现在安全事件详情页顶部时，会让审核员产生困惑：

> "我是应该去修服务器，还是继续处理这个安全事件？"

**建议**：对安全运营人员，系统只需告诉他**"这是什么风险"**以及**"我为你提供了哪些辅助"**。底层降级、熔断逻辑应统一折叠为一句话，如"AI 辅助当前不可用，已自动切换至纯规则检测"。

## 三、工作流割裂：用户不知道下一步该点哪里

[event-detail.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/events/event-detail.html:0:0-0:0) 的右侧操作区存在严重的**"按钮迷宫"**：

### 3.1 三组操作按钮群同时出现

1. **AI 辅助研判卡片**：确认研判 / 修正 / 拒绝
2. **AI 处置建议卡片**：采纳并执行 / 修改后执行 / 拒绝并记录 / 转人工
3. **处置动作卡片**：指派负责人 / 下发限制 / 标记误报 / 接受风险 / 处置登记

### 3.2 逻辑死锁

- 如果我认为事件是误报，应该点右侧的 **"拒绝（AI研判）"**，还是底部处置区的 **"标记误报"**？
- 如果我点击了 **"确认研判"**，这是否等同于事件的 **"处置登记"**？
- AI 建议"限制工具调用频率"，但处置动作区也有"下发限制"——这两个按钮是什么关系？

**本质问题**：系统将 **"对 AI 的反馈"** 与 **"对事件的处置"** 作为两个独立的操作流，但用户的心理模型是"处理这个事件"。

## 四、信息层级混乱：左顾右盼的阅读体验

### 4.1 证据与结论被物理拆散

当前设计中：

- **AI 为什么认为有风险**（命中片段、判定理由、反例提示）藏在左侧 **证据工作区 → AI检测结果 Tab**
- **AI 对全局的看法**（攻击手法、影响面、处置优先级）放在右侧 **AI辅助研判卡片**

用户在阅读时，必须在左侧切换 Tab 查看证据片段，然后再去右侧看研判结论。这种**左右分裂的布局**打断了"证据 → 结论"的连贯思考过程。

### 4.2 首屏被开发态术语占领

事件概况卡片充斥着：

```
trace_id: TRC-20260416-018 | span_id: sp_04_tool
source_field: tool.input | evidence_offset: 63-89
model_version: sec-judge-v1.2 | prompt_template_version: judge-prompt-v0.8
```

`trace_id`、`span_id`、`evidence_offset`、`model_version` 等字段对模型调优有用，但对日均处理几百个告警的运营人员来说是**严重的视觉噪音**，占据了页面最宝贵的上半屏空间。

---

## 五、分期策略混乱：P0.5a 页面混入了 P3 能力

[event-detail.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/events/event-detail.html:0:0-0:0)（P0.5a 核心闭环）中出现了大量不属于该阶段的能力：

| 页面元素                                                    | 所属期次     | 问题                               |
| ----------------------------------------------------------- | ------------ | ---------------------------------- |
| AI 处置建议卡片（推荐动作、动作级别、TTL、影响评估）        | **P3** | 自动响应尚未实现，建议卡片无法执行 |
| 自动执行台账（L1/L2/L3 动作级别、TTL 倒计时）               | **P3** | 展示未交付的能力                   |
| 动作与审批台账（action_id / approval_id / rollback_status） | **P3** | 工程调试字段直接暴露               |

**后果**：用户在 P0.5a 阶段看到"采纳建议并执行"按钮，点击后系统无法真正执行，产生信任危机。

## 六、知识库页面（P1）：功能堆砌但缺乏操作引导

以用户当前打开的 [security-qa.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/knowledge/security-qa.html:0:0-0:0)（安全知识问答）为例：

- 页面只有一个输入框和"提问"按钮，下方直接展示问答历史
- 缺乏**常见问题的快捷入口**或**引导性问题**，首次使用的用户不知道可以问什么
- 问答结果中的 `source-ref`（来源引用）以纯文本链接形式展示，用户难以判断信息可信度

对比 `04-P1知识库与评测治理原型说明.md` 中的设计目标，该页面只实现了"能问答"，但没有实现"帮助用户快速获取策略配置、威胁情报和合规要求的解答"的**引导性设计**。

## 七、安全总览：工程状态直接暴露

[dashboard.html](cci:7://file:///e:/code/%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%AE%89%E5%85%A8%E7%9B%91%E6%B5%8B%E5%B9%B3%E5%8F%B0/%E8%AE%BE%E8%AE%A1%E6%96%87%E6%A1%A3/%E5%8E%9F%E5%9E%8B%E5%9B%BE-%E6%99%BA%E8%83%BD%E7%89%88/pages/assets/dashboard.html:0:0-0:0) 中的"AI状态分布"使用原始枚举值作为标签：

```
success ———— 72%
pending ———— 9%
timeout ———— 6%
circuit_open ———— 3%
skipped ———— 10%
```

`circuit_open`、`skipped` 对运营人员是黑话。`success` 也不明确——是"AI检测成功"还是"风险已确认"？

**建议**：转化为业务语言，如：

- "AI 辅助正常" 72%
- "检测排队中" 9%
- "AI 服务超时，已降级" 6%
- "模型熔断中，纯规则运行" 3%
- "策略跳过 AI 检测" 10%

## 总结

当前原型设计更像是一个**"数据模型字段的 UI 堆砌版"**：后端新增了 20 多个实体字段，前端把它们全部平铺展示，但忽略了**安全运营人员的心智模型**。

**核心改造方向**：

1. **从"以字段为中心"转向"以工作流为中心"**：将枯燥的模型运行状态沉淀到水下
2. **合并操作流**："对 AI 的反馈"与"对事件的处置"合二为一，例如在点击"标记误报"时，系统弹窗询问是否同时反馈给 AI 样本库
3. **以"故事线"重组页面**：将事件基本信息和 AI 研判摘要置于顶部核心区，关联证据紧贴在结论下方
4. **分期可见性控制**：未交付的 P1/P2/P3 功能应从导航中隐藏，避免"功能幻影"
5. **术语翻译层**：工程枚举值（`circuit_open`、`timeout`）必须经业务语义转换后再展示给用户
