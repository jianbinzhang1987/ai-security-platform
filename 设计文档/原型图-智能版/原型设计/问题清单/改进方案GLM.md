# 当前原型设计易用性与用户理解度问题分析

## 一、信息架构问题

### 1. 安全监控导航项过多（9个平级入口）

`@/index.html:374-467` 中"安全监控"下挂了9个平级子菜单：风险溯源、会话追踪、内容检索、意图偏离、SOC驾驶舱、人员风险、关联分析、行为基线、组织态势、AI服务监控。

**问题**：日常高频操作（溯源、会话追踪）与低频分析页面（SOC驾驶舱、组织态势）平铺，用户难以快速定位。没有优先级视觉区分。

**建议**：分为"日常监控"和"高级分析"两组，或用分隔线/子标题区分高频与低频入口。

### 2. 策略中心三级嵌套，入口分散

导航为"网关策略管理 → 4子项" + "探针策略管理 → 3子项" + "自动响应规则" + "通知渠道"。

**问题**：用户需先理解"网关策略"和"探针策略"的技术区别才能找到配置入口。安全运营人员更关心"防什么"（提示词攻击？数据泄露？），而非"这个策略跑在网关还是探针上"。

**建议**：提供"按防护对象"的视图入口（如：提示词防护、数据防泄露、工具管控），作为网关/探针技术分类的补充。

### 3. 知识库管理模块定位模糊

知识库下含"知识条目、样本库、策略模板库、安全知识问答、模型效果评估"——功能跨度从内容管理到ML运维，用户很难预期"模型评测"在"知识库"下面。

**建议**：将"模型效果评估"移至系统管理下的"AI模型治理"子模块，知识库聚焦知识+样本。

## 二、认知负荷问题

### 4. 风险事件详情页信息过载（最严重问题）

`@/pages/events/event-detail.html:62-297` — 单页包含 **8个卡片区域 + 6个弹窗**：

| 区域                      | 信息量                                  |
| ------------------------- | --------------------------------------- |
| 事件概况                  | 17个描述字段                            |
| 上下文预览                | 4段上下文                               |
| 证据工作区                | 5个Tab（摘要/JSON/AI检测/Raw/规则解释） |
| 处置记录                  | 时间线                                  |
| 自动执行台账              | 表格                                    |
| 动作与审批台账            | 表格                                    |
| 状态变更记录              | 表格                                    |
| 处置结论                  | 字段                                    |
| **右侧** AI研判卡片 | 8个字段+3个操作                         |
| **右侧** 相似事件   | 列表                                    |
| **右侧** AI处置建议 | 建议内容+4个操作                        |
| **右侧** 处置动作   | 6个按钮                                 |
| **右侧** 审计要求   | 列表                                    |

**问题**：一个安全运营人员打开事件详情页，面对 **17个基础字段 + 5个证据Tab + 3个右侧卡片 + 6个弹窗**，认知负荷极高。核心问题"这个事件是不是真的风险？我该做什么？"被淹没在信息海洋中。

**建议**：

- 采用**渐进式披露**：首屏只展示"事件概要+AI研判结论+核心操作"，其余折叠
- AI研判卡片应置顶为"首要行动指引"，而非与相似事件、审计要求并列
- 处置动作和AI处置建议合并为一个操作区，避免两套按钮让用户困惑

### 5. AI状态术语晦涩

`@/pages/events/event-detail.html:67-71` 中标题区展示：

```
detection_source: rule_and_ai
ai_status: success / timeout / circuit_open / skipped_by_policy
ai_analysis_status: generated / confirmed / modified / rejected
```

**问题**：`circuit_open`（熔断）、`skipped_by_policy`（策略跳过）是工程术语，安全运营人员不理解其含义。7种ai_status + 8种ai_analysis_status = **15种状态组合**，用户无法快速判断"这个事件的AI结果能不能信"。

**建议**：

- 将状态映射为用户语言：`circuit_open` → "AI服务熔断中，仅规则结果可用"；`skipped_by_policy` → "按策略配置跳过AI检测"
- 减少展示状态数：合并为3个用户关心的维度——"AI是否参与？结果是否可信？是否需要我操作？"

### 6. 内容安全策略页信息密度过高

`@/pages/policy/content-security.html:86-151` — 单页包含4个安全域Tab，每个Tab下有带checkbox的表格，表头10列，加上统计卡片、批量操作、版本历史、样例模拟、检测融合设置等入口。

**问题**：策略运营人员面对此页面，不知道从哪里开始。4个Tab × 10列 × 多个操作按钮，且"检测融合设置"是全局配置却放在页面顶部按钮区，容易被忽略或误操作。

**建议**：检测融合设置移至系统管理；页面默认展示当前最常用的Tab而非全部平铺；表格列按场景精简。

## 三、交互流程问题

### 7. AI研判反馈操作路径不清晰

事件详情页右侧有3套操作区：

- AI研判卡片：确认/修正/拒绝
- AI处置建议：采纳/修改后执行/拒绝/转人工
- 处置动作：指派/下发限制/标记误报/接受风险/处置登记/生成摘要

**问题**：用户不知道先做哪个。是先确认AI研判，再采纳处置建议，最后点处置动作？还是可以跳过？三套操作之间没有明确的步骤引导和前置依赖提示。

**建议**：设计为**向导式流程**——Step1确认研判 → Step2选择处置 → Step3执行，而非三个并列的操作区。

### 8. 修正弹窗字段过多

`@/pages/events/event-detail.html:368-381` — 修正AI研判弹窗含6个字段（攻击手法、优先级、影响面、修正原因、是否加入样本集、样本类型），其中"样本类型"对安全运营人员来说是ML概念，不应在此暴露。

**建议**：修正弹窗只保留"修正内容+修正原因"，样本相关选项自动处理或放入高级选项折叠区。

### 9. 自动响应规则L1-L4分级理解门槛高

`@/pages/policy/auto-response-rules.html:34` — 页面副标题"L1-L4分级自动响应规则：通知、观察、软限制、强控制"。

**问题**：L1-L4是系统内部概念，用户需要记忆4个级别的含义和区别。新建规则时需选择级别，但级别选择与"是否需要审批""是否需要MFA"等安全约束的映射关系不直观。

**建议**：用"影响程度"替代抽象级别——"仅通知"→"标记观察"→"临时限制"→"强制阻断"，并在选择时直接展示该级别隐含的安全约束。

## 四、术语与概念理解问题

### 10. 专业术语未做用户层翻译

| 设计中的术语                | 用户困惑                       |
| --------------------------- | ------------------------------ |
| `detection_source`        | "检测来源"是什么意思？         |
| `ai_status: circuit_open` | 什么是熔断？                   |
| `risk_stage: tool`        | "工具能力边界确认"是什么阶段？ |
| `span_id / trace_id`      | 非开发人员不理解               |
| `RAG Prompt安全沙盒预览`  | 知识库页面中的ML术语           |
| `σ偏离度`                | 统计学术语，运营人员不理解     |
| `Token预算`               | AI成本概念，非所有用户关心     |
| `干跑验证`                | 工程术语，应叫"历史回放验证"   |

**建议**：建立术语映射表，UI层使用业务语言，技术字段放在"技术详情"折叠区。

### 11. 概念重叠导致用户混淆

- "内容安全策略" vs "高级规则项" vs "提示词防护策略"：三者都涉及内容检测，边界不清
- "风险溯源工作台" vs "风险关联分析"：都是分析风险关联，区别是什么？
- "会话风险追踪" vs "会话审计"：一个在安全监控下，一个在策略中心下，用户难以区分

**建议**：合并或明确区分。如"内容安全策略"和"高级规则项"可合并为一个页面用Tab切换；"会话风险追踪"和"会话审计"应明确标注前者是"实时监控视角"、后者是"策略合规视角"。

## 五、新用户/初级用户友好度问题

### 12. 缺少引导和空状态设计

大部分页面没有：

- 首次使用引导（如"第一步：配置内容安全基线策略"）
- 有意义的空状态提示（仅 `@/pages/policy/content-security.html:153-160`有一个空状态示例）
- 推荐配置/快速开始入口

**建议**：安全总览页增加"快速配置向导"；空状态提供"创建第一个XX"的快捷入口；关键页面增加"这是什么？"帮助气泡。

### 13. 策略配置缺少预置模板

内容安全策略、高级规则项、自动响应规则都是从零新建，没有预置模板或推荐配置。新用户不知道"一个合理的内容安全策略应该配哪些字段"。

**建议**：提供3-5个预置模板（如"基础提示词防护""严格数据防泄露""观察模式"），用户基于模板修改而非从零配置。

### 14. 页面间缺少上下文连贯性

从"安全总览"点击指标卡下钻到"事件列表"，但事件列表没有回传筛选上下文；从"人员风险分析"点击事件跳转到"事件详情"，但事件详情不知道用户是从哪个分析路径来的。

**建议**：页面跳转携带来源上下文，并在目标页提供"返回分析"的面包屑或快捷入口。

## 总结：核心问题优先级排序

| 优先级       | 问题                                 | 影响                             |
| ------------ | ------------------------------------ | -------------------------------- |
| **P0** | 事件详情页信息过载（#4）             | 核心工作流页面，直接影响运营效率 |
| **P0** | AI状态术语晦涩（#5）                 | 用户无法判断AI结果可信度         |
| **P0** | 三套操作区无流程引导（#7）           | 用户不知先做哪个操作             |
| **P1** | 安全监控导航9项平铺（#1）            | 找不到功能入口                   |
| **P1** | 策略中心按技术分类而非业务分类（#2） | 配置入口难找                     |
| **P1** | 专业术语未翻译（#10）                | 理解门槛高                       |
| **P1** | 概念重叠混淆（#11）                  | 不知该用哪个功能                 |
| **P2** | 缺少引导和模板（#12/#13）            | 新用户上手困难                   |
| **P2** | 页面间缺少上下文（#14）              | 分析链路断裂                     |
| **P2** | L1-L4分级理解门槛（#9）              | 自动响应配置困难                 |

**核心结论**：当前设计的主要矛盾是**系统功能完备但用户认知通道过窄**——设计者从系统能力出发铺陈了所有功能点，但缺少从用户工作流出发的渐进式信息组织和操作引导。建议以"安全运营人员处理一个风险事件的完整流程"为主线，重新组织核心页面的信息层级和操作步骤。
