### 1 & 2. 关于临时屏蔽部分菜单以及“监控覆盖度”缺失的影响

* **屏蔽方案**：对于 `index.html`中的“工具与权限”、“监控覆盖度”以及“租户管理”，我们可以直接在对应的 `<div class="nav-item">` 标签上添加 `nav-hidden-p0` 这个 CSS 类。这是我们原型中预设的用于隐藏 P0 阶段非核心菜单的样式，这样做可以平滑地隐藏入口，完全保留底层代码逻辑。
* **影响评估（屏蔽“监控覆盖度”）**：
  * “监控覆盖度”页面主要是全局视角的统计（例如全盘有多少应用/实例安装了探针，策略下发版本是否一致，哪些规则有冲突）。
  * 屏蔽该页面的主要影响是**管理者暂时失去了全局视角的“体检报告”**。但是，单个应用的监控情况、配置拉取状态（v18 / v17）在“应用详情”的“运行实例”和“安全概览”中依然有体现；整体的安全检测和干预流程也不依赖于这个大盘面板。因此，在初期版本中屏蔽该模块**对核心功能（风险检测与溯源处置）没有实质性影响**。

### 3. 应用详情的精简与“Skills”定位

* **页面精简**：在 `app-detail.html` 中，屏蔽“接入配置”、“监控配置”、“策略覆盖检查”是非常合理的，这让详情页的视线更聚焦于**资产现状**和**安全态势**。这可以通过在 `#appTabNav` 中隐藏对应 tab 以及 `#appTabContent` 中隐藏对应内容面板来实现。
* **Skills（技能）的归属探讨**：
  * 在现代大模型应用中，“Skills”通常指的是智能体能执行的具体功能块（如联网查询、生成图表等）。
  * 在当前的“工具与资源”（Tools & Resources）分类中，**Skills最适合被归类为“MCP Tool”或“Tool（工具）”**。
  * 如果该能力是通过标准的 MCP 协议（Model Context Protocol）暴露的服务，则归为 `MCP Tool`；如果是基于代码硬编码（如 LangChain 的 @tool 装饰器定义的函数），则直接归为 `Tool`。平台无需专门为其新增一个“Skills”大类，这样能保持概念的统一性，降低用户认知的复杂度。

### 4. 关于事件编号（Event ID）与风险编号的去留及定义

* **是否有必要保留？**：**强烈建议保留**。
  * 一旦系统上线运行，安全运营人员日常交流、提单（Jira/工单）或进行规则误报反馈时，必须有一个简短、明确的唯一标识。“那个 4 月 16 号早上 10 点代码审查助手的越界事件”这种描述在实际场景中效率极低。
  * Trace ID 或 Span ID（如 `TRC-20260416-018`）过于冗长且代表的是代码执行链路，不代表“安全工单”，两者需要解耦。
* **编号该如何定义？**（建议方案）：
  * 规则：`业务前缀 - 年份格式 - 序列号`
  * 示例：`EVT-2604-A018`
  * 释义：`EVT` 代表事件（Event），`2604` 代表 26年4月，`A`代表自动检出（区别于人工 `M`），`018` 代表当月流水号或当天流水号。

### 5. 简化风险事件列表字段

* **操作建议**：在 `event-list.html` 中，将“平台动作”和“关联 Trace / Span”两列隐藏。
* **收益**：这两个字段在列表中确实略显冗余。列表界面最重要的目的是让安全人员判断**“谁（关联对象）、什么事（类型/等级）、什么证据（证据要点）、处理的怎么样了（状态）”**。至于底层的 Trace ID 和系统干预动作，可以放在后面的“溯源”或点击“详情”后再展示，这能极大减轻列表带来的视觉负担。

### 6. 简化事件处置流程与详情页（只保留“备注”与“状态”）

当前的详情页/列表中有非常细的动作（确认、指派、下发限制、标记误报、接受风险）。如果我们要回归最简单的流程（只留“状态”和“备注”）：

* **状态定义（简化版）**：只需保留 3 个状态：`待处理` (Open)、`已忽略/误报` (Ignored)、`已处置` (Resolved)。
* **详情页（event-detail.html）修改梳理**：
  1. 移除底部的多个状态操作按钮，合并为一个 **“更新状态”** 的动作按钮。
  2. 弹窗中，只提供 `变更目标状态` (下拉单选) 和 `处置备注` (文本框) 两个输入项。
  3. 原有的“误报记录”、“接受风险审批单号”等模块全部下掉或隐藏。

### 7. 风险溯源工作台（Trace 工作台）的上下级层级讨论

* **当前痛点**：当前的 `trace-list.html` 其实是一个“列表 + 详情”一体化的视图。随着请求量增大（可能一天几十万条 Trace），把这个当做“Trace 总入口”会让页面加载非常沉重，且左侧狭窄的列表无法展示完整的过滤信息。
* **讨论结论：非常有必要增加一层上级页面**。
  * **上级页面（Trace 检索主页）**：展示一个全宽的数据表格（类似传统日志检索）。字段包含：Trace ID、关联应用、Session 时长、Tokens 消耗、风险标识、发生时间等。头部配有强大的过滤搜索。
  * **详情页面（即现在的原型主骨架）**：当用户在上一层列表点击某条 Trace ID 时，跳转或弹窗进入当前的视图，右边大面积展示“风险链路（Node 图/步骤流）”和“证据工作区”。
  * 这种设计（List -> Detail）是 Datadog / Langfuse 等成熟监控产品的标准做法，更符合“先宏观过滤，后微观查证”的分析心智。
