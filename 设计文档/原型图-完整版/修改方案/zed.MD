综合讨论

### 1. 临时屏蔽：工具与权限、监控覆盖度、租户管理

**屏蔽方案很清晰**，原型中已有先例——部分菜单用了 `nav-hidden-p0` 的 CSS class 来隐藏但保留代码，完全遵循这个模式即可：

| 模块       | 位置                                  | 屏蔽方式建议             |
| ---------- | ------------------------------------- | ------------------------ |
| 工具与权限 | 资产中心子菜单 `tool-exposure.html` | 菜单加 `nav-hidden-p0` |
| 监控覆盖度 | 资产中心子菜单 `coverage.html`      | 菜单加 `nav-hidden-p0` |
| 租户管理   | 系统管理子菜单 `tenant-list.html`   | 菜单加 `nav-hidden-p0` |

屏蔽后，资产中心可见菜单只剩：**接入应用**（主要功能），系统管理只剩：用户与权限、操作审计日志、数据采集器配置。整体导航更聚焦。

### 2. 屏蔽「监控覆盖度」对其他功能的影响评估

这一项**影响较大，需要逐处处理**：

**直接影响点：**

- `app-detail.html` 的 **stat-cards** 中有「策略覆盖 92%」卡片 → 建议一并屏蔽或折叠
- `app-detail.html` 的 Tab 列表中有 **「策略覆盖检查」tab** → 按第3点一起屏蔽
- `dashboard.html` 安全总览页很可能有覆盖度相关指标 → 需审查并替换为其他统计
- 应用详情顶部 stat-cards 中的「工具声明覆盖 78%」也属覆盖度衍生指标 → 可保留但归类为"资产完整度"，不再叫覆盖度

**间接影响：工具与权限也屏蔽了**，两个功能都屏蔽后，「工具声明覆盖」这个指标的来源也弱化了，建议把应用详情 stat-cards 里这张卡片也同步屏蔽，否则数字无处点进去查。

**结论**：屏蔽监控覆盖度 = 需要同步清理 app-detail 的 stat-cards + 该 tab + dashboard 相关区域，否则会出现「有数字但无落地页」的断链问题。

### 3. 应用详情中屏蔽的 Tab，以及 Skills 归类问题

#### 需屏蔽的 3 个 Tab：

| Tab          | 屏蔽原因                                                           |
| ------------ | ------------------------------------------------------------------ |
| 接入配置     | 展示 OTLP endpoint / 接入命令，属于运维配置，当前阶段功能未就绪    |
| 监控配置     | 采集开关、采样率、PII 规则等，属于探针端配置，当前尚无配置下发能力 |
| 策略覆盖检查 | 依赖「监控覆盖度」功能，已随之屏蔽                                 |

屏蔽后，Tab 只剩 5 个：**安全概览 / 智能体·节点 / 工具与资源 / 风险事件 / 运行实例**，结构非常清晰，且信息优先级也符合原型评审建议（安全、资产、风险、基础信息递进）。

#### Skills 的归类问题：

当前「工具与资源」tab 中，类型分为：`Tool`、`MCP Tool`、`知识库`、`外部 API`。**Skills 并没有专门出现在原型里**——结合 LangChain/Agent 的实际语义来看：

- **LangChain 的 Tool** 本质上就是 skill（比如 `crm_search`、`ticket_create`），这类工具来自 LangChain 元数据，在原型里是 `Tool` 类型
- **MCP Tool** 是通过 MCP 协议提供的工具服务，来源是 MCP 服务器声明
- **Skill** 这个词在 LangGraph / AutoGen 等框架里也指 agent 具备的能力单元，更偏向于"高阶封装的工具"

**建议的处理方式**：Skills 归入 `Tool` 类型，**来源字段写成 "agent skill 声明"**，而不是单开一个类型。原因有三：

1. 从安全监测角度，skill 和 tool 的监控逻辑是一样的（都需要观测调用、声明状态、权限边界）
2. 分太细会让类型列表混乱（已有 Tool / MCP Tool / 知识库 / 外部 API 4 种）
3. 来源字段可以区分是 LangChain 元数据、MCP 声明、还是 Agent Skill 声明，信息更精确

如果将来 skill 有独立的治理需求（比如技能版本管理），再单独拆出来也不迟。

### 4. 事件编号与风险编号：保留、删除还是统一？

这是当前**两套编号并存**的问题，需要明确：

| 编号     | 当前位置                               | 格式              | 语义                           |
| -------- | -------------------------------------- | ----------------- | ------------------------------ |
| 事件编号 | 应用详情→风险事件 tab、风险事件列表   | `EVT-2026-A018` | 一个已聚合、定级的风险事件记录 |
| 风险编号 | 同一个事件列表 `th` 也叫「事件编号」 | `EVT-2026-A018` | 实际上是同一个东西             |

**现状其实是同一个编号，只是名字叫法不统一**。原型里没有独立的「风险编号」字段，只有「事件编号」。

**建议**：

- **统一叫「事件编号」**，格式 `EVT-YYYY-XXXXX`（年份 + 5位序号），不需要两套
- **保留，不要删除**——因为编号是跨页面联动的关键锚点：
  - 应用详情的风险事件 tab 通过编号跳转详情
  - 溯源工作台通过编号反查事件
  - 告警与响应记录也会引用同一编号
  - 如果删除，这条链路就断了，只能靠 trace_id，但 trace_id 是运维维度而不是事件维度

**格式规范建议**：
`EVT-{年份}-{5位自增序号}` → 例如 `EVT-2026-00018`，去掉中间的字母前缀（A/B这种），改为纯数字序列，跨年查询更清晰。

### 5. 风险事件列表字段简化：屏蔽平台动作、关联 Trace/Span

**强烈支持简化**，当前列表 12 列太多，建议如下：

| 字段                        | 现状           | 建议                                                  |
| --------------------------- | -------------- | ----------------------------------------------------- |
| 事件编号                    | 保留           | ✅ 保留                                               |
| 发生时间                    | 保留           | ✅ 保留                                               |
| 关联对象（应用+工具）       | 保留           | ✅ 保留                                               |
| 风险等级                    | 保留           | ✅ 保留                                               |
| 风险类型                    | 保留           | ✅ 保留                                               |
| 证据要点                    | 保留           | ✅ 保留（这是核心列）                                 |
| **关联 Trace / Span** | 目前在列表显示 | **🚫 屏蔽**，移入详情页，列表太技术向           |
| 状态                        | 保留           | ✅ 保留                                               |
| **平台动作**          | 目前在列表显示 | **🚫 屏蔽**，移入详情页，用户不需要在列表看这个 |
| 负责人                      | 保留           | ✅ 保留                                               |
| 操作列                      | 保留           | ✅ 保留                                               |

简化后剩 **9 列**（含复选框），去掉 trace/span 和平台动作，列表更适合快速分诊。trace/span 信息保留在详情页和溯源工作台里，不是在列表展示的内容。

同时，**搜索筛选区的「Trace/Span」搜索框** 可以保留——这是高级用户的定向查询入口，价值在于能从 trace_id 直接找到相关事件，功能上有意义。

### 6. 简化事件处置流程：只保留备注 + 处置状态

**当前处置流程过重**，原型中有 6 个独立的处置弹窗：更新进度、指派负责人、下发限制、标记误报、接受风险、生成摘要。对于当前阶段，这套流程能落地的很少。

**建议的简化方案**：

保留核心的两个维度，合并成一个「**处置登记**」弹窗：

```
┌─────────────────────────────────┐
│  处置登记                        │
├─────────────────────────────────┤
│  处置状态  [下拉] ←—必填         │
│  ┌待确认 / 处理中 / 已处置       │
│  └误报 / 接受风险 / 已关闭       │
│                                 │
│  处置备注  [文本区] ←—必填       │
│  （填写处置过程、判断依据等）     │
│                                 │
│  [取消]          [提交]          │
└─────────────────────────────────┘
```

**风险事件详情页需要同步修改的内容**：

1. **处置动作区域**：6个按钮 → 合并为 1 个「处置登记」按钮（+ 可选的「指派」和「溯源」）
2. **事件概况字段**：去掉「平台动作」字段（已在列表里屏蔽，详情里也可以去掉），去掉「检测器」和「规则版本」（技术字段，留在证据区就够了）
3. **复核结论卡片**：目前有「误报原因」和「接受风险原因」两个字段 → 合并为一个「**处置结论**」字段，用状态区分语义
4. **处置记录 timeline**：保留，这是审计留痕的核心，每次处置登记都追加一条
5. **页面标题副标题**：去掉 `trace_id / span_id` 的直接展示，改成更用户友好的表述（trace 信息进入证据区）
6. **审计要求卡片**：可以去掉（太教条化），改为在处置登记弹窗里用 `placeholder` 自然引导

### 7. 风险溯源工作台是否需要增加一层上级页面？

**这个问题值得认真讨论，建议方向：增加，但不是简单的列表页**。

**现状分析**：
当前「风险溯源工作台」直接是一个**三栏调查布局**（Trace 列表 / 风险链路 / 证据工作区），它已经内置了左侧 Trace 列表，从功能上可以自给自足。但存在以下问题：

- 直接从侧边栏进入就是完整工作台，**没有上下文引导**，用户不知道这里展示的是什么范围的数据（什么应用？什么时间段？）
- 从应用详情或风险事件「溯源」按钮跳进来时，需要**携带上下文参数**（trace_id、app_id），但左侧列表仍然展示所有 trace，用户容易迷失
- 当左侧 trace 数量很多时，这个页面的**信息密度会很高**，不利于导航

**两种方案对比**：

| 方案                          | 描述                                                                           | 优点                                                       | 缺点                                  |
| ----------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------- | ------------------------------------- |
| A：增加上级列表页             | 新增一个 Trace 列表页作为入口，点击某条 Trace 进入当前三栏工作台（变成详情页） | 导航清晰；列表可支持搜索/过滤；工作台更专注于单 Trace 分析 | 多一层跳转；对单 Trace 调查流程更繁琐 |
| B：保持当前结构，优化现有页面 | 在现有三栏布局的搜索区加强筛选能力，左侧 Trace 列表作为导航                    | 减少跳转；工作台本身已有列表功能                           | 首次进入没有引导；上下文参数传递复杂  |

**推荐 A 方案**，理由：

1. 当前三栏工作台的左侧列表**能力太弱**（只有 4 条示例数据，没有分页、没有高级筛选），要承担入口责任需要大量改造
2. 安全分析人员的工作流通常是：**先确定调查范围（列表） → 再选定目标深入分析（详情）**，这两个步骤天然对应两个页面
3. 如果加了上级页面，当前工作台也不需要删，只需要把左侧的 trace-card 列表替换为**从上级页面跳转时的面包屑+返回按钮**即可，甚至可以在工作台保留一个精简的 trace 切换侧栏

**上级列表页建议内容**：时间范围、应用筛选、风险等级、风险类型筛选 + 一个 trace 卡片列表，每张卡展示：trace_id、关联应用、时间、风险等级、Span 数量、关联事件编号。点击进入当前工作台（作为详情页）。
