# 大模型安全监测平台原型图审查报告

**版本**：v1.1  
**日期**：2026-04-16  
**状态**：P0 原型整改依据  
**审查范围**：管理端原型图、P0 菜单收敛结果、P0 MVP 功能与页面清单

---

## 一、审查结论

当前原型已经完成 P0 菜单收敛：只在侧边栏展示 P0 相关页面，P1/P2 页面通过 `nav-hidden-p0` 做导航屏蔽，页面文件和入口配置保留不删除。

主流程方向是正确的：

```text
安全总览 -> 风险溯源工作台 -> 风险事件 -> 证据面板 -> 处置闭环
```

但原型仍存在若干会影响 P0 评审的问题，主要集中在三类：

1. **部分 P0 可见页面文案不专业**，尤其是租户、用户、审计、采集器配置页面。
2. **规则策略模块还没有达到 P0 可用标准**，检测规则配置和告警规则都缺少规则启停、版本、干跑、样本预览等能力。
3. **事件、溯源、处置记录的数据锚点还不完整**，部分页面缺少 `event_id`、`trace_id`、`span_id`、`risk_stage`、Agent、Resource、TTL、审批和回滚状态。

本报告只针对当前 P0 可见菜单提出整改建议。已屏蔽的 P1/P2 页面不作为 P0 阻塞项，除非其页面仍被 P0 链路引用。

## 四、P0 阻塞项

### 1. 系统管理类页面文案不符合企业级产品标准

涉及页面：

- `pages/system/tenant-list.html`
- `pages/system/user-list.html`
- `pages/system/audit-log.html`
- `pages/ops/collector-config.html`

问题：

- 存在戏谑化、夸张化、俚语化表达。
- 存在不适合内网客户语境的强对抗词。
- 审计日志页面存在不严谨技术表述，例如把审计日志描述为不准确的“区块链存根”。
- 采集器配置页面使用大量非专业文案，会严重影响客户对平台可信度的判断。

整改要求：

| 页面 | 必须调整 |
|---|---|
| 租户管理 | 改为标准租户、状态、套餐、资源配额、创建、冻结、恢复等表达 |
| 用户与权限 | 改为标准用户、角色、状态、MFA、禁用、强制下线等表达 |
| 操作审计日志 | 改为日志 ID、操作人、操作类型、对象、时间、结果、详情；删除不实技术声明 |
| 数据采集器配置 | 改为噪音过滤、采样策略、批量发送、心跳、队列、写入状态等表达 |

建议替换口径：

| 当前问题方向 | 建议口径 |
|---|---|
| 强制、拉闸、踢出、封锁等表达 | 冻结、恢复、禁用、强制下线、限制处置 |
| 后门、阴谋、撞库等表达 | 异常登录尝试、认证失败、权限校验失败 |
| 垃圾、发车、懵懂等表达 | 噪音数据、批次发送、恢复默认配置 |
| 夸大技术能力 | 按实际实现描述，例如“追加写入、权限控制、审计留痕” |

### 2. 检测规则配置页定位不清

涉及页面：`pages/policy/policy-list.html`

当前问题：

- 导航标签是“检测规则配置”，但页面标题和内容更像“安全策略库”。
- 页面混合采集策略、脱敏策略、处置响应规则，不利于安全运营人员理解。
- 缺少 P0 检测规则配置核心能力。
- 页面内仍存在不专业文案和强处置口径。

P0 应提供：

| 能力 | 要求 |
|---|---|
| 规则列表 | 规则 ID、名称、风险类型、等级、置信度阈值、状态、版本 |
| 启停控制 | 支持 Enable / Disable |
| 版本管理 | 展示当前版本、历史版本、变更说明 |
| 应用绑定 | 展示规则绑定的应用范围 |
| 干跑验证 | 支持选择样本 Span 进行 Dry-Run |
| 样本预览 | 展示命中证据、置信度、误报原因 |
| 命中统计 | 展示近 7/30 天命中次数、误报数、处置结果 |

整改建议：

- 将该页面重构为“检测规则配置”。
- 采集参数放到 `collector-config.html`。
- 脱敏规则可作为检测规则的一类，但应明确字段来源、动作和脱敏状态。
- 响应动作不要和检测规则混在同一个创建表单中，可通过规则绑定告警/处置策略实现。

### 3. 告警规则页功能不足

涉及页面：`pages/policy/alert-rules.html`

需要修正的判断：

- 该页面已经有 `page-header`、页面标题、副标题和“新增规则”按钮。
- 真实问题不是没有页面头，而是功能仍停留在静态表格和 toast。

P0 缺口：

| 能力 | 当前问题 |
|---|---|
| 新建规则 | 仅 toast，没有创建弹窗或表单 |
| 编辑规则 | 缺少编辑入口 |
| 条件配置 | 缺少条件树或基础条件表单 |
| 窗口聚合 | 仅文本展示，无法配置 |
| 规则测试 | “测试”按钮没有测试面板 |
| 响应动作 | 缺少动作范围、通知方式、事件创建策略 |

整改建议：

- 增加“新增/编辑告警规则”弹窗。
- 增加“测试规则”弹窗，输入样本风险事件后展示是否命中。
- P0 可先不做通知渠道配置页，但告警规则中应能展示“企业微信、短信、工单、创建事件”等动作引用。

### 4. 告警与响应记录缺少证据链路

涉及页面：`pages/events/alert-log.html`

当前问题：

- 缺少 `event_id`、`trace_id`、`span_id`。
- 无法从记录行跳转到风险事件详情或风险溯源工作台。
- “实体网元属性”仍偏服务器视角，应改为应用、Agent、工具、资源。
- 页面缺少标准 `page-header`。
- 部分提示和按钮文案仍不够专业。

P0 应调整为“告警与处置记录”，字段建议：

| 字段 | 说明 |
|---|---|
| `action_id` | 响应动作 ID |
| `event_id` | 关联风险事件 |
| `trace_id` / `span_id` | 证据锚点 |
| `app_id` / Agent / Tool | 关联对象 |
| `action_type` | 通知、限制、降级、恢复 |
| `scope` | Session、Tool、Agent、App |
| `ttl` | 生效时长 |
| `operator` | 操作人或系统 |
| `approval_id` | 审批记录 |
| `rollback_state` | 回滚状态 |

### 5. 数据采集器配置缺少采集健康

涉及页面：`pages/ops/collector-config.html`

该页面当前在 P0 菜单中可见，因此不能只作为 P1 运维页处理。P0 至少需要展示采集健康状态。

P0 应补充：

- Collector 实例在线状态
- 最近心跳时间
- Kafka / 队列积压
- ClickHouse / 存储写入状态
- OTLP 接收 QPS
- 错误率和丢弃数
- 配置版本和同步状态

采集参数配置本身可以简化，但采集健康必须存在，否则安全总览中的“采集异常应用”“监控覆盖度”缺少下钻落点。

## 五、P0 重要缺陷

### 6. 安全总览高风险排行需要拆分

涉及页面：`pages/assets/dashboard.html`

当前只有一个混合排行，应用、工具、智能体混在一起。P0 清单要求首屏能快速识别不同安全对象的风险状态。

建议改为三个独立列表：

- 高风险应用 TOP5
- 高风险工具 TOP5
- 高风险智能体 / 工作流节点 TOP5

同时建议保留近 7 天 / 30 天切换，便于评审时展示趋势视角。

### 7. 风险溯源工作台筛选条件不完整

涉及页面：`pages/monitor/trace-list.html`

P0 左侧筛选建议包含：

| 筛选项 | 当前状态 |
|---|---|
| 时间范围 | 缺失 |
| 应用 | 已有 |
| Agent / Workflow Node | 缺失 |
| 工具 / MCP | 已有 |
| 风险等级 | 已有 |
| 事件状态 | 缺失 |
| Trace ID | 已有 |

右侧证据面板建议补充：

- `risk_stage`
- `subject_type / subject_id`
- `resource_id`
- `false_positive_reason` 或误报记录入口

### 8. 风险事件详情字段不完整

涉及页面：`pages/events/event-detail.html`

当前页面已具备风险类型、等级、置信度、应用、工具、Trace / Span、检测器、规则版本和证据面板，但还缺少：

- 标准风险阶段 `risk_stage`
- 关联智能体 / 工作流节点
- 关联资源 `resource_id`
- 事件状态
- 误报原因或接受风险原因
- 处置动作的状态适配

处置动作按钮应根据事件状态变化，例如：

| 状态 | 主要动作 |
|---|---|
| New | 确认风险、标记误报 |
| Confirmed / In Progress | 下发限制、接受风险、补充说明 |
| Resolved | 关闭、回退处置 |
| False Positive | 查看误报原因、进入规则优化 |

### 9. 应用详情 Tab 顺序不符合 P0 信息优先级

涉及页面：`pages/assets/app-detail.html`

当前 Tab 顺序把“运行实例”放得过早，且缺少独立“风险事件”Tab。

建议调整为：

```text
安全概览
智能体 / 节点
工具与资源
风险事件
接入配置
运行实例
策略覆盖检查
```

运行实例是辅助信息，不应排在安全分析主体之前。

### 10. 监控覆盖度指标仍需补全

涉及页面：`pages/assets/coverage.html`

建议补充：

- 黑盒工具调用数
- 活跃 Agent 数
- 处置闭环率
- 长期零触发检测类型
- Trace 断链 TOP 应用

其中“黑盒工具调用数”和“Trace 断链 TOP 应用”对 P0 评审价值最高。

## 六、P0 可增强项

### 11. 面包屑更新不完整

涉及页面：`index.html` 及各子页面

当前不少页面未调用 `setBreadcrumb()`，切换页面后面包屑可能停留在默认值。

建议：

- P0 关键页面都调用 `setBreadcrumb()`。
- 至少覆盖安全总览、接入应用、工具与权限、监控覆盖度、风险溯源、风险事件、规则策略、系统管理四页。

### 12. 侧边栏和顶部通知数字为硬编码

涉及页面：`index.html`

当前侧边栏风险事件 Badge 和顶部通知数量是静态值。作为原型可以接受，但建议标注为“待处置事件数”，避免看起来是复制粘贴。

### 13. 工具与权限详情面板仍是静态联动

涉及页面：`pages/assets/tool-exposure.html`

点击不同工具后，目前主要只切换工具名称，右侧能力边界、关联 Agent、风险事件等仍是固定数据。

P0 可以接受静态 Mock，但建议至少同步切换：

- 能力类型
- 声明状态
- 关联 Agent 数
- 关联风险事件数
- 建议动作

### 14. 应用列表列数偏多

涉及页面：`pages/assets/app-list.html`

当前列较多，评审演示时可读性一般。建议：

- 合并 Trace / Span 统计。
- 将语言框架放入详情或二级信息。
- 保留 P0 决策字段：状态、负责人、活跃实例、Trace 完整率、工具声明、风险数、采集健康、策略覆盖。

## 九、整改后的验收标准

P0 原型整改完成后，至少应满足：

1. 左侧菜单只显示 P0 页面，已屏蔽页面仍保留文件和入口配置。
2. 所有 P0 可见页面无戏谑化、夸张化、不专业文案。
3. 页面标题、按钮、报告、审计记录使用“风险、合规、异常、越界、证据、处置、能力边界、风险链路、风险溯源”等口径。
4. 风险事件详情能展示 `risk_type`、`risk_level`、`confidence`、`risk_stage`、`trace_id`、`span_id`、Agent、Tool、Resource、证据、规则版本。
5. 告警与处置记录能跳转到风险事件详情和风险溯源工作台。
6. 规则策略能完成检测规则查看、启停、版本、干跑和样本预览的原型演示。
7. 采集器配置能展示采集健康和配置同步状态。
8. 安全总览能分别看到高风险应用、工具、智能体 / 节点。
9. 应用详情以安全概览、智能体、工具、风险事件为主，运行实例作为辅助信息。
10. 浏览器打开主原型无控制台错误，关键页面可通过主框架加载。

## 十、最终结论

这版原型主方向正确，已经从通用性能可观测性逐步转向智能体运行安全证据平台。但要进入 P0 评审，还需要优先修复系统管理文案、规则策略能力、告警与处置记录、采集健康和事件详情字段。

建议下一步不要继续扩展新页面，先完成 P0 必修项整改。整改顺序建议为：

```text
系统管理文案
  -> 检测规则配置
  -> 告警规则
  -> 告警与处置记录
  -> 采集器配置
  -> 风险事件详情
  -> 风险溯源筛选
  -> 应用详情 Tab
```
