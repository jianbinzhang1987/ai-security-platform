# 网关防护子系统分工方案

**文档版本**: v2.0  
**编制日期**: 2026年4月20日  
**文档目的**: 为网关防护子系统中"业务控制"与"安全防护"的团队分工提供决策分析  
**目标受众**: 技术决策层  
**核心议题**: 安全防护模块应由 SUP 团队统一承接，还是由 AI 安全团队独立负责  

---

## 执行摘要

### 决策问题

网关防护子系统包含两大功能域：**业务控制**（权限认证、资源授权、Token 校验）和**安全防护**（Prompt 注入检测、PII 脱敏、越狱识别、策略执行）。当前需要决定：安全防护由 SUP 团队统一承接，还是由 AI 安全团队独立负责。

### 倾向性建议

**建议采用分工模式**——SUP 团队负责业务控制插件，AI 安全团队负责安全防护模块。

核心判断依据：**安全防护交给 SUP，不是消除了风险，而是将风险转移到了一个更不适合承担它的团队**。同时，AI 安全团队需配套分阶段交付计划和兜底机制，确保"接得住"。

### 两种模式对比

| 维度 | 统一给 SUP | 分工模式 |
|------|------|------|
| 安全防护专业度 | SUP 缺 AI 安全经验，效果打折 | 专业团队持续精进 |
| 策略联动效率 | 治理系统→跨团队→SUP 排期→上线 | 治理系统→同团队→快速上线 |
| 问题责任归属 | 两个团队都不精通，容易推诿 | 责任明确，倒逼持续改进 |
| 初期投入 | 低 | 略高（需接口规范与联调） |
| 长期运维成本 | 高（跨团队返工+策略迟滞） | 中等（独立迭代+边界清晰） |

## 零、团队能力与交付保障

> 本节直面核心顾虑：AI 安全团队是否有能力承接安全防护模块？

### 0.1 现有能力盘点

| 能力维度 | 现状 | 说明 |
|------|------|------|
| AI 安全检测规则 | ✅ 已积累 | 已有 Prompt 注入、PII 识别、敏感指令等检测规则库 |
| 策略编排与下发 | ✅ 已实现 | 统一策略中心已设计完成，支持策略发布状态机和下发机制 |
| 治理系统 | ✅ 自研 | AI 安全治理子系统由本团队自研，策略→防护链路天然贯通 |
| Higress 插件开发 | ⚠️ 需预研 | 团队有网关开发经验，Higress Go 插件模式需 1-2 周技术预研 |
| 语义级检测模型 | ⚠️ MVP 阶段复用 | MVP 阶段采用规则引擎+第三方检测 API，不依赖自研重模型 |

### 0.2 分阶段交付计划

```
阶段 1（2 周）: 规则级防护上线
  ├─ 关键词黑名单 + 正则匹配 + 基础 PII 脱敏
  ├─ 复用 Higress 内置 WAF 能力 + 自定义规则
  └─ 交付标准: 拦截已知攻击模式，误报率 < 5%

阶段 2（2 周）: 策略联动上线
  ├─ 对接统一策略中心，接收治理系统下发的策略
  ├─ 支持策略灰度发布和版本管理
  └─ 交付标准: 策略从治理系统到网关生效 < 5 分钟

阶段 3（持续迭代）: 语义级防护增强
  ├─ Prompt 注入语义检测、越狱识别
  ├─ 可选: 接入第三方检测 API（如阿里绿网等），降低自研压力
  └─ 交付标准: Prompt 注入检出率 > 90%，持续优化至 > 95%
```

每个阶段独立交付、独立验证，领导可看到阶段性成果，不必一次性押注。

### 0.3 兜底机制

```
1. 阶段评估机制
   阶段 1 交付后评估: 若检出率 < 80%，启动 SUP 协助方案

2. 第三方检测兜底
   语义级检测可接入商业 API，不依赖团队自研模型能力

3. 策略规则可迁移
   若后续决定转交 SUP，策略规则和检测逻辑可标准化导出，不产生锁定
```

## 一、方案架构概览

### 1.1 系统分层

> 边界原则引自系统全景图：SUP 管"谁能用、能用什么资源"；安全平台管"用了以后是否安全、是否越权、如何处置和审计"。

```
┌───────────────────────────────────────────┐
│  L5: AI 安全治理子系统（AI安全团队）        │
│  ├─ 风险评估引擎                          │
│  ├─ 策略编排与下发                        │
│  ├─ 告警与处置                           │
│  └─ 审计与合规                           │
└───────────────────────────────────────────┘
             ▲                ▼
             │ 策略下发         │ 事件回调
             │                │
┌───────────────────────────────────────────┐
│  L2: 网关防护子系统                        │
│                                          │
│  ┌─────────────────┐  ┌─────────────────┐│
│  │  业务控制插件    │  │  安全防护模块   ││
│  │  (SUP团队)      │  │  (AI安全团队)   ││
│  │ ├─ Token认证    │  │ ├─ Prompt检测  ││
│  │ ├─ 权限决策     │  │ ├─ PII脱敏    ││
│  │ ├─ 资源授权     │  │ ├─ 越狱识别   ││
│  │ └─ 权限上下文   │  │ ├─ MCP审计    ││
│  │   传递         │  │ └─ 实时处置   ││
│  └─────────────────┘  └─────────────────┘│
│        ▲ 权限判决          ▲ 安全检测结果
│        │ + 用户上下文      │ + 处置决策
└───────────────────────────────────────────┘
                 ▲
                 │ OpenAPI Token
         ┌───────┴──────────┐
         │  客户请求        │
         └──────────────────┘
```

### 1.2 Higress 双插件部署架构

两个功能域在 Higress 上以独立插件形态部署，实现开发、部署、发版三独立：

```
请求入站
  │
  ▼
┌──────────────────────────────────────────────┐
│  Higress 网关                                │
│                                              │
│  ① SUP 业务控制插件 (优先级: 高)              │
│     ├─ Token 校验、权限判决                   │
│     ├─ 将 user_context 写入请求 Header        │
│     └─ 权限不通过直接拒绝                      │
│                    │                          │
│                    ▼ (权限通过后)              │
│  ② AI 安全防护插件 (优先级: 中)               │
│     ├─ 读取 Header 中的 user_context          │
│     ├─ Prompt 注入检测 / PII 脱敏 / 越狱识别  │
│     └─ 处置: 放行 / 阻断 / 脱敏 / 降级        │
│                    │                          │
│                    ▼ (安全通过后)              │
│  ③ 转发至后端模型 / MCP / Agent               │
│                                              │
│  响应出站                                     │
│  ④ AI 安全防护插件: 输出审查                   │
│     ├─ 输出内容安全检测                        │
│     └─ 处置: 放行 / 脱敏 / 降级 / 阻断         │
└──────────────────────────────────────────────┘

关键设计:
  - 两个插件独立开发、独立部署、独立发版
  - 通过请求 Header 传递上下文 (X-User-Id, X-Org-Id, X-Roles 等)
  - 执行顺序由 Higress 插件优先级配置决定
  - 任一插件异常不影响另一个插件运行 (熔断隔离)
  - 安全防护插件不可用时 fallback 为仅业务控制放行 + 告警
```

### 1.3 数据流向

```
请求入站
  │
  ├─→ SUP 业务控制插件: 权限检查
  │   返回: { allow: true/false, user_context: {...} }
  │   (user_context 通过 Header 传递给下游插件)
  │
  ├─→ AI 安全防护插件: 语义安全检测
  │   - Prompt注入检测
  │   - PII扫描+脱敏
  │   - 敏感指令过滤
  │   - MCP参数校验
  │   返回: { risk_level: HIGH/MEDIUM/LOW, action: ALLOW/BLOCK/MASK/... }
  │
  ├─→ 执行处置动作
  │   - 拦截 / 脱敏 / 放行 / 降级
  │
  ├─→ 后端模型/MCP/Agent 执行
  │
  ├─→ 响应出站: 输出安全审查
  │   - 输出内容检测 / 脱敏 / 降级
  │
  ├─→ 上报审计日志 → OTel Collector
  │
  └─→ AI安全治理系统: 风险评估与策略反馈

异常回退:
  - 安全防护插件不可用 → 仅业务控制放行 + 上报告警
  - 业务控制插件不可用 → 请求拒绝 (权限不可降级)
```

## 二、职责分工详解

### 2.1 SUP 团队职责（业务控制插件）

#### 核心职能

| 职能项 | 具体内容 | 说明 |
|------|------|------|
| **OpenAPI 认证** | 解析并验证 Token | 标准的 API Key / JWT 校验 |
| **权限决策** | 查询权限系统，判断"用户能否访问资源" | 调用 SUP 权限评估 API |
| **资源授权** | 下发用户可访问的资源清单 | model_ids / mcp_ids / agent_ids 等 |
| **用户上下文传递** | 将 user_id / org_id / roles 等传给下游 | 用于审计和成本归属 |
| **权限缓存管理** | 在网关层缓存权限结果 | 降低对 SUP 后端的调用压力 |
| **权限变更同步** | 权限系统更新后，实时同步到网关 | 保证权限决策的即时性 |

#### 关键责任

- ✅ 权限系统的真实源头
- ✅ 确保"谁能访问什么"的决策正确性
- ✅ 提供清晰的权限判决接口
- ❌ 不参与安全防护的技术决策

#### 成功指标

- 权限判决准确率 > 99.9%
- API 响应延迟 < 50ms
- 权限更新同步时间 < 5 分钟

---

### 2.2 我们团队职责（安全防护模块 + 治理系统）

#### L2 网关层职能（安全防护模块）

| 职能项 | 具体内容 | 说明 |
|------|------|------|
| **Prompt 注入检测** | 实时识别 Prompt 注入、越狱尝试 | 规则+模型混合检测 |
| **PII 扫描与脱敏** | 扫描请求中的个人隐私信息并脱敏 | 本地端侧脱敏，数据不出进程 |
| **敏感指令过滤** | 拦截高危指令（如文件删除、系统命令） | 基于黑名单和启发式规则 |
| **MCP 调用审计** | 校验 MCP 工具调用的参数合法性 | 参数类型、范围、权限验证 |
| **输出安全审查** | 对模型输出进行安全检测和处置 | 输出脱敏、降级、阻断 |
| **实时处置动作** | 根据检测结果执行阻断/脱敏/放行 | 毫秒级响应，不影响用户体验 |
| **审计日志上报** | 将所有请求的安全检测结果上报到 OTel | 用于后续分析和审计 |
| **策略引擎执行** | 执行来自治理系统的安全策略 | 对接统一策略中心，实时下发、灰度发布、版本管理 |

#### L3 治理系统职能（安全治理子系统）

| 职能项 | 具体内容 | 说明 |
|------|------|------|
| **风险评估** | 分析审计日志，识别异常行为和风险模式 | 深度检测，支持异步处理 |
| **策略编排** | 根据风险等级，编排和优化检测规则 | 条件+动作的编排引擎 |
| **策略下发** | 将策略动态下发到网关防护模块 | 支持灰度、版本管理、自动回滚 |
| **告警生成** | 触发安全告警并下发通知 | 邮件、钉钉、企业微信等 |
| **处置建议** | 为每个安全事件提供人工处置建议 | 支持阻断、观察、忽略等决策 |
| **审计报表** | 生成合规审计报表和安全仪表盘 | 支持按租户、应用、威胁类型维度统计 |
| **技术赋能** | 输出新型攻击的防护模型供防护模块使用 | 持续迭代和优化 |

#### 关键责任

- ✅ AI 语义安全检测的核心专家
- ✅ 安全防护的快速迭代和优化
- ✅ 独立拥有防护模块的代码和技术决策权
- ✅ 与治理系统的紧密协同（同团队，无跨团队理解偏差）
- ❌ 不参与业务权限的决策

#### 成功指标

- Prompt 注入检出率 > 95%（阶段 3 达成，阶段 1 目标 > 80%）
- PII 脱敏准确率 > 99%
- 网关防护延迟 < 100ms
- 策略更新到生效时间 < 5 分钟

## 三、方案对比分析

### 3.1 分工模式 vs 统一模式

#### 分工模式

##### 优势

| 优势项 | 说明 |
|------|------|
| **安全防护专业度** | AI 安全团队持续积累检测规则与防护经验，避免防护能力成为两个团队都不精通的灰色地带 |
| **策略联动效率** | 治理系统与防护模块同属一个团队，策略从发现风险→设计防护→上线生效无跨团队理解偏差 |
| **安全响应速度** | 新型攻击出现时，安全策略可独立快速上线，缩短用户风险暴露期 |
| **责任归属清晰** | 安全防护出问题，责任明确在 AI 安全团队，无法推诿，倒逼持续改进 |
| **架构一致性** | 与"探针端+治理系统"保持一致的分工模式，架构清晰可维护 |
| **独立发版** | 安全防护插件独立开发部署，不依赖 SUP 发版周期 |

##### 劣势

| 劣势项 | 说明 | 缓解措施 |
|------|------|------|
| **团队交付压力** | 需要投入人力承接安全防护模块，团队力量需保障 | 分阶段交付，MVP 先规则级后语义级；第三方 API 兜底 |
| **集成耦合** | 依赖 SUP 的权限接口，需要联合测试 | 定义清晰的接口规范，自动化测试覆盖 |
| **接口维护** | 需要与 SUP 维护权限数据交互接口 | 版本化接口，向后兼容 |
| **联合调试** | 排查问题时需要跨团队协作 | 建立联合测试环境，共享日志系统 |
| **性能协议** | 需要与 SUP 约定权限决策的响应时间 | SLA 约定：< 50ms |

##### 成本投入

```
初期投入:
  • 接口规范设计: 2-3 天
  • 集成测试用例: 1-2 周
  • 跨团队文档: 3-5 天
  总计: 3-4 周

运维成本:
  • 独立发版、监控: 中等
  • 跨团队沟通: 低（明确分工后）
  • 问题排查: 低（边界清晰）
```

#### 统一给 SUP 模式

##### 优势

| 优势项 | 说明 |
|------|------|
| **集成简单** | 一个团队维护全链路，不需要跨团队交互 |
| **初期投入低** | 不需要接口规范设计和联调 |
| **文档一致** | 避免多个团队维护文档导致的混乱 |

##### 劣势

| 劣势项 | 说明 | 影响程度 |
|------|------|------|
| **SUP 同样缺 AI 安全人才** | SUP 擅长权限认证，不擅长 Prompt 注入检测、PII 语义识别，安全防护效果打折 | 🔴 严重 |
| **策略联动成本更高** | 治理系统由 AI 安全团队开发，SUP 做防护模块→策略下发需跨团队联调，理解偏差风险大 | 🔴 严重 |
| **新型攻击响应依赖 SUP 排期** | 安全团队发现风险后，需推动 SUP 修改防护规则，沟通链路长 | 🟠 严重 |
| **SUP 承载压力更大** | SUP 同时承揽业务+安全两大职能，业务控制和安全防护都可能顾此失彼 | 🟠 严重 |
| **防护规则仍依赖安全团队提供** | SUP 无法独立判断防护规则的有效性，最终仍需 AI 安全团队输出规则，实质上并未减少安全团队工作量 | 🟠 严重 |
| **版本管理混乱** | 一个插件混合业务控制和安全防护两个功能域，版本兼容性和回滚困难 | 🟡 中等 |
| **反复返工** | 治理系统发现防护效果问题后，需跨团队推动 SUP 修改，返工周期长 | 🟡 中等 |

##### 隐性成本

```
统一模式的隐性成本:
  • 治理系统发现风险后，需跨团队推动 SUP 修改防护规则，沟通成本高
  • SUP 对 AI 安全场景理解不足导致的返工成本
  • 安全事件响应延迟导致的用户信任损失
  • 防护规则仍依赖安全团队提供，实质上安全团队工作量未减少
```

## 四、关键风险与规避

### 4.1 如果将安全防护完全交给 SUP，会存在的 5 大风险

#### 风险 1：AI 安全能力衰退（最严重）⚠️ 致命

**现象**:
- 团队核心成员逐步失去对防护模块的理解
- 新型攻击出现时，反应缓慢

**示例场景**:
```
第 3 个月: 用户反馈 PII 脱敏效果不理想
  ├─ 你们说: "这是网关防护的问题，得问 SUP"
  ├─ SUP 说: "我们按标准做的，但 AI 场景比较复杂..."
  └─ 结果: 问题在两个团队间反复沟通，用户体验恶化

第 6 个月: 出现新型 Prompt 注入
  ├─ 你们的治理系统检测到了
  ├─ 需要下发新的防护规则
  ├─ SUP 说: "我们需要排期，预计 2 周后有版本"
  └─ 结果: 用户暴露在风险中 2 周
```

**规避方案**: 采用分工模式，安全防护完全由你们掌控

---

#### 风险 2：标准化方向错误⚠️ 严重

**现象**:
```
SUP 的思维模式（传统网关）:
  请求 → API Key 检查 → 通过/拒绝 → 返回
  ✅ 二值决策，简单清晰

AI 安全防护的需求（语义级）:
  请求 → Token 识别 → Prompt 分析 → 风险评分
       → 打分/脱敏/阻断/降级多种策略
  ✅ 多值决策，需要精细化调优
```

**后果**:
- PII 脱敏采用"通过/拒绝"二值逻辑，无法微调
- 误报率高达 20%+，用户投诉频繁
- 难以应对企业特定的敏感信息格式

**规避方案**: 采用分工模式，由专家团队设计防护标准

---

#### 风险 3：策略更新迟滞⚠️ 严重

**现象**:

| 场景 | 独立维护（分工模式） | 统一给SUP（风险模式） |
|------|------|------|
| 发现新型攻击 | 1 小时 | 1 小时 |
| 分析 & 设计防护 | 2-4 小时 | 2-4 小时 |
| 编码 & 测试 | 4-8 小时 | 4-8 小时 |
| 等待 SUP 排期 | 0 | 3-5 天 |
| SUP 开发 | 0 | 1-2 周 |
| 测试 & 发版 | 2-4 小时 | 2-4 小时 |
| **总用时** | **1-2 天** | **1-2 周** |
| **风险暴露时间** | 低 | 高 |

**规避方案**: 采用分工模式，防护策略由你们快速迭代

---

#### 风险 4：接口碎片化和版本管理混乱⚠️ 中等

**现象**:

如果 SUP 同时维护"业务控制"和"安全防护"两个功能，版本号的含义会变得混乱：

```
Higress 版本 v2.5.0:
  ├─ 更新了什么？
  │  ├─ API Key 认证逻辑（业务控制）
  │  ├─ PII 脱敏规则（安全防护）← 这两个是不同的功能域
  │  └─ Token 配额算法（业务控制）
  │
  └─ 对应我的治理系统 v1.2.0 吗？
      ├─ 需要调用哪个 API？
      ├─ 新增了什么字段？
      ├─ 兼容老版本吗？
      └─ 能回滚吗？
```

**后果**:
- 版本兼容性文档难以维护
- 升级时容易踩坑
- 回滚困难

**规避方案**: 采用分工模式，保持版本设计的清晰性

---

#### 风险 5：职责混淆导致问题甩皮球⚠️ 中等

**现象**:

```
Prompt 注入被绕过 ← 到底是谁的问题？

场景 A: 防护规则太宽松
  你们说: "这是网关防护的问题，应该由 SUP 改规则"
  SUP 说: "我们按你们给的规范做的，应该是规范本身有问题"
  结果: 推诿 1-2 周

场景 B: 权限决策导致安全隐患
  SUP 说: "我们的权限决策是对的，安全防护没有生效"
  你们说: "我们的防护是对的，问题在于权限上下文传递有误"
  结果: 问题在两个团队间踢皮球
```

**后果**:
- 用户安全事件响应缓慢
- 双方士气低落
- 用户满意度下降

**规避方案**: 采用分工模式，职责边界清晰，快速定位问题

### 4.2 分工模式中的潜在风险及规避

#### 风险A：接口变更导致不兼容

**规避措施**:
```
1. 版本化接口设计
   GET /sup/api/v1/authz/check    ← 版本号在 URI 中
   GET /sup/api/v2/authz/check    ← 新版本独立 URI

2. 向后兼容性承诺
   新增字段采用可选方式，默认值不改变行为
   
3. 弃用计划
   新版本发布后，给 6 个月过渡期
   发布弃用通知，给团队充足的升级时间
```

#### 风险 B：性能下降（权限查询延迟）

**规避措施**:
```
1. 本地缓存: 在网关层缓存权限结果，TTL = 5 分钟
2. 异步预热: 在空闲时段预加载常用权限
3. SLA 约定: 权限查询响应时间 < 50ms
4. 熔断保护: 权限服务不可用时，使用本地缓存 fallback
```

#### 风险 C：两个团队间的沟通成本

**规避措施**:
```
1. 建立联合工作组
   - 每周一次技术同步会议（15 分钟）
   - 明确的问题上报和解决流程

2. 共享日志与监控
   - 两个团队共享 ELK 日志系统
   - 设置联合告警规则

3. 定期架构评审
   - 每月一次分工评审
   - 评估是否需要调整分工边界
```

## 七、决策建议

### 7.1 对领导层的建议

#### 结论

**强烈推荐采用分工模式**。虽然初期投入略高，但长期价值明显：

1. **保留团队的核心竞争力** - AI 安全防护是你们的差异化品牌
2. **加快防护迭代速度** - 新型威胁可在 1-2 天内得到防护，而不是 2 周
3. **降低长期运维成本** - 职责边界清晰，问题定位和修复更快
4. **为产品线扩展打基础** - 防护模块可复用于其他 AI 产品

#### 风险成本分析

| 指标 | 初期投入 | 运维成本（年） | 机会成本（统一方案）| 总成本 |
|------|------|------|------|------|
| 分工模式 | 4-5 周 | 中等 | 0 | **低** |
| 统一模式 | 0 周 | 高 | 5-10 倍投入 | **极高** |

**建议决策**: 采用分工模式

## 八、附录：常见问题 FAQ

### Q1: 如果两个团队的接口不兼容怎么办？

**A**: 
- 前期通过严格的接口评审来避免
- 后期通过版本化设计来保证向后兼容
- 建立问题快速解决机制（最晚 24 小时响应）

### Q2: 安全防护和业务控制的边界会不会模糊？

**A**: 
建立明确的判断标准：

| 场景 | 归属 |
|------|------|
| "这个用户被授权访问这个资源吗？" | SUP 业务控制 |
| "这个请求的内容有没有安全风险？" | 我们安全防护 |
| "这个 MCP 工具调用的参数是否合法？" | 我们安全防护 |
| "这个用户的 Token 是否有效？" | SUP 业务控制 |
| "这个 Prompt 是否包含注入攻击？" | 我们安全防护 |

### Q3: 会不会因为分工导致性能下降？

**A**: 
- 权限查询延迟 < 50ms（通过本地缓存）
- 安全防护处理 < 100ms（实时规则匹配）
- 总网关延迟仍在 200ms 以内

### Q4: 为什么不让 SUP 也做安全防护的部分工作呢？

**A**: 
因为：
1. **领域专业性** - AI 安全需要深度的LLM安全知识
2. **快速迭代** - 新型威胁出现时需要快速响应，不能等发版周期
3. **品牌差异化** - 这是你们团队的核心竞争力

### Q5: 分工模式下如何应对突发的安全事件？

**A**: 
- 建立应急响应 SLA：发现威胁 → 1 小时内部署防护规则
- 双团队应急值班机制
- 提前建立应急沟通通道（钉钉群、电话等）
