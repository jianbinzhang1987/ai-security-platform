## 二、对SUP团队的具体诉求

### 诉求 1：提供标准化权限决策接口

#### 为什么需要

- 我们需要在网关层实时调用权限API，判断"用户是否有权访问这个资源"
- 权限决策的准确性直接影响安全防护的有效性

#### 接口需求

```yaml
API 端点: 
  GET /sup/api/v1/authz/check

请求参数:
  - token (string): OpenAPI Token
  - resource_type (string): 'model' | 'mcp' | 'agent' | 'skill'
  - resource_id (string): 具体资源ID
  - operation (string): 'call' | 'read' | 'execute'

响应结构:
  {
    "allow": boolean,
    "reason": string,                    # "authorized" | "insufficient_permission" | "token_expired"
    "user_context": {                    # 权限通过时必返回
      "user_id": string,
      "org_id": string,
      "tenant_id": string,
      "roles": string[],
      "permission_level": number
    },
    "metadata": {
      "resource_name": string,
      "resource_owner": string,
      "last_checked_at": timestamp
    }
  }

性能要求:
  ✅ 响应时间 < 50ms (P95)
  ✅ 可用性 > 99.9%
  ✅ 支持本地缓存 (TTL建议 5 分钟)
```

#### 验收标准

- [ ] 接口文档完整，字段定义清晰
- [ ] 支持自动化测试覆盖
- [ ] 性能基准测试通过
- [ ] 向后兼容性承诺文档

### 诉求 2：提供用户上下文传递机制

#### 为什么需要

- 我们的安全防护模块需要了解"请求来自哪个用户、哪个组织、什么角色"
- 用于后续的审计、风险评分、策略差异化执行

#### 传递方式需求

```yaml
通过请求 Header 传递上下文:

Header 字段:
  - X-User-Id: string
  - X-Org-Id: string
  - X-Tenant-Id: string
  - X-Roles: string (逗号分隔)
  - X-Permission-Level: number
  - X-Auth-Time: timestamp

示例:
  X-User-Id: user_123
  X-Org-Id: org_456
  X-Tenant-Id: tenant_789
  X-Roles: user,developer,auditor
  X-Permission-Level: 3
  X-Auth-Time: 2026-04-20T10:30:00Z

Header 特性要求:
  ✅ 由SUP业务控制插件写入
  ✅ 下游安全防护插件可读取
  ✅ 传递给后端日志系统用于审计
  ✅ 不包含敏感信息（如Token本身）
```

#### 验收标准

- [ ] Header 传递方案文档
- [ ] 字段规范定义
- [ ] 安全性评审（不泄露敏感信息）
- [ ] 集成测试用例

### 诉求 3：权限变更实时同步机制

#### 为什么需要

- 网关层需要缓存权限结果以提升性能
- 用户权限变更后，需要快速同步到网关

#### 同步机制需求

```yaml
同步方式选项（至少支持一种）:

方案 A: 事件驱动（推荐）
  - SUP权限系统变更时主动推送事件
  - 事件格式: 
    {
      "event_type": "permission_changed",
      "user_id": string,
      "org_id": string,
      "timestamp": timestamp,
      "changes": {
        "added_resources": [],
        "removed_resources": [],
        "updated_permissions": []
      }
    }
  - 推送目标: 我们网关的webhook端点

方案 B: 拉取 + 订阅（备选）
  - 提供权限列表批量查询API
  - 我们定期（如每5分钟）拉取全量或增量权限变更
  - API格式:
    GET /sup/api/v1/permissions/changes?since={timestamp}

同步时间要求:
  ✅ 权限变更到网关生效 < 5 分钟
  ✅ 缓存TTL建议值: 5-10 分钟
  ✅ 异常情况下能快速清空缓存
```

#### 验收标准

- [ ] 选择同步方案并文档化
- [ ] 事件格式规范定义
- [ ] 容错机制说明（失败重试、部分失败处理）
- [ ] 监控指标定义

  - 变更前至少提前 3 个月通知

### 诉求 5：接口可靠性与容错保障

#### 为什么需要

- 网关层权限查询故障会影响全链路
- 需要明确的SLA承诺和容错机制

#### 容错需求

```yaml
SLA 承诺:
  ✅ 可用性: > 99.9% (年度)
  ✅ 响应时间: < 50ms (P95)
  ✅ 错误率: < 0.1%

容错机制:
  1. 网关层本地缓存
     - 缓存最近N个用户的权限结果
     - TTL = 5 分钟
     - SUP 服务不可用时使用缓存结果

  2. 熔断保护
     - 当SUP错误率 > 5% 时自动降级
     - 使用缓存或安全默认值 (DENY)
     - 自动恢复机制

  3. 重试策略
     - 支持幂等的失败重试
     - 建议重试次数: 2-3 次
     - 指数退避策略

  4. 告警机制
     - SUP API 响应时间超过阈值时告警
     - 错误率突增时告警
     - 主动通知两个团队协调

降级方案:
  ┌─ SUP 权限查询成功 ──→ 使用权限结果
  │
  ├─ SUP 权限查询失败（缓存命中）──→ 使用缓存结果 + 告警
  │
  └─ SUP 权限查询失败（缓存未命中）──→ 安全降级 (DENY) + 告警
```

#### 验收标准

- [ ] SLA 承诺书
- [ ] 容错设计文档
- [ ] 降级测试覆盖
- [ ] 告警规则定义

### 诉求 6：安全性设计审核

#### 为什么需要

- 权限决策API是安全关键路径
- 需要保证API本身的安全性

#### 安全需求

```yaml
认证与授权:
  ✅ 权限API必须有自己的认证机制（非客户Token）
  ✅ 网关使用专用Service Account访问权限API
  ✅ Service Account权限最小化原则

传输安全:
  ✅ 必须使用 HTTPS / TLS
  ✅ 不允许在Header中传递明文密钥
  ✅ 支持 mTLS（如有要求）

数据安全:
  ✅ 权限API不得返回敏感信息（如Token、密钥等）
  ✅ 日志中不得记录完整的权限决策细节（隐私考虑）
  ✅ 缓存数据必须有加密存储选项

审计:
  ✅ 所有权限查询都应被记录（审计日志）
  ✅ 支持查询审计日志
  ✅ 异常查询行为应有告警
```

#### 验收标准

- [ ] 安全设计文档
- [ ] 认证方案说明
- [ ] 安全测试报告
- [ ] 审计机制说明
