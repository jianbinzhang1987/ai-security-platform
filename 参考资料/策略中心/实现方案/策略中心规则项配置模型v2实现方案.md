# 策略中心规则项配置模型 v2 实现方案

**文档编号**：AGENTSEC-POLICY-IMPL-RULE-V2  
**版本**：v1.0 | **日期**：2026-04-20 | **状态**：实现方案稿  
**适用范围**：统一策略中心 / 规则项管理 / 策略包管理 / 绑定与下发  
**关联文档**：`合并方案/原型修改方案.md`

## 1. 方案结论

当前原型中的规则项模型可用于 `MVP`，但不足以支撑“灵活定义规则”的目标。

现有规则项字段主要为：

- `规则项名称`
- `类型`
- `执行面`
- `Hook Point`
- `匹配条件`
- `动作`
- `优先级`
- `状态`

这套结构只能覆盖“简单显式规则”，例如：

- 关键词匹配
- 基础正则匹配
- 简单阻断 / 告警 / 脱敏动作

但无法充分表达以下能力：

- 内容安全中的分类模型、风险分值与阈值
- 数据防泄露中的字段识别、字典匹配、脱敏模板
- 工具管控中的参数约束、审批流、频次控制
- 访问控制中的主体 / 资源 / 动作 / 条件组合
- 采集与审计中的采样率、保留字段、时间窗口、灰度策略

因此，本方案建议将规则配置模型升级为：

**规则项 + 规则实现 + 策略包 + 绑定与下发**

其中：

- `规则项` 负责表达业务语义
- `规则实现` 负责表达技术执行方式
- `策略包` 负责组合与版本化发布
- `绑定与下发` 负责面向接入应用生效

## 2. 核心判断

### 2.1 是否需要按类型拆不同页面

不建议为每一种策略类型单独维护一套完全独立的页面。

原因：

- 独立页面会导致规则维护入口分散
- 用户难以统一查看、搜索和复用规则项
- 后续新增策略类型时页面成本过高

### 2.2 是否可以完全使用一套通用表单

也不建议只保留一套完全通用的规则表单。

原因：

- 各类规则的配置差异过大
- 单一的“匹配条件 + 动作”无法覆盖复杂场景
- 会迫使用户把复杂逻辑塞进自由文本，难以校验和复用

### 2.3 推荐方案

推荐采用：

**统一规则项入口 + 类型化子表单**

即：

- 统一的规则项列表页
- 统一的规则项编辑页
- 在编辑页内部根据“规则类型”切换不同配置区

这是兼顾统一入口、扩展性和表达能力的最稳方案。

## 3. 模型分层

### 3.1 规则项

规则项是业务语义层对象，用来表达“要防什么、发现后怎么处理”。

典型示例：

- Prompt 注入检测
- 手机号脱敏
- 高危工具审批
- 未备案域名外联限制

建议字段：

| 字段 | 说明 |
|---|---|
| `rule_id` | 规则项唯一标识 |
| `name` | 规则项名称 |
| `rule_type` | 规则类型 |
| `target` | 执行面：网关 / 探针 / 双端预留 |
| `hook_point` | 执行点 |
| `scope` | 适用范围 |
| `priority` | 优先级 |
| `status` | 启用 / 停用 |
| `implementation_type` | 规则实现方式 |
| `action_policy` | 命中后的动作策略 |
| `remark` | 备注 / 变更说明 |

### 3.2 规则实现

规则实现是技术执行层对象，用来表达“这条规则如何被执行”。

它不应与策略包混淆，也不建议继续命名为“规则包”。

推荐命名：

- 面向产品：`检测能力`
- 面向系统：`规则实现`

本方案中统一使用：

**规则实现**

建议字段：

| 字段 | 说明 |
|---|---|
| `impl_id` | 实现唯一标识 |
| `implementation_type` | 显式规则 / 阈值规则 / 模型规则 / 外部服务规则 / 流程规则 |
| `impl_config` | 具体参数 |
| `version` | 实现版本 |
| `fallback_action` | 实现失败时兜底动作 |
| `timeout_ms` | 调用超时 |
| `owner` | 维护人 |

### 3.3 策略包

策略包是发布与下发层对象，用来组合多条规则项并形成版本快照。

建议字段：

| 字段 | 说明 |
|---|---|
| `package_id` | 策略包 ID |
| `name` | 策略包名称 |
| `description` | 用途说明 |
| `rule_refs` | 关联的规则项集合 |
| `current_version` | 当前版本 |
| `status` | 草稿 / 灰度 / 已发布 / 已废弃 |

### 3.4 绑定与下发

绑定与下发负责将某个策略包版本生效到接入应用。

建议字段：

| 字段 | 说明 |
|---|---|
| `app_id` | 接入应用 ID |
| `package_id` | 绑定的策略包 |
| `package_version` | 当前生效版本 |
| `bind_status` | 已绑定 / 灰度中 / 已下发 / 部分失败 |
| `last_sync_at` | 最近同步时间 |

## 4. 规则类型设计

### 4.1 内容安全

用于识别和处置提示注入、越权指令、有害内容等风险。

建议专属字段：

| 字段 | 说明 |
|---|---|
| `content_target` | prompt / response / tool_input / tool_output |
| `risk_category` | 注入 / 越权 / 暴力 / 色情 / 政治 / 自定义 |
| `detect_mode` | 关键词 / 正则 / 分类模型 / 外部服务 |
| `threshold` | 风险阈值 |
| `prompt_template` | 命中后的提示文案 |

### 4.2 数据防泄露

用于识别敏感字段并执行脱敏、拦截或告警。

建议专属字段：

| 字段 | 说明 |
|---|---|
| `data_target` | 输入 / 输出 / 工具结果 |
| `sensitive_type` | 手机号 / 身份证 / 邮箱 / API Key / 自定义 |
| `detect_mode` | 正则 / NER 模型 / 字典 |
| `mask_template` | 脱敏模板 |
| `whitelist_condition` | 白名单条件 |

### 4.3 工具管控

用于限制高风险工具调用或参数越界。

建议专属字段：

| 字段 | 说明 |
|---|---|
| `tool_scope` | 指定工具 / 工具组 / 全部高危工具 |
| `param_constraints` | 参数约束 |
| `frequency_limit` | 调用频次限制 |
| `approval_policy` | 审批策略 |
| `degrade_action` | 超限后的降级动作 |

### 4.4 访问控制

用于控制主体访问特定资源的权限。

建议专属字段：

| 字段 | 说明 |
|---|---|
| `subject_scope` | 应用 / 智能体 / 节点 / 角色 |
| `resource_scope` | 知识库 / 数据源 / MCP / API |
| `operation` | read / write / execute / export |
| `condition_expr` | 生效条件表达式 |
| `decision` | allow / deny / challenge |

### 4.5 采集控制 / 审计控制

用于控制采样、字段保留、审计级别和存储策略。

建议专属字段：

| 字段 | 说明 |
|---|---|
| `sample_rate` | 采样率 |
| `retain_fields` | 保留字段 |
| `mask_fields` | 脱敏字段 |
| `audit_level` | 审计级别 |
| `window_policy` | 时间窗口策略 |

## 5. 规则实现方式

规则实现方式用于表达规则背后的技术能力，至少支持以下五类。

### 5.1 显式规则

适用于：

- 关键词
- 正则
- 枚举匹配
- 黑白名单
- 简单表达式

建议参数：

- 字段选择器
- 运算符
- 比较值
- AND / OR / NOT 组合

### 5.2 阈值规则

适用于：

- 风险分值
- 调用频率
- 次数限制
- 时间窗口计数

建议参数：

- 阈值类型
- 阈值值
- 窗口周期
- 超限动作

### 5.3 模型规则

适用于：

- 分类模型
- 风险评分模型
- 异常检测模型
- 语义相似度判断

建议参数：

- 模型名称
- 模型版本
- 输入字段
- 置信度阈值
- 结果映射动作

### 5.4 外部服务规则

适用于：

- 外部审核服务
- 第三方风控服务
- 企业内审核 API

建议参数：

- 服务地址
- 请求模板
- 超时与重试策略
- 失败兜底动作

### 5.5 流程规则

适用于：

- 人工审批
- 双人复核
- 升级确认

建议参数：

- 审批流标识
- 审批角色
- 超时动作
- 失败回退动作

## 7. 页面形态建议

### 7.1 不建议的方案

以下两种都不建议作为最终方案：

- 完全一套通用表单
- 每种类型拆一套独立页面

### 7.2 推荐方案

推荐：

**统一规则项页面 + 按类型动态切换配置区**

实现效果：

- 列表统一
- 搜索统一
- 维护入口统一
- 编辑区根据类型切换字段模板

这是后续扩展新类型时成本最低的方案。

## 8. 与策略包的关系

规则项与策略包之间的关系应保持清晰：

- 规则项负责“定义能力”
- 策略包负责“组合能力”
- 接入应用负责“消费能力”

因此：

- 不允许在策略包中临时编辑规则实现细节
- 不建议将模型或算法能力直接定义为“策略包”
- 模型或算法能力应属于“规则实现层”

示例：

| 层级 | 示例 |
|---|---|
| 规则项 | 高危工具审批 |
| 规则实现 | 参数风险评分模型 v2 |
| 策略包 | 研发审计增强包 v2 |
| 绑定对象 | Code_Interpret_Agent |

## 9. 实施顺序建议

### 9.1 第一阶段

实现：

- 统一规则项列表页
- 统一规则项编辑页骨架
- 按类型切换的子表单
- 显式规则 / 阈值规则两类实现方式

### 9.2 第二阶段

实现：

- 模型规则
- 外部服务规则
- 流程规则
- 更完整的条件表达式编辑器

### 9.3 第三阶段

实现：

- 规则实现复用
- 检测能力目录化
- 更细粒度的版本管理
- 干跑 / 模拟命中 / 影响分析

---

## 10. 最终建议

本方案的最终落点如下：

- 保留 `规则项 + 策略包 + 接入应用绑定` 主模型
- 将规则项从“简单表单”升级为“统一骨架 + 类型化配置区”
- 新增 `规则实现` 层，用于承载模型、算法、外部服务等高级能力
- 不为每种策略类型拆独立主页面
- 不用“规则包”来承载模型能力，避免与“策略包”概念冲突

一句话总结：

**最优方案不是“完全一套表单”，也不是“完全分类型页面”，而是统一规则项中心 + 类型化编辑区 + 规则实现层 + 策略包版本化下发。**

- A. 基础信息

## 15. 页面联动规则

### 15.1 基础联动

- 当 `规则类型` 变化时，类型子表单整体重绘
- 当 `执行面` 变化时，`Hook Point` 可选值联动变化
- 当 `规则实现方式` 变化时，实现参数区整体重绘

### 15.2 条件显示联动

- 当主动作包含 `审批` 时，显示审批流字段
- 当主动作包含 `告警` 时，显示通知渠道字段
- 当主动作包含 `脱敏` 时，显示脱敏模板字段
- 当规则类型为 `访问控制` 时，隐藏与内容风险无关的阈值字段

### 15.3 校验联动

- `规则项名称` 必填且长度受限
- `rule_id` 若允许编辑，则需唯一
- `Hook Point` 必须与执行面一致
- `模型规则` 必须选择模型名称和版本
- `外部服务规则` 必须配置响应映射和失败兜底动作
- 保存启用时，必须填写变更说明

## 17. 最终落点

“规则项配置页面字段清单 v2” 的核心目标不是把页面做复杂，而是：

- 让复杂能力有明确承载层

## 19. 原型改造总原则

当前原型不应继续强化“用户直接配置复杂规则项”的主路径，而应改成：

**策略包主入口 + 规则项高级入口**

建议将复杂度分为三层：

### 19.1 普通用户层

主要面向：

- 接入应用负责人
- 业务管理员
- 常规安全运营人员

这类用户只需要完成：

- 选择策略包模板
- 调整少量开关
- 绑定策略包版本
- 查看当前生效内容

不应让其默认进入复杂规则项编辑。

### 19.2 安全运营层

主要面向：

- 安全管理员
- 平台运营人员

这类用户可基于模板创建和调整规则项，但仍应优先走：

- 规则模板
- 场景模板
- 推荐参数

而不是从空白表单开始。

### 19.3 专家层

主要面向：

- 平台专家
- 风控规则专家
- 规则引擎维护人员

这类用户才进入：

- 模型规则
- 外部服务规则
- 流程规则
- fallback 配置
- 响应映射
- 高级表达式模式

因此，原型改造的目标不是删除能力，而是：

**让复杂能力后置、折叠、按角色暴露。**

- 新建规则项

开始，而应从：

- 选择场景模板

开始。

- 场景模板卡片
- 模板推荐说明
- 模板预览

### 21.2 从“空白表单”改为“模板驱动”

当前复杂规则项编辑页虽然完整，但默认对普通用户过重。

建议：

- 新建规则时先弹“模板选择”
- 选模板后带出推荐字段和默认值
- 用户只修改少量关键参数

### 21.3 从“全量字段默认展开”改为“渐进展开”

建议所有复杂字段改成：

- 默认收起
- 按条件显示
- 放在高级区

包括：

- 模型规则
- 外部服务规则
- 流程规则
- fallback
- 响应映射
- 高级表达式

### 21.4 从“文本表达式优先”改为“可视化构造器优先”

对于匹配条件，不建议默认只有自由文本。

建议：

- 默认展示字段 + 运算符 + 值 的条件构造器
- 专家用户再切换为表达式模式

这样可以显著降低配置门槛。

### 21.5 从“配置后未知结果”改为“边配边预览”

建议在策略包和规则项编辑页增加：

- 命中后动作预览
- 影响对象预览
- 示例数据测试
- 自动生成规则说明

用户在填写时就能理解“这条配置会产生什么效果”。
