# 下一步工作方向与产品边界汇报材料

## 1. 汇报主结论

下一步团队建议聚焦在一个方向：建设“面向 Agent 与 AI 应用的安全治理平台”。

对领导可以用一句话说明：

> 我们不是再做一个大模型 Token 授权平台，也不是只做一个敏感词围栏，而是围绕 Agent、MCP、Skill、知识库、模型调用链，做从资产发现、静态扫描、运行时监测、风险处置到审计报表的一体化 AI 安全治理能力。

建议把现有能力对外组织成“两个产品、一个平台内部分层”的结构：

| 名称 | 对外定位 | 核心职责 | 是否与团队A冲突 |
| --- | --- | --- | --- |
| Agent 智能体中心 | 安全可控的 Agent 运行与能力编排中心 | Agent 管理、MCP/Skill/知识库关联、会话与调用链、与安全平台深度联动 | 局部重叠，但可弱化“统一授权”，强调“Agent 运行治理” |
| AI 安全平台 | 面向 Agent 与 AI 应用的一体化安全平台 | 网关防护、资产发现、静态扫描、运行时行为监测、安全引擎、告警审计、报告 | 不冲突，是我们的核心生存空间 |

建议对领导统一称为“AI 安全平台”，不要再单独强调“AI 安全网关是另一个产品”。内部可以把 AI 安全平台拆成两个核心子系统：

- 网关防护子系统：请求链路上的实时执行层，基于 Higress 承担统一入口、认证、限流、脱敏、同步检测、阻断和打标。
- 安全治理子系统：策略、检测、审核、审计、告警、运营治理层，承担资产发现、静态扫描、行为监测、知识库安全和报告闭环。
- Agent 中心：被安全平台深度治理的 Agent 资产与业务运行入口。

### 1.1 建议统一命名

对领导和跨团队沟通时，建议统一使用以下命名：

| 场景 | 推荐叫法 | 不建议叫法 | 原因 |
| --- | --- | --- | --- |
| 对外汇报整体产品 | AI 安全平台 | AI 安全网关 + AI 安全平台两个产品 | 顺应领导已有认知，减少解释成本 |
| 讲 Higress 相关能力 | AI 安全平台的网关防护子系统 | 独立 AI 安全网关产品 | 保留技术边界，但不制造产品割裂 |
| 讲检测、审计、告警、报告 | AI 安全平台的安全治理子系统 | 后台管理端、另一个安全平台 | 强调这是平台核心治理能力 |
| 讲 Agent 深度结合 | Agent 中心 + AI 安全平台 | Agent 平台 + 安全网关 + 安全平台 | 保持汇报结构简单 |

建议统一话术：

> AI 安全平台内部包含两类能力：一类是基于 Higress 的网关防护能力，负责请求链路上的实时拦截和脱敏；另一类是安全治理能力，负责资产发现、静态扫描、运行监测、知识库安全、告警审计和报告闭环。

## 2. 当前核心矛盾与建议口径

### 2.1 领导认知里的混淆点

当前领导可能把以下能力混在一起理解：

- 大模型 Token 授权、统一登录、模型资源管理。
- Agent 智能体中心、MCP、Skill、知识库管理。
- AI 安全网关、敏感词围栏、Prompt 拦截。
- AI 静态扫描、动态运行时检测、服务器侧行为审计。

这里最容易造成的问题是：如果我们继续强调“统一模型 Token 管理、MCP 管理、Skill 管理”，会被自然归入团队A的统一授权与资源管理平台，竞争态势不利。

### 2.2 建议汇报口径

建议把汇报重心从“我们也能做统一授权”转成：

> 团队A偏企业统一入口、统一身份、统一资源授权；我们偏 AI 应用运行后的安全治理和风险闭环。团队A管“谁能用、能用什么资源”，我们管“Agent 实际用了什么、有没有越权、有没有被投毒、有没有泄密、风险如何处置和审计”。

这样既保留合作姿态，也给团队争取清晰空间。

### 2.3 与团队A的合作接口

对领导建议这样讲：

- 团队A负责用户、组织、统一登录、统一授权、模型资源目录、Token 发放等底座能力。
- 我们通过标准接口接入团队A的用户身份、组织权限、模型目录、Agent/MCP/Skill 元数据。
- 我们向团队A和业务系统输出安全检测结果、风险标签、审计链路、告警事件。
- 在边界上，不重复建设“大一统授权平台”，但保留本系统必要的接入 Token、探针注册 Token、SDK 上报鉴权能力。

需要避免的说法：

- 避免说“我们也要做统一模型 Token 管理平台”。
- 避免说“我们替代团队A”。
- 避免把 Agent 中心包装成“全公司统一 AI 平台”，否则容易被认为和团队A正面冲突。

建议采用的说法：

- “我们与团队A共享统一身份和资源底座。”
- “我们补齐 AI 运行安全、Agent 行为审计、知识库投毒检测、MCP/Skill 安全治理能力。”
- “我们做的是团队A平台之上的 AI 安全治理闭环，也可以独立服务第三方 Agent 和模型应用。”

## 3. AI 安全平台的内部分层

### 3.1 对外一句话

> AI 安全平台是一套完整平台，内部既包含请求经过时的实时防护能力，也包含 AI 资产和 Agent 运行过程中的风险治理、审计和闭环能力。

### 3.2 内部分层边界

| 维度 | 网关防护子系统 | 安全治理子系统 |
| --- | --- | --- |
| 核心定位 | 实时安全执行层 | AI 安全治理与运营层 |
| 技术基础 | Higress、Wasm 插件、网关路由 | Client Agent、SDK、OTel、检测引擎、审计存储、控制台 |
| 处理对象 | 经过网关的模型/MCP/OpenAPI 请求 | 服务器上的 Agent、进程、配置、Prompt、MCP、Skill、知识库、文件/命令/网络行为 |
| 工作时机 | 请求进入模型前、模型输出返回前 | 上线前、运行中、事后审计、周期扫描 |
| 决策特点 | 毫秒级，同步放行/拦截/脱敏/打标 | 状态流转、异步扫描、长期分析、告警处置、报告 |
| 优势 | 路径统一、处置快、容易做流量收口 | 视野深、能看到静态配置和运行行为、能形成治理闭环 |
| 局限 | 只能看经过网关的流量，难以看到服务器本地行为和配置风险 | 不直接承担高并发模型转发，不应做主链路网关 |

### 3.3 对领导的解释方式

可以把 AI 安全平台类比成一个完整的安全体系：

- 网关防护子系统类似“门禁和安检机”：请求经过时检查、拦截、放行。
- 安全治理子系统类似“安全运营中心”：知道有哪些资产、谁出了风险、风险从哪来、怎么处置、怎么审计。

因此对外可以统一叫 AI 安全平台，但内部一定要分清实时防护层和治理运营层，否则后续研发范围、性能要求和职责边界会混乱。

## 4. 与其他团队的错位关系

### 4.1 与团队A：统一授权平台

团队A可能覆盖：

- 统一用户登录。
- 模型统一管理。
- Token 授权。
- Agent、MCP、Skill 管理。
- 类似传统 Gateway 的统一入口。

我们的错位空间：

- 不主打“统一授权”，主打“Agent 和 AI 应用安全治理”。
- 不抢全公司统一资源底座，接入它。
- 不只看资源配置，看 Agent 的真实调用链和安全行为。
- 聚焦团队A难以覆盖的服务器侧运行时、知识库投毒、MCP/Skill 风险、行为审计、攻击链分析。

推荐定位：

> 团队A是 AI 资源与身份底座，我们是 AI 安全治理与运行审计能力。两者通过身份、资源、策略、审计接口对接。

### 4.2 与团队C：大模型围栏

团队C偏敏感词、正则、规则拦截等围栏能力。

我们的错位空间：

- 团队C可以作为安全检测引擎的一类能力组件。
- 我们不只做“拦一句话”，而是做规则管理、策略编排、证据链、告警处置、审计报表。
- 我们覆盖 Prompt、Response、MCP、Skill、知识库、行为链，而不是单点敏感词拦截。

推荐定位：

> 团队C的围栏可以接入我们的安全平台，作为检测能力之一；我们负责把检测结果纳入 Agent 资产、调用链、告警处置和安全运营闭环。

### 4.3 与团队D：大模型智栏 PC 客户端

团队D偏 PC 终端侧大模型使用安全。

我们的错位空间：

- 我们聚焦服务器、容器、业务 Agent、MCP 服务、知识库、模型应用运行环境。
- 团队D覆盖办公终端，我们覆盖生产侧 AI 应用和服务器侧 Agent。
- 双方可通过统一事件接口汇总风险，不必抢同一个客户端形态。

推荐定位：

> 团队D做终端侧 AI 使用安全，我们做服务端和业务运行态 AI 安全。未来可以统一汇总到安全平台形成全域视图。

## 5. Agent 中心的建议定位

### 5.1 不建议继续主打的点

Agent 中心不要把核心卖点放在：

- 大模型 Token 统一管理。
- 全公司模型资源统一授权。
- 通用 MCP/Skill 大市场。
- 替代团队A的统一入口。

这些方向容易与团队A正面冲突。

### 5.2 建议主打的点

Agent 中心建议改为：

> 安全可观测、可审计、可治理的 Agent 运行中心。

核心价值不是“谁都能建 Agent”，而是：

- 每个 Agent 的 Prompt、模型、知识库、MCP、Skill 都有清晰台账。
- 每次 Agent 运行都有 Session、Trace、工具调用链。
- 每个 Agent 的权限边界、工具调用次数、执行超时、安全策略可控。
- 每个 Agent 都能接入 AI 安全平台，实现上线前扫描、运行中监测、事后审计。

### 5.3 Agent 中心核心模块

| 模块 | 主要功能 | 与安全平台的结合 |
| --- | --- | --- |
| Agent 资产管理 | Agent 创建、配置、发布、版本、负责人、业务线 | 为安全平台提供资产台账 |
| 模型与 Token 适配 | 调用团队A或模型网关的模型资源，不做大一统底座 | 记录模型调用上下文和 Token 消耗 |
| MCP 管理 | MCP 注册、测试、状态、工具描述、权限关联 | MCP 描述投毒扫描、工具越权检测 |
| Skill 管理 | Skill 注册、Schema、生命周期、执行代理 | Skill 描述扫描、URL 风险、执行审计 |
| 知识库管理 | 文档上传、解析、向量化、权限绑定 | 文档投毒扫描、敏感信息扫描、召回片段复检 |
| 统一会话与 Trace | Session、Message、Tool Call、SSE 事件 | 行为链重建、异常分析、审计取证 |
| Agent 安全配置 | 工具白名单、调用次数、超时、阻断策略 | 安全策略下发与处置闭环 |

## 6. AI 安全平台核心模块

AI 安全平台建议作为团队真正的核心产品。

### 6.0 核心模块总览

对领导建议先用这张表讲清楚“AI 安全平台到底做什么”：

| 核心模块 | 解决的问题 | 核心功能 | 对外价值 |
| --- | --- | --- | --- |
| 网关防护子系统 | 模型和 MCP 请求经过时如何实时防护 | 统一入口、认证鉴权、限流配额、PII 脱敏、输入输出检测、风险阻断、审计打标 | 把所有 AI 请求收口，形成实时防护第一道防线 |
| AI 资产发现与台账 | 企业环境里到底有哪些 AI Agent 和相关资产 | 主机/容器/进程识别、Agent 指纹识别、配置路径发现、生命周期事件、资产拓扑 | 解决“看不见、管不住”的问题 |
| 静态安全扫描 | Agent 上线前和配置层面有没有安全隐患 | Prompt 扫描、MCP 配置扫描、Agent 配置扫描、Skill 扫描、凭证泄露扫描、扫描任务与报告 | 在风险进入运行态前提前发现 |
| 运行时行为监测 | Agent 实际运行时做了什么 | LLM 调用采集、MCP/Skill 调用采集、文件/命令/网络行为监测、Session/Trace 重建 | 看到网关看不到的服务器侧行为 |
| AI 安全检测引擎 | 如何判断 Prompt、工具、知识库和行为是否有风险 | Prompt 注入检测、越狱检测、PII/敏感信息检测、工具投毒检测、行为序列分析、意图对齐审计 | 形成平台核心安全判断能力 |
| 知识库安全检测 | RAG 文档和召回内容是否被投毒或泄密 | 文档上传扫描、隐藏指令检测、敏感信息扫描、文档状态流转、RAG 召回片段复检 | 覆盖普通网关和敏感词围栏难以覆盖的间接注入风险 |
| 策略与权限治理 | Agent 能调用什么、什么情况要阻断或告警 | Agent/MCP/Skill/知识库权限矩阵、工具白名单、阻断策略、规则中心、策略下发 | 把安全规则变成可执行的治理策略 |
| 告警审计与报告 | 风险发现后如何处置和向管理层说明 | 风险事件、告警通知、处置工单、审计日志、Trace 取证、安全评分、周/月报 | 形成从发现到整改的管理闭环 |

如果只能给领导讲 4 个关键词，建议概括为：

- 看得见：发现 AI 资产、Agent、MCP、Skill、知识库。
- 查得出：扫描 Prompt、配置、文档、工具、凭证和行为风险。
- 拦得住：在网关、SDK、Client Agent 三个位置做阻断、脱敏、告警。
- 说得清：用审计、Trace、报告、评分说明风险来源和处置结果。

### 6.1 模块一：AI 资产发现与台账

解决“环境里到底有哪些 AI 资产”的问题。

主要功能：

- 主机资产管理。
- 智能体进程识别。
- 容器和服务识别。
- 配置文件和运行路径发现。
- Agent 生命周期事件上报。
- Agent 与文件、容器、网络、MCP、知识库的关联拓扑。

差异化价值：

- 团队A知道“平台里登记了什么”，我们知道“服务器上实际跑了什么”。
- 网关防护子系统知道“哪些请求经过了我”，安全治理子系统知道“哪些 Agent 在机器上运行、用了哪些配置和资源”。

### 6.2 模块二：静态安全扫描

解决“上线前和配置层面有没有风险”的问题。

主要功能：

- Prompt 注入、越狱、敏感信息扫描。
- MCP 配置扫描：来源可信度、危险工具、权限过大。
- Agent 配置扫描：最小权限、Root/Administrator 运行、明文 Key。
- Skill 描述和参数 Schema 扫描。
- 扫描任务管理、定时扫描、增量扫描。
- 风险报告、整改流转、白名单和豁免审批。

### 6.3 模块三：运行时行为监测

解决“Agent 实际运行时做了什么”的问题。

主要功能：

- LLM 调用事件采集。
- MCP/Skill 工具调用采集。
- 文件操作监控。
- 命令执行监控。
- 网络访问监控。
- Session/Trace 调用链重建。
- 异常工具调用、异常外联、敏感文件读取识别。

差异化价值：

- 能看到网关看不到的本机行为，例如读敏感文件、执行 shell、异常外联。
- 能把 Prompt 注入与后续行为串起来，例如“注入成功 -> 调用高危工具 -> 读取文件 -> 外联发送”。

### 6.4 模块四：AI 安全检测引擎

解决“如何判断风险”的问题。

主要功能：

- Prompt 输入检测。
- 模型输出检测。
- PII 与敏感信息检测。
- 凭证泄露检测。
- MCP 工具描述投毒检测。
- MCP 返回内容注入检测。
- Skill 参数和描述风险检测。
- 行为序列分析。
- 意图对齐审计。

建设方式：

- 基础敏感词、正则、规则库可复用团队C能力。
- Prompt 注入、越狱、PII 等可接入开源或已有引擎。
- 我们重点自研“检测编排、证据链、Agent 行为序列、MCP/Skill/知识库风险模型”。

### 6.5 模块五：知识库安全检测

这是下一步建议重点新增的差异化方向。

主要功能：

- 文档上传后异步安全扫描。
- 文档中隐藏 Prompt 注入检测。
- 文档中敏感信息、凭证、内网地址、涉密词检测。
- 文档来源、上传人、所属 Agent、所属知识库的权限校验。
- 风险文档状态流转：待扫描、已通过、待复核、已阻断、已豁免。
- 风险文档不进入向量化或不参与召回。
- RAG 召回片段二次安全过滤。
- 知识库投毒告警和审计报告。

推荐对领导强调：

> 知识库是 Agent 风险的入口之一。攻击者不一定直接攻击 Prompt，也可能把恶意指令藏在文档、网页、PDF、工具返回内容里，等 Agent 检索后自动执行。因此知识库安全是 AI 安全平台中治理侧能力的重点，普通网关拦截和敏感词围栏都难以完整覆盖。

### 6.6 模块六：策略、告警、审计与报告

解决“风险发现以后如何闭环”的问题。

主要功能：

- 安全策略中心。
- 工具白名单、黑名单、权限矩阵。
- 告警规则和通知渠道。
- 风险事件工单。
- 审计日志检索。
- Trace 取证。
- 周报、月报、合规报告。
- Agent 安全评分。

## 7. AI 安全平台中的网关防护子系统

对外统一称为 AI 安全平台时，原来的 AI 安全网关能力建议改名为“网关防护子系统”或“模型安全接入层”。它不是另一个对外产品，而是 AI 安全平台里的实时执行层。

网关防护子系统负责：

- 所有模型调用统一经过 Higress。
- 所有 MCP 调用统一经过 Higress。
- API Key/JWT 认证。
- Token 配额和限流。
- 输入输出检测接口调用。
- PII 快速脱敏。
- 风险请求阻断。
- 审计字段采集和 TraceId 透传。

安全治理子系统负责：

- 检测引擎。
- 规则中心。
- 权限决策服务。
- 审计日志落库与检索。
- 告警和报告。
- 知识库、MCP、Skill 审核。
- Agent 行为分析。

两者接口：

| 对接点 | 说明 |
| --- | --- |
| `/check/input` | 网关调用安全平台做输入检测 |
| `/check/output` | 网关调用安全平台做输出检测 |
| `/permission/check` | 网关调用安全平台做 Agent/MCP/Skill/知识库权限判断 |
| 审计事件上报 | 网关异步上报请求、风险、Token、Trace 信息 |
| 策略下发 | 安全平台向网关下发 PII、敏感词、阻断、降级策略 |
| TraceId 透传 | 贯通业务系统、网关、安全平台和审计日志 |

### 7.1 我们和原生 Higress 的区别

对领导需要讲清楚：我们不是“把 Higress 部署起来就算 AI 安全平台”，Higress 是底座，我们做的是面向大模型和 Agent 安全场景的产品化增强。

| 维度 | 原生 Higress 能力 | 我们的网关防护子系统 | 差异价值 |
| --- | --- | --- | --- |
| 产品定位 | 云原生 API 网关、Ingress、服务网关 | AI 安全平台的实时防护入口 | 从通用流量治理升级为 AI 场景安全防护 |
| 模型调用支持 | 有 ai-proxy、路由、插件基础 | 模型统一入口、模型供应商适配、模型调用上下文透传、Token 消耗审计 | 能把模型调用纳入统一安全审计 |
| 身份鉴权 | key-auth、jwt-auth、ext-auth 等通用认证插件 | 结合用户、部门、Agent、应用、MCP、Skill、知识库的 AI 资源权限判断 | 从“请求有没有权限”扩展到“Agent 是否有权调用该能力” |
| 限流配额 | 请求级、Key 级、插件级限流配额 | 用户/部门/Agent/API Key/模型维度 Token 配额、成本统计、超限处置 | 更贴合大模型 Token 成本和滥用治理 |
| 输入输出检测 | 原生不内置完整 AI 安全检测体系 | 调用安全治理子系统的输入/输出检测服务，执行 PASS/WARN/BLOCK/SANITIZE | 把检测引擎和网关实时处置打通 |
| PII 与敏感信息 | 可通过插件扩展 | 输入侧快速脱敏、输出侧敏感内容替换、策略可下发、结果可审计 | 形成可配置、可追溯的数据防泄漏能力 |
| MCP/Skill 安全 | 原生只具备通用路由或插件扩展基础 | MCP 路由、工具调用前权限校验、参数摘要采集、风险打标、调用审计 | 覆盖 Agent 工具调用场景 |
| 审计与证据链 | 可记录访问日志 | TraceId/SessionId/AgentId/CheckId 贯穿，审计事件上报安全平台，关联风险事件和调用链 | 从访问日志升级为安全证据链 |
| 策略管理 | 插件配置为主 | 由安全平台统一管理策略、规则、白名单、阻断模式，并下发到网关 | 便于安全运营人员配置，不依赖网关工程师改配置 |
| 告警与报表 | 非核心能力 | 与风险事件、告警、报告、Agent 安全评分联动 | 形成管理闭环 |

可以这样总结：

> Higress 提供网关底座，解决通用流量接入、路由、认证、插件扩展问题；我们在 Higress 之上做 AI 安全产品化增强，重点补齐模型调用安全、Agent 权限、MCP/Skill 审计、输入输出检测、PII 脱敏、审计证据链和策略闭环。

### 7.2 哪些能力复用 Higress，哪些能力是我们新增

| 能力类型 | 复用 Higress | 我们新增或二开 |
| --- | --- | --- |
| 流量入口 | 路由、Ingress、负载均衡、TLS | 模型/MCP/OpenAPI 场景化路由规范 |
| 认证鉴权 | API Key、JWT、ext-auth 插件机制 | Agent/MCP/Skill/知识库权限模型和权限决策接口 |
| 限流配额 | 限流、ai-quota、ai-statistics 基础能力 | Token 成本维度配额、部门/Agent 维度预算、超限策略 |
| 插件机制 | Wasm 扩展能力 | `ai-safety-check`、`pii-detector`、`ai-audit-log` 等 AI 安全插件 |
| 安全检测 | 可调用外部服务 | 输入检测、输出检测、Prompt 注入、越狱、PII、工具投毒检测编排 |
| 审计日志 | 请求响应日志基础能力 | 标准化 AI 审计事件、Trace 证据链、风险事件关联 |
| 管理控制台 | Higress 控制台偏网关配置 | 面向安全运营的策略、告警、报告、资产、知识库安全控制台 |

这部分可以作为我们和“只是 Higress 二开”的关键区别：

- Higress 是基础设施，不直接形成 AI 安全治理产品。
- 我们的价值在于把 Higress 变成 AI 安全平台的实时执行层。
- 真正的产品壁垒在网关与安全治理子系统联动后的闭环能力，而不是单个网关插件。

## 8. 两种解决方案形态

### 8.1 方案一：Agent 中心 + AI 安全平台深度结合

适用场景：

- 公司自有 Agent。
- 新建智能体平台。
- 希望做到深度安全治理。

能力特点：

- Agent 创建时就纳入安全台账。
- Prompt、模型、知识库、MCP、Skill 配置天然可见。
- 会话、Trace、工具调用链完整。
- 可以做上线前扫描、运行中监测、事后审计。
- 可以做 Agent 级安全评分和治理报告。

对领导的表达：

> 这是我们的深度方案。因为 Agent 中心本身掌握 Agent 的配置、知识库、工具和会话链路，所以安全平台能做到更细粒度的监测和闭环。

### 8.2 方案二：独立 AI 安全平台

适用场景：

- 第三方 Agent。
- 其他团队已有 AI 应用。
- 客户已有模型应用和智能体平台。
- 不方便迁移到我们的 Agent 中心。

接入方式：

- Client Agent 探针部署到服务器。
- SDK 插桩接入 Python/Java/Node Agent。
- 通过网关审计日志接入流量数据。
- 通过开放接口同步 Agent/MCP/知识库元数据。

能力特点：

- 覆盖面更广。
- 不要求业务迁移平台。
- 可发现服务器上真实运行的 AI 资产。
- 对第三方系统可做基础监测和审计。

局限：

- 如果没有 Agent 中心的配置信息，会缺少部分语义上下文。
- 对会话、工具、知识库的理解不如深度方案完整。

对领导的表达：

> 这是我们的外部化方案。即使没有 Agent 中心，也可以通过探针、SDK、网关日志接入第三方 Agent 和模型应用，只是深度会比自有 Agent 中心方案弱一些。

## 9. 下一步路线图建议

### 阶段一：边界澄清与 MVP 闭环

周期建议：1-2 个月。

目标：

- 明确团队定位，避免被归入团队A的统一授权平台。

周期建议：3-4 个月。

## 11. 汇报时可直接使用的话术

### 11.1 开场

领导，现在 AI 安全这块如果只理解成 Token 授权或网关拦截，会比较窄。我们建议把下一步方向定义为 Agent 与 AI 应用的安全治理平台，重点解决 Agent 真实运行后带来的风险，包括 Prompt、MCP、Skill、知识库、工具调用、服务器行为和审计闭环。

### 11.2 解释和团队A的关系

团队A更适合做统一身份、组织、模型资源和授权底座，我们不建议重复做一个大一统授权平台。我们的定位是接入团队A的身份和资源能力，在此基础上补齐 AI 安全治理，包括 Agent 运行时行为、知识库投毒检测、MCP/Skill 安全审核、风险处置和审计报告。

### 11.3 解释 AI 安全平台的内部分层

我们对外统一叫 AI 安全平台。这个平台内部有两层能力：第一层是网关防护子系统，在请求经过时实时拦截，动作是放行、阻断、脱敏、打标；第二层是安全治理子系统，负责规则、检测、审核、审计、告警、报表和长期分析。这样既符合一个平台的产品认知，也能保证内部研发边界清晰。

### 11.4 解释我们和 Higress 的区别

Higress 是很好的网关底座，但原生 Higress 解决的是通用流量接入、路由、认证、限流和插件扩展问题。我们要做的是 AI 安全平台，不是简单部署一个 Higress。我们的新增价值在于把模型、Agent、MCP、Skill、知识库这些 AI 语义对象纳入安全治理：网关侧实时拦截，平台侧做检测引擎、权限决策、策略下发、审计证据链、告警处置和报告闭环。

可以简单理解为：

> Higress 提供“路”，我们在这条路上加 AI 安检规则、风险判断、阻断动作、审计证据和安全运营闭环。

### 11.5 解释我们的核心差异化

我们的差异化不是敏感词拦截，也不是 Token 管理，而是能把 Agent 的配置、知识库、工具、模型调用、服务器行为串成一条安全证据链。比如一个文档里藏了恶意指令，Agent 检索后调用了高危 MCP 工具，又读取了服务器文件并外联，这类风险单靠网关或统一授权平台都很难完整发现。

### 11.6 解释两种交付形态

如果业务使用我们的 Agent 中心，安全平台可以做到最深，因为 Agent 的配置、工具、知识库和会话链路都在我们掌握范围内。如果业务不用我们的 Agent 中心，我们也可以通过探针、SDK、网关日志和开放接口接入第三方 Agent，但安全深度会相对弱一些。

## 12. 最推荐争取的团队生存空间

建议团队优先争取以下方向：

1. Agent 运行安全监测。
2. 服务器侧 AI 资产发现与静态扫描。
3. MCP/Skill 安全审核与运行审计。
4. 知识库文档投毒检测与 RAG 召回安全。
5. Agent 调用链 Trace、行为序列分析、攻击链还原。
6. 安全告警、审计报告、治理闭环。

这些方向与团队A的统一授权平台、团队C的围栏能力、团队D的 PC 客户端都有明显差异，更适合作为我们团队下一步的主线。
